### D-001 — Clean-room policy and licensing default (2026-10-04, accepted)
**Context:** We reproduce Urban Terror's movement and balance. Its assets and game code are proprietary; Quake III's code is GPL v2.
**Decision:**
- Use no UrT files, code, names or assets, and do not decompile or reverse-engineer its binaries.
- Use no GPL code. Implement from our specs; observing the original's behavior is allowed.
- Shipped dependencies are permissive only (MIT/BSD/Apache/ISC/MPL).

**Consequences:** some constants are ESTIMATE until measured from gameplay captures. We keep licensing options open (decision O-5).

### D-002 — Tech stack (2026-10-04, accepted)
**Decision:** TypeScript strict monorepo (pnpm), Vite client, Node LTS server, Vitest, Biome, Three.js (`WebGLRenderer` first), `ws` for WebSocket.
**Why:** one language across server, worker and client; mature tooling; Mustafa's existing Three.js/React experience (FORGE).
**Consequences:** performance discipline needed in JS hot paths (`docs/06` §9).

### D-003 — Server-authoritative Q3-style netcode (2026-10-04, accepted)
**Decision:**
- Inputs-only clients. Shared deterministic sim; client prediction + reconciliation.
- Snapshot interpolation for remote entities. Hitscan lag compensation with capped rewind (200 ms).

**Consequences:** every gameplay feature must define networked state, prediction and tests.

### D-004 — 60 Hz fixed tick (2026-10-04, accepted)
**Context:** UrT ended at a 20 Hz server rate. Modern competitive shooters run 60–128 Hz.
**Decision:** 60 Hz simulation, snapshots (30 Hz fallback per client) and inputs (with 4-cmd redundancy). Render decoupled with interpolation.
**Consequences:** movement feel is tuned at 60 Hz; changing the tick requires re-tuning (`docs/03` §1).

### D-005 — Everything runs through a server, even offline (2026-10-04, accepted)
**Decision:** local play uses the same server code in a Web Worker over a loopback transport, plus a network simulator.
**Why:** netcode is never an afterthought; one gameplay path.

### D-006 — Units and axes (2026-10-04, accepted)
**Decision:** 1 u = 1 inch, Z-up in sim, maps and netcode. Conversion to Three.js Y-up meters happens only in `client/render/space.ts`.
**Why:** matches UrT's unit convention and TrenchBroom/Quake map space; avoids conversion bugs in physics.

### D-007 — Brush-based collision; no physics engine for players (2026-10-04, accepted)
**Decision:** world collision = convex brushes (planes) with swept-AABB traces; Q3-style kinematic collide-and-slide.
**Why:** crisp, predictable edges are essential for wall jumps, ledge grabs and slides. Triangle meshes cause internal-edge snags.

### D-008 — Compiled map format + TrenchBroom via Valve 220 (2026-10-04, accepted)
**Decision:**
- A greybox TypeScript builder first.
- In M5, a TrenchBroom `.map` (Valve 220) compiler producing the same `cmap`.
- Custom TrenchBroom game config + FGD.

### D-009 — Transport abstraction; WebSocket first, WebTransport later (2026-10-04, accepted)
**Decision:** all messages are designed for unreliable delivery (acks, baselines, redundancy). Ship WebSocket in M3; add WebTransport datagrams with fallback in M9.
**Why:** WebTransport reached all major browsers in 2026, but server-side tooling is younger. WebSocket's head-of-line blocking is acceptable early on.

### D-013 — Art direction: "Comic Noir" (2026-10-04, accepted)
**Context:** O-4 was open. The game needs its own visual identity (pillar 5) that stays readable at competitive speed and fits the browser performance budgets.
**Decision:**
- Adopt **"Comic Noir"**: a modern Franco-Belgian comic look inspired by XIII (2003), rebuilt for a competitive browser FPS. The rules live in `docs/08`; `docs/08a` is reference research, not rules.
- Core techniques: banded lighting with tinted shadows over baked lightmaps, pixel-width hull outlines on actors, compiler-emitted crease lines plus a screen-space edge pass, world-space hatching on environments only, onomatopoeia lettering and comic panels.
- When rules collide: readability and fairness → performance budgets → style fidelity.
- Borrow the style family only: no XIII characters, story elements, logos, UI layouts or traced art (`docs/08` §3).
- Onomatopoeia is generated only from sound events the client legitimately receives (`docs/08` §11.2).

**Why:** flat color, baked light and ink lines are cheap to render in a browser and suit brush-built maps (`docs/08` §6, §7.2). Onomatopoeia doubles as a fair sound visualizer and an accessibility feature (`docs/08` §11).
**Consequences:**
- Exact parameters (bands, line widths, palettes, team colors, lettering font) are locked in look-dev (`docs/08` §17) and recorded in a later D-entry.
- Art work starts before M8 (`docs/08` §18): an optional style spike after M2, crease-line data from the compiler in M5, comic FX and UI hooks in M6–M7.
- Baked world lighting narrows the `docs/07` §5 lighting choice to a lightmap bake (options 1–2).

### D-015 — The dedicated-server dev command is `pnpm dev:server` (2026-10-04, accepted)
**Context:** the docs named it `pnpm server`, but pnpm 10 has a built-in `pnpm server` command (it manages a store server). Built-in commands take priority over package scripts, so `pnpm server` silently did nothing and exited 0.
**Decision:** the root script is `dev:server`. It runs the server from source with tsx. Production runs the esbuild bundle that `pnpm build` produces (`node packages/server/dist/main.js`).

### D-016 — Deterministic math (2026-10-05, accepted)
**Context:** prediction needs client and server to compute bit-identical results. ECMA-262 lets engines approximate `Math.sin`, `cos`, `atan2`, `pow`, `exp`, `log`, `hypot` and the other transcendental functions, so Chrome, Firefox and Safari can return different bits for the same input. A one-ulp difference is enough to diverge a predicted state from the server's.
**Decision:**
- **Banned** in `packages/shared` and in compiler code that produces output (the greybox compiler from M1, `mapc` later): `Math.acos`, `acosh`, `asin`, `asinh`, `atan`, `atanh`, `atan2`, `cbrt`, `cos`, `cosh`, `exp`, `expm1`, `hypot`, `log`, `log1p`, `log10`, `log2`, `pow`, `sin`, `sinh`, `tan`, `tanh`, and the `**`/`**=` operators (they are `pow`).
- **Allowed**, because the spec rounds them exactly: `+ − * / %`, `Math.sqrt`, `fround`, `round` (halves toward +∞), `floor`, `ceil`, `trunc`, `abs`, `sign`, `min`, `max`, `imul`, `clz32`, bitwise operators, number literal parsing, and constants such as `Math.PI`.
- **Trig:** `math/dtrig.ts` builds `dsin`/`dcos` from exact operations only (Cody–Waite reduction, Taylor polynomials, |x| < 1e5), plus a quarter-wave table for u16 angles: `sinU16`/`cosU16` are exact at the cardinal angles and exactly odd and even.
- **Vectors** are `Float64Array`s with out-params. Modules keep named scratch vectors instead of sharing a general pool, which would add bookkeeping and aliasing bugs for no allocation benefit (`docs/06` §3 and §5).
- Never route sim values through a `Float32Array` (render code copies, never writes back), never store NaN, normalize −0 to +0 when quantizing, and never enable "unsafe math" minifier options.
- `dpow` (from deterministic exp and log) follows in M4 for the fall-damage curve.

**Consequences:**
- The shared purity guard rejects the banned names and `**`, and flags any use of `Math` other than `Math.<allowed member>` (computed access, optional chaining, aliasing, destructuring). The rules live in `packages/tools/src/code/deterministicMath.ts`, so compiler code can reuse them.
- The same guard flags any bare `Date` (an alias would reach `Date.now`), locale-dependent APIs (`localeCompare`, `toLocale*`, `Intl`), whose results vary by engine and locale, and `\u` escapes outside strings, which would hide a banned identifier from every name rule.
- Committed determinism vectors (`packages/shared/test/vectors/determinism.ts`, input bits → output bits for dtrig, quantizers, `quantizePlayerState`, `sanitizeUserCmd`, Mulberry32 and hash32) are recomputed by the tests; M2 replays them in Chrome, Firefox and Safari (`docs/09` M2, `docs/10` §1).
- Constants that were written with `**` in shared (the cvar registry's i32 range) are now literals.

### D-017 — Trace epsilon, touching, and snapping to the nearest clear grid point (2026-10-05, accepted)
**Context:** M1 builds the brush traces (M1 design A, `docs/design/M1-design.md`) and needs a rule for contact. `docs/05` §4.1 and `docs/03` §6 rounded the origin to the nearest 1/32 u every tick. That is safe after a single stop, but not across repeated slides on a slope or a rotated wall: sliding keeps the distance to the plane unchanged, each tick's rounding moves the box by up to √3/64 u along the normal, and nothing pulls it back. Within tens of ticks the box sits inside the brush, the next trace starts solid and the player is stuck. Axis-aligned planes at grid distances can't drift, so only slopes and angled walls (the kick lanes) show it.
**Decision:**
- **ε = 1/32 u** (`TRACE_EPSILON` in `packages/shared/src/world/trace.ts`): a trace stops one skin short of the surface it hits. It is a design constant, not a cvar: client and server must trace identically, and ε is not a feel knob. It is exact in binary and one origin grid step.
- **Touching counts as outside.** Inside a brush means strictly behind every plane, so a box that exactly touches a brush is clear: a spawn with its feet on the floor, or a box flush against two brushes.
- **Trace rules:** entering times stop ε early and leaving times are exact, so in exact math a box can touch a brush but never enter it. A move that does not approach a plane, as computed, is free, which covers sliding on a face or inside the skin; one that approaches it from inside the skin stops at once without `startSolid`. Ties between brushes go to the lower brush index, so the result never depends on visiting order. `endpos` copies the end exactly at fraction 1 and the start at fraction 0, and the reported plane is the brush plane, not the box-expanded one.
- **End-of-tick snap** (`snapOrigin`): the nearest **clear** 1/32 u grid point, in this order:
  1. the rounded point, if a position test says it is clear;
  2. otherwise the 8 corners of the grid cell holding the exact position, nearest first, ties in corner bit order (bit 0 = x rounded up, bit 1 = y, bit 2 = z);
  3. otherwise last tick's origin, which was on the grid and clear.
- The snap tests world brushes only (the mask excludes players), so a client's prediction never depends on where it thinks other players are. The common case costs one position test per player-tick.

**Consequences:**
- pmove calls `snapOrigin` at the end of every tick from M2, instead of plain rounding. `quantizeOrigin` stays the codec primitive: the snap only chooses which grid point, and the result is already on the grid. Positions stay out of solid by induction: traces never end inside a brush, the snap never accepts a solid point, and the course tests check that spawns are clear.
- **Map metrics:** on a flat floor a player rests at floor + 1/32. Crouched, the hull top is then at 40 + 1/32 u, so a 40 u gap blocks: slide gaps are 41–44 u (the courses use 41, 42 and 44) and the crouch tunnel is 48 u. An 18 u step still clears and a 19 u step blocks. `docs/07` §3 and §6 say so.
- `docs/05` §4.1 and `docs/03` §6 say "nearest clear 1/32 u grid point"; `docs/03` §4 states the trace contract.
- **Tangency is not exact on angled planes.** On slopes and rotated walls a move along the stored plane can round to approaching it by a few ulps (about 1e-14 u), and from inside the skin that stops the trace at fraction 0. We keep the rule table rather than add a tolerance, because a tolerance would let slow inward drift through; M2's slide move leaves a plane through the overclip (`docs/03` §4.7) and the same-plane nudge (§4.8), not exact tangency. The M2 feel tests on the slope set watch for stalls.
- An `allSolid` trace reports no hit (brush and plane −1, zero normal, no surface flags; contents are the brushes it started in), even when a later brush lies on its path: the box never moves, so that brush is not a contact (M1 review; one committed trace vector changed).
- Traces and position queries reject coordinates beyond ±2^20 u (`TRACE_COORD_LIMIT`) like NaN: farther out, f64 rounding eats the skin and then whole brushes.
- The cost is corner snags of up to ε when a box passes within ε of an edge. Shrinking the leaving time by ε instead would allow real penetrations of up to ε, which would show up as `startSolid` on the next tick.
- Tests: `packages/shared/test/world/{trace,traceQueries,snapOrigin}.test.ts`, including slide-and-snap chains on 0.69/0.71/0.8 slopes and 15/30/45/60° walls: the snap never goes solid, and plain rounding does on every surface except the 45° wall, where rounding x and y moves the plane distance monotonically and by less than ε, so it cannot drift. Committed trace vectors in `packages/shared/test/vectors/trace.ts` (input bits → output bits on a fixed world) are recomputed by the tests, and M2 replays them in browsers. The increment 9 fuzz test adds 200-step snap chains (P7).

### D-018 — PlayerState and UserCmd layout for M1 (2026-10-05, accepted)
**Context:** M1 implements `PlayerState` (`docs/03` §6) and `UserCmd` (`docs/05` §3.4). Both docs leave the bit order, the fixed-point stamina format and the field ranges open, and `docs/05` lists "kick-eligible" among the buttons although it reads as derived state.
**Decision:**
- **Kick-eligible is not a button.** It reads as state derived from the player and the weapon, not an input, so it is left out until the kick is built in M4 (M1 plan, open question 1). `buttons` bits 0–11 are attack … drop in the `docs/05` order; bits 12–15 are spare.
- **Stamina** is an integer count of hundredths (u16). `flags` bits 0–9 are the `docs/03` §6 flags in the listed order.
- **Ranges:** `origin` ±16384 u and `velocity` ±(2^19 − 1)/16 u/s (±32767.9375, the i20 range) per axis, clamped by the end-of-tick quantizers so a stored value is exactly what the codec carries; `groundEntity` −1 (none) to 32767 (the world); `waterLevel` 0–3; move axes ±127 (the i8 never carries −128); pitch ±89°; `weaponSlot` 0–7 (the knife plus the seven `docs/04` §9 loadout slots); `tick` 0…2^30 − 1 (not the full u32), so ticks stay V8 small integers (about 207 days at 60 Hz).
- `quantizePlayerState` maps a non-finite `groundEntity` to −1, not 0, because 0 is a real entity. `sanitizeUserCmd` clamps and masks untrusted input and never throws. It is idempotent, and the client applies it before predicting, storing and sending a cmd (`docs/05` §5), so client and server simulate the same cmd.

**Consequences:**
- `docs/03` §6 and `docs/05` §3.4 carry "Pinned down in M1" notes; the code is in `packages/shared/src/sim/`.
- M1 implements the `docs/03` §6 fields `origin`, `velocity`, the view angles, `flags`, `groundEntity`, `waterLevel` and `stamina`. `wallJumps`, `health`, `armor`, `breathMs`/`drownMs`, `climbTarget`, the timers and `movementEvents` are appended to `PlayerState` (with their quantize, codec and parity coverage) by the milestone that first simulates them.
- Open for later milestones: whether kick-eligible needs any wire bit (M4), and which `weaponSlot` index is which and whether out-of-range slots clamp or mean "no change" (weapon switching). The `docs/03` §2 hull table is labelled FACT for Q3 (Mustafa, 2026-10-06).

### D-019 — Brush contents, surface flags and build rules for M1 (2026-10-05, accepted)
**Context:** M1 implements the collision brushes of `docs/07` §2. The doc names the contents flags and optional per-side surface flags but leaves their bits open, and §4.3 says to reject degenerate brushes without saying what degenerate means. Traces also need bevel planes, which the doc does not mention (M1 design B).
**Decision:**
- Contents bits 0–7 in the `docs/07` §2 order; masks `MASK_PLAYERSOLID` (solid + playerclip), `MASK_SOLID`, `MASK_WATER`.
- Surface flags per side: ladder, slick and nodamage bits (`docs/03` §4.10, §4.14, §5.6), plus a 4-bit footstep material field (`docs/07` §6 prefixes). M2 decides whether ladders use the face flag or the LADDER volume; M1 provides both.
- Brushes are built from f32-rounded planes, so polygons, bevels, bounds and render vertices agree with what traces use. Axial bevels follow the faces with outward-rounded distances; they make boxes, boxes rotated about Z and axis-aligned wedges exact. `buildBrush` adds only axial bevels, so other shapes build but trace inexactly: the greybox MapBuilder (increment 7) rejects shapes that would need edge bevels, and `mapc` adds edge bevels in M5.
- Cleanup rules the design left open: a vertex near its neighbours' line (1e-4 u) is removed only when it lies on fewer than 3 kept faces, so a real corner where two faces meet almost flat stays; vertices within 1e-5 u of an exactly axial face snap onto it, so axial coordinates are exact and the face distance is a tight bound.
- Each brush's bounds must be exactly the distances of six axial planes among its faces and bevels; `createCollisionWorld` rejects other bounds (increment 5). The BVH culls by these bounds, so a brush reaching past them would make `traceBox` drop hits that `traceBoxBrute` reports.
- Validation thresholds: weld 1/64 u (§4.3), minimum edge 1/8 u, no two vertices of a face within the weld distance, minimum volume above 1 u³, vertex-on-plane tolerance 1e-4 u, world limit ±16384 u (a plane further than 16384·√3 + 1 u from the origin is rejected up front, since no face of an in-bounds brush can be there).

**Consequences:**
- `docs/07` §2 carries a "Pinned down in M1" note and `docs/06` §3 lists the world modules.
- The shared polygonizer is the single implementation: the greybox compiler (M1), `mapc` (M5) and the trace fuzz oracle all use it, and its own tests cross-check it against brute-force triple-plane intersection.
- Outward-rounded bevels make the traced brush reach up to one f32 step of the coordinate past its vertices (about 1e-4 u at 1000 u, 1e-3 u near the ±16384 u limit), and position tests call a box in that sliver solid. Traces stop ε short of bevels like any other plane and the snap only accepts clear points, so a player never ends up there. The trace fuzz test (`packages/tools/test/fuzz/`) compares traces with exact geometry, so wherever the runtime may report contact beyond the true brush (P2, P3, P4) it allows that brush's sliver on top of τ = 1e-5, capped at one f32 step of the brush's largest vertex coordinate so a misplaced bevel cannot widen its own tolerance. P1 inherits the allowance: it excuses the brushes the runtime puts the start inside, and by M1 design A.4 (a box may move out of a brush it starts in) a box starting in the sliver may move through that brush; P2 bounds that set to τ + sliver, and such starts are unreachable in play. P4 checks the stop two-sided: at most M1 design G's 2√3·ε + τ (+ sliver), and at least ε − 1e-6 when the trace moved, because the entering plane is then exactly ε away.

### D-020 — cmap v1 layout: contentHash in a binary preamble (2026-10-05, accepted)
**Context:** `docs/07` §2 put `contentHash` in the JSON header, which would make the hash cover a header that contains it, and allowed a `.cmap.json` + `.cmap.bin` pair in dev. D-008 fixes the format's role, not its layout (M1 plan, spec change 3).
**Decision:**
- One little-endian file: a 32-byte preamble (magic, `formatVersion`, JSON length, section count, the 64-bit `contentHash`, total length), a section table, canonical ASCII JSON metadata, then 8-aligned binary sections (`PLNS`, `PLSF`, `BRSH`, `SURF`, `VTXS`, `IDXS`). No dev file pair: the greybox compiler writes the single file directly.
- `contentHash` is two Murmur3 x86_32 lanes over the whole file with the hash field read as zero: every other byte is covered, the hash never covers itself. This includes the preamble (the M1 plan said bytes [32, EOF)), so a corrupted `formatVersion`, length or reserved word also changes it. Identity and caching only, not security.
- The decoder accepts only the exact layout the encoder writes (sections contiguous in table order, zero padding, nothing after the last section, JSON followed by fewer than 8 spaces), so no two accepted files differ only in filler bytes.
- M1 review tightened this to the content the encoder writes as well: the JSON must be exactly `canonicalJson` of its parsed value (moved from tools to `packages/shared/src/world/canonicalJson.ts` so the decoder can check it), entity origins lie within ±16384 u, the header bounds equal the union of the brush bounds, and render surfaces tile `VTXS`/`IDXS` in order, one non-empty surface per material in increasing order. Overlapping surfaces made the index check cost surfaces × indices, so a small hostile file could stall a loader; tiled, it is linear. Every committed map already met these rules, so no map changed. A size cap for maps sent over the network is left to the milestone that first sends one.
- The BVH is built at load time, deterministically, not stored. Unknown section tags are ignored; `formatVersion` changes when the layout breaks, `compiler.version` when output changes on purpose.

**Consequences:**
- `docs/07` §2 carries the layout tables; `decodeCmap` validates everything and throws `CmapError`; `*.cmap` is `binary` in `.gitattributes`. Tests: `packages/tools/test/greybox/cmap.test.ts`, `packages/shared/test/world/cmap{,Hash}.test.ts`.

### D-021 — Greybox builder API and render-surface conventions (2026-10-05, accepted)
**Context:** M1 increment 7 builds the greybox compiler and `MapBuilder` (`docs/07` §3). The doc's API sketch has no slopes with a target normal, rotated boxes, ladders with a face flag or named anchors, which the courses need (M1 design I), and it leaves open where entity yaw goes, which faces render and how uv0 is mapped.
**Decision:**
- `MapBuilder` adds `slope` (rise = run·√(1 − nz²)/nz, returns the compiled wedge's f32 top so a platform at that z shares the crest's plane distance), `rotatedBox` (closed-form cos/sin, D-016), `ladder` (wall with the ladder surface flag plus a 16 u LADDER volume, both until M2 picks one, D-019) and `anchor` (`info_target` with `targetname`). `stairs`, `ramp` and `slope` return their top z.
- `ramp` must be axis-aligned; the builder throws otherwise. Every brush also passes an exactness check (each edge × axis, oriented outward between the edge's two face normals, is parallel within 1e-6 to an axis or points the same way as a face normal), so nothing that needs edge bevels compiles before `mapc` adds them in M5. A call that throws adds none of its brushes.
- Entity `angles` are [pitch, yaw, roll] in degrees, yaw 0 facing +x (now stated in `docs/07` §2); the builder stores yaw there as [0, yaw, 0], not in `props`.
- Render surfaces: one per material in material order (the table is in order of first use); solid brushes and water volumes render, clip, trigger, nodraw and other non-solid volumes don't; fans from each polygon's canonical start vertex, counter-clockwise from outside, f32 positions, flat face normals.
- uv0 is a world-space planar projection on the normal's dominant axis (ties to z, then x) at 1 uv per 64 u, which M2's grid texture relies on.
- `compile()` returns the decoded file (validated, with its hash); `compiler.version` starts at 1.

**Consequences:**
- `docs/07` §3 lists the API and conventions. Courses (increment 8) use anchors instead of coordinates in tests.
- The D-016 math ban now also guards `packages/tools/src/greybox` (`greybox-determinism.test.ts`), as D-016 already required.
- Tests: `packages/tools/test/greybox/{brushCompiler,mapBuilder}.test.ts`.
- Courses (increment 8): each course in `packages/tools/src/greybox/courses/` is a function that builds and returns its Cmap, listed in a fixed order in `courses/index.ts`. `pnpm greybox` writes them to `content/maps/<name>.cmap`, which is committed (M1 plan); a test fails with "run pnpm greybox and commit" when a file is stale. Anchors and spawns are standing spots (origin = ground + 24 u). `docs/07` §3 lists the sizes the courses pin down (lab area, water depths 12/36/128 u, slide gaps 41/42/44 u plus a blocking 40 u gap, 48 u tunnel, runway timers 2048 u apart, catch rails 64 u tall in separate columns so one catches a 768 u fall); they are design values, not ESTIMATEs of the original game.

### D-022 — Browser determinism replay (2026-10-06, accepted)
**Context:** D-016 and D-017 freeze the bits of the deterministic math and the traces as vectors, and the M1 plan promised a replay in real browsers in M2 (risk 2), because clients predict with the same code in Chrome, Firefox and Safari. M2 plan, increment 1 and risks 4–5.
**Decision:**
- Vitest browser mode with `@vitest/browser-playwright` (MIT) replays every `packages/shared/test/*-vectors.test.ts` unchanged, headless, from `vitest.browser.config.ts`; `pnpm test:browser` runs it and `pnpm test` (the Node run) never loads it. The vectors tests stay free of Node APIs and other packages: `packages/shared`'s `types: []` makes a `node:` import fail the type check, and `packages/tools/test/guards/browser-vectors.test.ts` checks that everything they load is a relative module or `vitest`, that the config stays in headless browser mode on that glob, and that the CI job's test step runs all three engines.
- `BROWSERS` (comma list of `chromium`, `firefox`, `webkit`; default `chromium`) picks the engines; an unknown, repeated or missing name stops the run. The dev container uses its preinstalled Chromium build and never runs `playwright install`; a CI job `browsers` installs all three with `playwright install --with-deps` and runs them, and other machines can run `pnpm exec playwright install` (README).
- WebKit runs JavaScriptCore, Safari's engine, so it stands in for Safari. It is not Safari itself; a phone test page for real Safari or Chrome on a phone comes in M2 increment 12.

### D-023 — pmove contract (2026-10-06, accepted)
**Context:** M2 increment 3 builds the base pmove pipeline (`docs/03` §3, §4.4–§4.11). The spec left four things open: what "starts in solid" means now that D-017 distinguishes `startSolid` from `allSolid`; where slick and nodamage come from, since bevel planes carry no face flags; what "crouch-blocked" means; and how the tick length and the movement events reach and leave pmove (M2 plan, "Spec decisions"; M2 design §2–§3).
**Decision:**
- **Signature:** `pmove(ps, cmd, world, params, dt, events | null, debugLog | null)` updates `ps` in place.
  - `cmd` is already sanitized.
  - `dt` is a parameter: `TICK_DT` in play, 1/120 s only in tests (MV-04).
  - `params` is `PmoveParams`, refreshed outside the tick when `CvarRegistry.version` changes.
  - `events` (step, jump, land) and the trace log are output only. No `PlayerState` fields are added, and the hull changes only in the pre-checks, at the tick's start origin.
  - Each tick ends with `snapOrigin` (fallback: the start origin), then `quantizePlayerState`.
- **Stuck rule (Q1):** the slide move stops only on an **allSolid** sweep: it zeroes vz, reports blocked and asserts in dev, since the snap keeps every start clear. A `startSolid` sweep that is not `allSolid` moves out of the brush and is accepted.
- **Ground surface (Q3):** ground is slick or nodamage when the hit plane's `SURF_*` bit **or** the hit brush's `CONTENTS_SLICK`/`CONTENTS_NODAMAGE` bit is set. Bevels keep flags 0, but `trace.contents` keeps the brush bits, so ramp crests work with no map format change.
- **Crouch-blocked:** crouched with the standing hull blocked at the origin, so no jump under a ceiling. Crouch-jumping in the open is allowed.
- **LAND value:** the downward speed at the start of the landing tick.
- **Landing clip:** when the ground trace turns an airborne player grounded, the velocity is clipped against the ground plane. Without it a fall that ended within `pm_groundTraceDist` of the floor, untouched by the slide sweep, kept its full vz, and the walk move's slope-following rescale turned it into horizontal speed (up to 690 u/s from a run-jump).
- **Ground settle:** after the move, a grounded player is moved down to the ground trace's end point before the snap. A walk along a slope rounds by the same vector every tick, and the accumulated drift otherwise lifted the player past the probe every 3–4 ticks (an air tick and a spurious LAND each time).
- **Step-down trace and ties:** the stepped path is traced back down by the raise plus `pm_groundTraceDist`, so it finds the floor at the start height. A stepped path within 1/16 u of the plain one (either way) is a tie: the plain origin, with whichever path's velocity kept more horizontal speed. Before this, a plain slide that touched a riser at a tick's end won with a velocity clipped to 0, and 7% (run) to 19% (walk) of stair approaches snagged to a stop.
- **Slope crests (M2 increment 4):** in the walk move the step-down trace also covers any rise of the stepped slide itself, so it reaches at least `pm_groundTraceDist` below the start height. A hull walking up a slope rides it inside the ε skin, so at the crest it meets the platform's riser a few hundredths of a unit below the platform top. The stepped path rose with the walk (3.8 u a tick on a 0.71 slope at the run cap), the old trace stopped above the platform, and the plain path's clip left the player stalled at 0.3 u/s of horizontal speed, popped 33 u into the air. MV-06 found it on `movement_lab`: before the fix 66–89% of start phases stalled at the crest (by slope and speed), after it none do. Air moves keep the old trace: there, reaching down further would pull a rising jump onto the ledge beside it.
- **Crest kick-off (accepted):** where the plain slide clears the riser lip instead (a few percent of start phases at the run cap on 0.71, none on 0.8; about a quarter at walk speed on 0.8), the walk reaches the platform still carrying the slope's vz, and the ground trace's kick-off rule (`docs/03` §4.10, vz > 0 and v·n > 10 against the flat platform) makes it airborne for one ballistic hop at the speed it had: up to 35 u and 35 ticks from 0.71 at the run cap, under 10 u at walk speed. It follows from the kick-off rule as specified (suppressing it would change that rule, so it stays open for a feel decision), and it depends on where a tick ends at the crest, so MV-06 allows it at the crest only (never on the incline, never gaining vz, at most one LAND).
- **Steep toes (accepted for now):** a hull whose feet are exactly on the floor (an anchor start, and a fresh spawn until D-027 raised it; a walk on flat ground never lifts it) meets the toe of a steep (non-walkable) wedge on the wedge's axial bevel, which the trace reports at the same fraction as the slope plane, and stops there as at a wall without touching the slope. A hull one ε above the floor (any player that has landed, D-017) is clipped onto the slope, slides back down and lands, and while forward is held repeats that jitter at the toe (about one LAND every 7–18 ticks). Walkable slopes are unaffected: the step-up carries both onto them. The match loop's spawn rests at floor + ε (D-027, M2 increment 9), so only anchor starts in tests have their feet exactly on the floor; MV-06 pins both behaviours so a change is noticed.
- **Steep crevices** (a V of non-walkable planes) can hold a player who can neither slide out nor jump. Accepted as base-movement behaviour; maps must avoid them, and a map-validation check is planned with the map pipeline.
- **Slide-move clip order:** as `docs/03` §4.8 step 4 says, the plane just hit is clipped against first, then every stored plane the result still moves into. Starting from the first stored plane instead would let the flat ground plane (which a level walk only grazes, so its clip changes nothing) use up the pass, and an acute corner would then not stop the move.
- **Design constants**, not cvars (the same code runs on client and server, and none is a feel knob):
  - same plane: normals' dot > 0.99;
  - a stored plane is cleared only when the velocity leaves it at more than 0.1 u/s;
  - a stepped path must get 1/16 u farther than the plain one;
  - a step event needs |Δz| ≥ 1/32 u.

  In the seeded random-input property run (`pmoveProperty.test.ts`), the step margins remove spurious "steps" (−2.5 u while falling past edges, 0.05 u on a slope) and leave the run's other tallies unchanged. Walking up a slope still tries the stepped path whenever a sweep grazes the slope; the 1/16 u margin is what keeps those from becoming step events.

**Consequences:**
- `docs/03` §3 states the contract and §4.8–§4.11 the rules above. The code is in `packages/shared/src/sim/pmove/` (`slideMove`, `stepSlideMove`, `ground`, `walk`, `debug`, `pmove`). It is tested in `packages/shared/test/sim/pmove/`, including a seeded 1e4-tick random-input property on slopes and rotated walls: never in solid, no consecutive previous-origin fallbacks.
- **Native ESM (M2 plan, risk 3):** pmove's move functions are too big for V8 to inline every call, and a double passed to a call that isn't inlined is boxed. So per-tick shared code passes no computed doubles across calls:
  - `accelerate(v, wishVel, kind, params, dt)` and `clipVelocity(out, v, n, params)` replace the increment-2 forms that took wishSpeed, coefficient and overclip;
  - `PmoveEvents.pushFrom` takes the event value from an array;
  - `angleVectors` gets sine and cosine from `sinCosU16` (same bits as `sinU16`/`cosU16`) through an out-array;
  - the slide move keeps its remaining time in a typed array.

  The native-ESM `pmove` workload allocates nothing. Rarely run code (a landing, a step) still boxes about 16 B per event until V8 optimizes it. Worse, a branch first reached after V8 has optimized its function (M2 review: the slide move's second clip on the first stairs, the first ladder) deoptimizes it, and every tick then boxes doubles until V8 optimizes it again (the first stairs: 40–230 B per tick over the first 2e4 ticks, about 42 B over the next 2e4, then under 1 B; measured as in `docs/10` §4): a one-off transient per process, not a steady state, and invisible to guards that warm up and measure the same mix (`docs/10` §4, known limit). The mitigation, a deterministic pmove primer at match and prediction start that reaches the late branches before the warm-up, with a late-branch native-ESM allocation workload to guard it, lands in M3 beside NET-09's server GC measurement.
- **Bench:** `pnpm bench` times pmove on `movement_lab` against the `docs/10` §4.4 budget, at about 1.6–1.75 µs per player-tick with 0 GCs (`docs/10` §4.4).
- **Tests** for the landing, settle and step rules sweep their phases: drops onto flat ground from 8–120 u in 1/8 u steps never exceed the run cap; 300-tick walks up and down 0.71–0.99 slopes at run and walk speed have no air tick and no LAND; stair climbs from 192 start offsets in 1/32 u steps never drop below 90% of the cap.

### D-024 — Ladders and water (2026-10-06, accepted)
**Context:** M2 increment 5 adds crouch, water and ladder movement (`docs/03` §4.12–§4.14). The spec left open which of the two ladder markers M1 emits (the `SURF_LADDER` face flag or the 16 u LADDER volume, D-019, D-021) the movement reads, where the water samples sit, how a swimmer moves vertically and what happens with no input. M2 plan, "Spec decisions" (Q2, Q4) and "New tunables"; M2 design §3–§4.
**Decision:**
- **Ladders read only the face flag (Q2).** Contact is a horizontal sweep of the tick's hull, `pm_ladderReach` (2 u) along the yaw-only forward (pitch ignored), that hits a `SURF_LADDER` plane with dot(forward, −n) > `pm_ladderFacing` (0.5). Contact is refused while the velocity leaves the face faster than `LADDER_DETACH_SPEED` = 16 u/s (v·n, a design constant), so a jump-off does not re-attach, and on the ground unless forward is held.
- **Ladder move:** ground-term friction on the 3D speed (no water term, even in water) and `pm_accelerate` toward a wish of the forward axis on world z and the right axis along the face (the view right projected onto the face plane), at `pm_runSpeed` × `pm_ladderScale` (160 u/s), with no gravity and a slide move. A fresh jump press adds n × `pm_ladderJumpPush` (150 u/s), detaches at once and emits `jump`. At the top the probe misses once the hull clears the face, and an air move carries the player over the edge.
- **Greybox:** `ladder()` drops the 16 u LADDER volume and gives the flagged face the material `grey/ladder` (a rung texture for M2's renderer). `compiler.version` becomes 2 and all five maps are recompiled: every file carries the version, and the ladders of movement_lab and fall_tower lose their volumes. `CONTENTS_LADDER` stays reserved: `volume("LADDER")` still builds one, and movement ignores it.
- **Water samples (Q4):** `pointContents` at feet + 1, feet + 28 (the middle of the standing hull) and the eye, feet + 50 standing or feet + 36 crouched, the feet being the hull bottom; cumulative levels 1–3; `PMF_IN_WATER` at level ≥ 1. Design constants, not ESTIMATEs.
- **Swim move** at level ≥ 2: the water friction term on the 3D speed; forward and right along the 3D view vectors plus a vertical axis on world z, jump +127 and crouch −127 added to the cmd's up axis and clamped; command scale without the crouch factor, times `pm_swimScale`, and the summed wish capped at that speed (world z and a pitched forward are not orthogonal, so forward + jump looking up would otherwise reach √2 × 160); with no forward, right or vertical input the wish is straight down at `pm_waterSinkSpeed` (60 u/s); `pm_waterAccelerate`; no gravity; a step-slide, so a swimmer steps out over an edge up to `pm_stepSize` above its feet. The step is refused while rising with no ground below (`docs/03` §4.9), so it comes at the top of the bob, feet about 24.5 u under the surface: a bobbing swimmer leaves only onto an edge about 6 u or more below the surface, and one coming up from depth at full speed reaches about 7 u above it. movement_lab's pool is left through its waist and wading sections (MV-17). No water-jump (M4), so until then an edge flush with the surface traps a bobbing swimmer; maps need a shallow exit or a low rim (`docs/07` §6).
- **Friction in water (clarifies `docs/03` §4.2):** the walk move adds the water term to its ground term with the same horizontal speed, so wading keeps the run, walk and crouch caps; the swim and ladder moves measure the 3D speed.
- **Crouch:** holding crouch sets `PMF_CROUCHED` and the crouched hull at once; on release a position test of the standing hull at the tick's start origin decides whether the player stands. No stamina cost until M4.
- **Pre-check order:** crouch, then water level, then ladder contact (`docs/03` §3 listed water first). The eye sample depends on the stance, and the ladder probe on the hull.

**Consequences:**
- `docs/03` §3, §4.2, §4.12–§4.14 state the rules; `docs/07` §3 the builder change and §4 that `mapc` must compile `tool/ladder` and `func_ladder` to flagged faces (M5).
- Code: `packages/shared/src/sim/pmove/{crouch,water,ladder}.ts`, dispatch in `pmove.ts` (ladder → swim → walk → air). Tests: shared unit tests (stand blocked, water levels, ladder facing threshold, detach, push-off), MV-03 (crouch cap and tunnel), MV-08, MV-17 and MV-18 on movement_lab, and a native-ESM `pmoveModes` allocation workload.
- `pnpm feel-report` (`packages/tools/src/reports/feelReport.ts`) prints the base metrics and writes `reports/feel.md`, git-ignored and byte-identical on every run.
- The pmove bench mix adds crouch and meets the pool and ladder anchors; its warm-up grows to 12500 ticks plus a scripted ladder climb per round, so the rarely run modes are optimized before the timed loop (0 GCs). The pre-checks cost about 0.7–0.9 µs per player-tick (`docs/10` §4.4), within the budget.
- The feel report also shows the D-017 snap bias: at the run cap the origin moves 320.625 u/s for a velocity of 320 (each 5.333 u step rounds to 171/32 u), so the runway takes 6.390 s against 6.400 s.
- Open for feel tuning, to decide with the user:
  - the ESTIMATEs above;
  - a jump at a ladder's foot with forward held pushes off the ladder rather than jumping (ladder dispatch comes first);
  - a standing jump at a ladder's foot with no move input, facing the face, is caught by the ladder on the next tick (the forward rule applies on the ground only, and a vertical jump has v·n = 0) and the player then hangs about 35 u up until back or jump is pressed (candidate rule: while rising from a ground jump, attach only with forward held; falling catches stay as they are; `ladder.test.ts` pins today's behavior);
  - a flush pool rim traps a bobbing swimmer until the M4 water-jump (see the swim move above); bring the water-jump forward or relax the rising-step refusal in the swim move if M5 maps need flush rims;
  - a ladder cannot be mounted from its top: walking back off the edge leaves the face faster than `LADDER_DETACH_SPEED`, so the player falls (options: refuse contact only for a while after a jump-off, skip the speed test while back is held, or skip it above the face's top edge);
  - crouching in the air cuts the air wish speed to `pm_runSpeed` × `pm_duckScale` (`docs/03` §4.1, §4.5 as written), which weakens air strafing on a crouch-jump and on every M4 power-slide approach; the Q3 lineage applies the crouch factor on the ground only.

### D-026 — Protocol v1 and transports (2026-10-06, accepted)
**Context:** M2 sends everything through a server, even offline (`docs/05` §2), so it needs a wire format before the match loop and the predictor (M2 increments 7–10). `docs/05` §3 named the messages and the INPUT and snapshot fields but not their bit widths, the message ids, how decoders fail (§3.2 said "throw → drop"), or what M2's snapshots hold. M2 plan, "Spec decisions"; M2 design §2 "Messages", §3. This entry covers the codec part (increment 7) and the transport part (increment 8).
**Decision (codecs):**
- **Bitstream:** `BitWriter`/`BitReader` over a preallocated `Uint8Array`, LSB-first, explicit widths 1–32, two's-complement signed values, f64 as raw bits. Neither throws: an overflow, a value its width can't carry or a short read sets a sticky error flag (this replaces "throw → drop" in `docs/05` §3.2; a throw would have to be caught on every packet, and a sticky flag needs one check per message).
- **Protocol v1** (`PROTOCOL_VERSION` = 1): one message per packet, a leading `u8` type (1 HELLO … 11 KICK; 0 is never a message), the layouts of `docs/05` §3.6. READY, PRINT and KICK are added to §3.3's list; LOADOUT, TEAM, CHAT, MAP and EVENTS stay for later milestones. Unreliable packets ≤ 1200 B, reliable messages ≤ 16384 B.
- **INPUT** carries 1–4 cmds newest first: the newest tick in full, older ones as a u8 offset back (strictly rising, never below tick 0). 55 B for four cmds.
- **SNAPSHOT in M2** is the `docs/05` §4.2 header plus a flags byte (starved, teleport) and the full local `PlayerState` (199 bits: origin 3 × i21 at 1/32 u, velocity 3 × i20 at 1/16 u/s, yaw and pitch u16, flags 10, groundEntity + 1 in 16, waterLevel 2, stamina 16), 42 B. `baselineTick` is always 0: delta snapshots are M3. The origin needs i21, not i20: ±16384 u is ±2^19 units, one more than i20 holds.
- **Validation:** decoders return false on a short read, a wrong type, a value the encoder never writes (origin past ±16384 u, velocity −2^19, pitch past ±16201, groundEntity past `ENTITY_WORLD`, ticks past `TICK_MAX`, an INPUT count outside 1–4 or cmds outside `sanitizeUserCmd`'s ranges, unknown snapshot flags, a non-zero baseline, PRINT level 3) or bits left after the message's last byte. The receiver drops the packet and counts a strike. The checks make the encoding canonical: a decoder that accepts a packet re-encodes it to the same bytes, and a decoded state is one `quantizePlayerState` leaves unchanged. Encoders refuse out-of-range fields with the same flag, so a sender bug never reaches the wire.
- **HELLO's first 3 B are frozen:** the type byte and protocolVersion u16 keep their place in every protocol version. The server reads a client's version with `peekHelloVersion` before it parses anything else, so it can answer a mismatch with a KICK that says why, whatever fields a newer HELLO adds. `decodeHello` parses the v1 layout and keeps any version.
- **Text:** short ASCII (u6 length, 7-bit printable) for the build hash, map name and cvar names; console text (u10 length, 8-bit Latin-1, printable plus tab and newline) for CMD, PRINT and KICK.
- INPUT, SNAPSHOT, PING and PONG encode and decode without allocating, refused packets included; text and cvar-block fields allocate (rare reliable messages). Decoders read every tick as two u16 halves and reject it past `TICK_MAX` before using it: a hostile u32 past 2^30 − 1 is not a small integer, and returning it from a reader call or storing it allocated a heap number on every such packet.

**Consequences:**
- Code: `packages/shared/src/net/{bitstream,protocol,messages,playerStateCodec}.ts`. `docs/05` §3.2–§3.4 and §4.1–§4.2 point at the new §3.6 layout table; `docs/06` §3 lists the files. A doc-golden test (`packages/tools/test/docs/protocol-docs.test.ts`) pins §3.6's type ids, state widths, sizes and the cvar hash seed to the code.
- Tests: bitstream widths, offsets, signed edges, overflow and short reads (`packages/shared/test/net/bitstream.test.ts`); NET-01 (`packages/shared/test/net/codecs.test.ts`): seeded round trips of every message, encoder and decoder rejections, every truncation, an extra byte and dirty padding refused, and fuzzing (1e4 random byte strings, every single-bit flip of messages up to 96 B and a seeded sample of about 768 bit flips of each longer one, random byte corruption) that never throws and only accepts packets its encoder takes back and re-encodes to themselves; per-message patched-field cases pin each decoder range check the fuzz can't reach. NET-01 is a shared unit test; its file is not named `net-01-*` because the naming guard then requires `pnpm test:net`, a stub until M2 increment 10, but its describe starts with `NET-01:` so `test:net` (`-t "^NET-"`) will select it.
- The native-ESM `codec` allocation workload (valid messages plus a hostile packet per message: random bytes behind an INPUT, SNAPSHOT or PONG type, and valid ones with a tick of 2^32 − 1) and `pnpm bench`'s codec part (`docs/10` §4.4): a snapshot round trip takes about 0.7 µs against the 30 µs budget, a four-cmd INPUT about 1.3 µs, 0 GCs.

**Decision (transports, increment 8):**
- **Interface** (`docs/05` §3.1): `sendUnreliable(d, len)` and `sendReliable(d, len)` take a `Uint8Array` plus its used length, so a sender encodes into one reused buffer; the transport copies what it keeps. `poll()` delivers queued messages to the `onMessage(d, len, reliable)` callback at fixed points of the caller's loop, never from inside a send, and `d` is valid only during the callback. This replaces the `ArrayBuffer` form, which would need a fresh buffer per packet. Unreliable packets are at most 1200 B and reliable ones 16384 B; an empty, oversized or out-of-buffer send is a sender bug, asserted in dev builds and dropped.
- **Reliable is ordered and lossless** on every transport (NetSim included); unreliable may lose, duplicate or reorder.
- **Close and `onClose`**, an addition to the M2 design's interface: after `close(reason)` that side drops its sends and delivers nothing more, while the other side still receives what was sent before and then gets `onClose(reason)` from its `poll()`, like a socket's graceful close. The server can send KICK and close at once, and a client learns that the Worker ended the session. `isOpen()` reports the state.
- **`TransportStats`** is one live object per transport: packets and bytes sent by its user and delivered to its callback, plus NetSim's lost, duplicated and reordered counts.
- **`createLoopbackPair()`**: two in-memory ends; a send copies into a pooled slot of the peer's inbox, and the peer's `poll()` drains the messages queued when it started, both channels interleaved in send order as on one socket. Slots start large enough for any unreliable packet and the pool doubles only when more packets are in flight than ever before, so steady traffic allocates nothing (a reliable message past 1200 B grows its slot once). `PortTransport` (increment 10, wired in increment 11) allocates one transferred `ArrayBuffer` per packet and the receiver's view of it, only at the `postMessage` boundary; its inbox is a ring of reused slots.
- **Bounded receive queues** (M2 review): every receiver (the loopback inbox, `PortTransport`'s ring, NetSim's inbound queue) holds at most `MAX_QUEUED_UNRELIABLE` = 2 × `PLAYER_STATE_RING_CAPACITY` = 256 unreliable packets and drops the oldest past it, counted in `TransportStats.lost`; reliable messages and the close are never dropped. Without it a hidden tab, whose page stops polling while the Worker keeps sending a snapshot every tick, grew the pools by doubling for the rest of the session (about 10 MB after 2 minutes, 78 MB after 10). Keeping the newest packets is what the predictor wants: an older backlog only ends in a hard resync from the newest (`docs/05` §8). The pools stay grow-only; bounded, they need no shrinking.

**Consequences (transports):**
- Code: `packages/shared/src/net/{transport,packetQueue}.ts`; `docs/05` §2 and §3.1, `docs/06` §3–§4 and the `docs/09` M2 scope name `createLoopbackPair` and `PortTransport` instead of a postMessage `LoopbackTransport`.
- Tests: `packages/shared/test/net/transport.test.ts` (send-order delivery on poll only, copy on send, counters, messages sent from a callback wait for the next poll, refused lengths (including fractional and NaN), a poll from inside a callback, pooling: no new slot or delivered buffer after warm-up, and close: drain then `onClose`, drops both ways, close from a callback, and the receive cap: an unpolled end keeps the newest 256 unreliable packets and every reliable one), the same cap in `PortTransport` and NetSim (`portTransport.test.ts`, `netsim.test.ts`) and a 30 s hidden tab in `client-paths.test.ts` (bounded queues, one hard resync); the native-ESM `transport` workload (a raw pair and a NetSim-wrapped pair on `bad-250-loss5`) runs with 0 GCs.

### D-027 — Replicated cvars (2026-10-06, accepted)
**Context:** prediction must use the server's tunables (`docs/05` §3.5), and a live `set pm_gravity 400` must not rubber-band. §3.5 said the cvars are sent "versioned by a hash" but not how they are encoded, which hash, or what a client does with a block. M2 plan, "Spec decisions"; M2 design §2 "Replicated cvar block", §3. This entry covers the block encoding and hash (increment 7), the server's match loop (increment 9) and the client's tick-switched parameters (increment 10).
**Decision (block and hash):**
- **Encoding:** every `REPLICATED` cvar in ascending lowercase-name order (the `CvarRegistry.replicated()` order), no duplicates: count u10, then per entry the name (u6 length + 7-bit ASCII), the kind (u2: int, float, bool, string) and the value: i32; the f64's raw bits, so a float arrives as the same double (finite, never −0, as the registry normalizes it); 1 bit; or a u8 length + 7-bit printable ASCII. The decoder requires that canonical form, so a block's bytes identify its values.
- **Hash:** `murmur3Bytes` over the block encoded alone from bit 0, zero-padded to a byte, seed `0x63766172` ("cvar"). It does not depend on registration order or on non-replicated cvars. CVARS carries all 32 bits (the decoder rejects a block whose hash differs), snapshots the low 16. The M2 movement defaults hash to `0x11df56b6` (a golden test; adding or changing a replicated cvar changes it).
- **Wire limits at the registry:** a `REPLICATED` cvar's name is at most 63 chars and a `REPLICATED` string's value printable 7-bit ASCII of at most 255 chars. Registration throws otherwise, and `set`/`setFromString` refuse such a value with a `type` error, so the block is always encodable: a console value can't stop WELCOME and CVARS or put the −1 "unencodable" result into snapshots (`cvarHash16` asserts on it).
- **Apply is all or nothing:** the block must list exactly the client registry's `REPLICATED` cvars, spelled as registered, with the same types and values within their min/max; unknown, non-replicated or missing cvars, wrong kinds and out-of-range values reject it unchanged. A client with another cvar set is another build, and a clamped value would mispredict.
- **The server's CHEAT and LATCH rules are the only ones:** it applied them before its values changed, so the mirror stores CHEAT and LATCH values as sent (`CvarRegistry.setReplicated`, which also drops a pending latched value), whatever the client's own cheat setting. A client-local gate would make it refuse every later block and predict with stale values. A latched server value changes when the server applies it (map restart) and reaches clients in the CVARS that follows, like any other change.

**Consequences:**
- Code: `packages/shared/src/net/cvarBlock.ts` (`captureCvarBlock`, `encodeCvarBlock`, `decodeCvarBlock`, `cvarBlockHash`, `registryCvarHash`, `cvarHash16`, `applyCvarBlock`); WELCOME and CVARS carry the block (`docs/05` §3.5–§3.6). `docs/06` §3 moves the block from `cvars/` to `net/`.
- Tests (`packages/shared/test/net/cvarBlock.test.ts`): a golden byte layout and hash for a four-kind registry (checked against an independent reference encoder when written), the golden hash of the M2 movement defaults, order independence over shuffled registrations, exact floats (0.1 + 0.2, the smallest denormal, −MAX_VALUE), seeded random round trips, canonical-form rejections, every apply rejection leaving the registry's version and hash unchanged, CHEAT and LATCH values taken from the server with the mirror's cheats off, and the registry's wire limits on names and replicated strings (`packages/shared/test/cvars.test.ts`).

**Decision (server match loop, increment 9):**
- **Environment-agnostic match code** (`packages/server/src/match/`, exported alone as `@game/server`): no clock, timer, console or I/O of its own. A `LoopHost { now(), schedule(cb, ms), log(level, msg) }` brings them (`performance.now` and `setTimeout` in the Worker, a Node host in M3), and the transports bring the clients. `tsconfig.match.json` (ES2023, `types: []`) and a purity guard (no `Date`, `performance`, `Math.random`, timers, `process`, imports beyond `@game/shared` and its own modules) keep it runnable in both. This replaces `docs/05` §8.1's `process.hrtime.bigint()`, which only Node has.
- **Loop:** re-armed through `schedule` after every wake, never an interval. A wake runs the ticks due since the loop started (tick k is due at start + k × 1000 / 60 ms; minus the ticks already run or dropped), not a sum of wake intervals, so rounding never drifts. The count of due ticks and the re-arm delay come from that one expression: a floor of elapsed × 60 / 1000 alone comes out one short at some ticks, so a host that wakes exactly when asked (a simulated clock) would find nothing due and re-arm with 0 ms forever. At most 5 per wake; more due are dropped with one warning, leaving less than a tick owed. An early wake runs nothing and re-arms. A restart while a wake is pending keeps one wake chain. A host whose timer truncates to whole milliseconds rounds the delay up.
- **A late wake yields first (2026-10-08, after M3 increment 4):** a wake that finds two or more ticks due runs none of them yet: it re-arms at 0 ms (`LoopStats.yields` counts it) and the next wake, which never yields, runs what is due by then. **Why:** the browser e2e failed now and then with "starved cmds, no long frame" (2 runs of 9 after increment 4, on a busy 4-core host). Probes on the Node server (tick and arrival times, both sides on one clock) showed the server process stalled 37–117 ms while the client's frames stayed at 16–34 ms; at the end of the stall the loop ran its catch-up ticks (5 in one wake) before Node read the cmds the client had sent during the stall, so the ticks past the input buffer repeated cmds that were waiting in the socket (2 starved; the failing e2e run had 2 starved and 2 starved corrections with no frame over 32 ms). Node 22 keeps that order when JS was blocked (a GC, a long I/O or signal callback, a stall inside the wake) or the process was SIGSTOPped: the overdue timer runs before the `data` events of the bytes that arrived meanwhile (a toy server, 6 stalls of 100 ms per kind, a client sending every 16 ms: 33–36 cmds read after the catch-up wake for each of those kinds, 0 with the yield); a 0 ms timer (`setTimeout`, 1 ms in Node) or `setImmediate` set from that timer runs after them. A process descheduled by the OS while idle in `epoll_wait` (a SCHED_FIFO hog pinned to its core) reads its I/O first anyway (0 either way): the yield costs it only the delay. **The Worker case is open:** the smoke e2e's "starved cmds, no long frame" (Worker server over `MessageChannel`s, `movement_lab`, 3 starved, no frame over 18 ms) is not explained by either cause here. A Chromium Worker already runs the messages queued during a busy task before an overdue timer, so this reorder does not happen there, and the browser's network process (the D-028 link gaps) is not on that path; it was not reproduced in about 40 runs, and the D-028 clock (its low edge or adaptive lead) and the increment-4 `SnapshotStore` drops are not ruled out for it. The Worker cases keep the strict rule and the page reports `lastStarve` (the lead, the low edge and mean, the frame and snapshot gaps, the round trip at the last starve), so the next failure says which. A Chromium Worker already runs the messages queued during a busy task before an overdue timer, and its 0 ms timer (clamped to 4 ms) after them. The cost is that delay on a wake already a tick late. Not a regression of increment 4: the loop and both hosts are unchanged since M2/M3 increment 1, and the e2e at increment 3 and 4 passed alike in 6 runs each with one core busy (the failure needs a server-side stall the client does not share). A browser that throttles a hidden page's timers to about 1 s makes every wake yield, so the catch-up runs one throttle period later (offline play only, where most of those ticks are dropped anyway); skipping the yield past the catch-up cap would starve a 100 ms stall again, so it stays. **Tests:** `loop.test.ts` (a late wake yields once and its ticks see what the host delivered between the two wakes; a wake under a tick late runs its tick at once; the stall, step-back, restart, stop and busy-time cases take the yield); the NET harness's `stallServer(ms)` holds the clients' input from a stalled match until after the wake due at the stall's end (Node's order), and `client-session.test.ts` (`NET-04: a server stall's catch-up ticks`, in `pnpm test:net`) stalls the server 50, 70, 85 and 100 ms under a 60 fps client on `lan`: no starved tick, correction or resync (13 starved ticks, each corrected, without the yield). That harness encodes Node's order, so `packages/tools/long/server-stall.long.ts` (`pnpm test:long`) holds the real Node server to it: the server from source as a child process, a `ClientSim` on Node's WebSocket at about 60 fps, 8 stalls of 90 ms (a busy-wait in a signal callback, from a test-only preload, and a SIGSTOP, in turn): no starved cmd in the windows with on-time client frames and a yield per stall (`loopYields` in `GET /metrics`); without the yield, 15 starved cmds over the 8 windows.
- **Tick order** (`docs/05` §8.1): poll every transport in client-id order and handle HELLO, READY, INPUT, PING and CMD; if the registry's `version` moved, refresh the pmove parameters and, when the replicated block's hash changed, broadcast CVARS with `effectiveTick` = this tick; per active client in id order take its cmd for the tick or repeat its last with attack cleared and the tick set (starved), sanitize, pmove; then per active client a SNAPSHOT with `lastProcessedCmdTick` = the tick, `inputBufferHealth` = newest received − the tick (clamped to i8), the low 16 bits of the block hash and the starved or teleport flag. Each message must arrive on its own channel (INPUT and PING unreliable, the rest reliable); a packet that doesn't decode, comes on the other channel or doesn't fit the session's state (a second HELLO or READY, a server-to-client type) is dropped with a strike. M2 only counts strikes; when they lead to a kick is left to M3.
- **Input queue:** 64 slots indexed `tick & 63`, each remembering its tick; duplicates, cmds for ticks already simulated and cmds 64 or more ticks past the next one are dropped and counted. A slot keeps its tick after its cmd is simulated, so the redundant copies that arrive afterwards count as duplicates and `late` counts only cmds for ticks simulated without them (starved), the case that costs the client a correction.
- **Input buffer health** is the newest cmd tick received, accepted or not, minus the tick simulated: a client whose cmds all arrive two ticks late reads −2, not a value sinking to −128. A received tick counts at most the horizon past the next tick, so a hostile tick cannot pin it. At READY it starts at the spawn tick (the neutral spawn cmd stands for the client's last cmd), so the spawn snapshot reads 0 and each tick before the first cmd arrives one less, whatever the absolute tick; `docs/05` §8.2. The horizon and the catch-up cap are design constants, as is `MATCH_MAX_CLIENTS` = 64 (client ids 0–63, lowest free first; WELCOME's u8 holds them).
- **Handshake:** another protocol version (read from HELLO's frozen first 3 B) or another build hash gets a KICK saying why, then the transport closes. WELCOME and PONG carry the newest tick simulated. READY spawns at once (no spectator step in M2) at the map's first `info_player_start`: at rest, the entity's yaw through `degreesToU16`, pitch 0, stamina 100 points (`staminaMax` at health 100, no vest; docs/03 §5.2, FACT), grounded when the ground trace finds walkable ground.
- **The spawn rests at floor + ε:** the entity's origin raised by `TRACE_EPSILON` to the D-017 rest height (floor + 1/32 u). With its feet exactly on the floor a fresh spawn met a steep wedge's toe as a wall, while any player that has landed is clipped onto it (D-023, "Steep toes", found in increment 4); raising it makes a spawn behave like every later moment of play. Map entities keep their feet-on-floor origins (`docs/07` §3).
- **The spawn state is the player's state at the tick that handled READY**, sent in that tick's snapshot with the teleport flag; simulation starts the next tick. The repeat for a starved tick starts as a neutral cmd with the spawn yaw, the same cmd the client predicts with until its own cmds arrive (M2 design §2, "Client clock"), so startup needs no correction.
- **Known limit, for M3:** the teleport flag rides only the spawn tick's snapshot, on the unreliable channel. M2 is unaffected (its only teleport is the first spawn, and the client adopts its first snapshot whole), but respawns and teleporters must not depend on one datagram: M3 keeps the flag set until INPUT's `lastSnapshotTick` acknowledges the spawn tick, or makes it a counter. M3 also adds the 5 s no-packet timeout (`docs/05` §2) with the Node transports; M2's match closes a session only on a kick or a transport close.
- **Replicated cvars from a console:** a client's `set`, `reset` or `toggle` on a `REPLICATED` cvar becomes a CMD (the client side lands with the console, increment 12). The server applies it to its registry with its own CHEAT and LATCH rules, replies with PRINT, and the next step broadcasts CVARS. Changing cvars needs the session's admin flag; the Worker's single client has it, and M3 decides authorization on the Node server. Non-admins get a PRINT error and nothing changes. `CMD cvars`, open to all, resends the current block with the tick it took effect. WELCOME and resends carry the block captured at the last change, not the registry's live values, so a value changed earlier in the same poll reaches clients only with its effective tick.

**Decision (client, increment 10):**

### D-028 — M2 clock and the net simulator (2026-10-06, accepted)
**Context:** NET-03/04 and the manual `net_profile wan-150-loss2` check need impaired links that are reproducible. `docs/05` §13 and `docs/10` §3 both listed the profiles but disagreed (§13 had no reorder for `wan-150-loss2`, §10 had 0.5%), and neither said how delay, jitter, loss, duplication and reordering combine, so jitter could reorder packets on its own. M2 plan, "Spec decisions"; M2 design §2 "Transport", §3. This entry covers the simulator (increment 8) and the client clock (increment 10: prediction in server-tick time, handshake lead, step re-anchoring; extended at the M2 close-out, 2026-10-07, with the adaptive input buffer).
**Decision (net simulator):**
- **Profiles:** `docs/10` §3 is the canonical table and `docs/05` §13 repeats it with Dup and Reorder columns (`wan-150-loss2` reorders 0.5%). `NET_PROFILES` and `findNetProfile` (`shared/src/net/profiles.ts`) implement it, frozen. Profiles are test conditions, not tunables, so they are not cvars.
- **`NetSimTransport(inner, profile, clock, seed, wake?)`** wraps the client's end and delays both directions by the one-way delay, so the round trip is twice it. Time is milliseconds from the injected monotonic `clock`; the draws come from Mulberry32 seeded with `seed`, a fixed count per packet (five per unreliable, one per reliable), so one seed and one send/poll schedule give one delivery schedule.
- **Unreliable packets:** independent draws for loss, reorder and duplication. Jitter is uniform within ±jitter. A kept packet is due at max(previous due, now + max(0, delay ± jitter)) in its direction, so jitter alone never reorders. A reordered packet is held a further 2 × jitter + one tick (16.7 ms; a design constant) past that and does not move the FIFO due, so the packets behind it overtake it. A duplicate draws its own jitter and follows its original through the FIFO rule.
- **Reliable packets** use the same delay and jitter, in order, never lost or duplicated. A close in either direction is queued like a reliable packet, behind everything sent before it (a reordered unreliable packet still held then is lost).
- **Pumping:** a send and `poll()` forward every due outbound packet to the inner transport (`pump()` does it alone); `wake(at)` reports each new earliest outbound due time once, so a browser host can arm a timer to pump between frames; `pump()` re-reports a front still pending, so a timer that fires early (`setTimeout` truncates a fractional delay) re-arms instead of stranding the packet. `poll()` takes the inner transport's arrivals, stamps them with the current time and delivers the due ones. `lan` therefore behaves like the bare transport.
- **`setProfile`** (the `net_profile` command) applies to packets sent or arriving afterwards; packets in flight keep their due times and new ones still queue behind them. Out-of-range values (negative or non-finite times, probabilities outside 0..1) are refused, asserted in dev builds.
- **Close is graceful**, so NetSim keeps the `docs/05` §3.1 close contract under every profile: after `close()` the simulator drops later sends and the arrivals it holds, still forwards the outbound packets it holds when due (through `pump()`, `poll()` or a wake), and closes the inner transport when its close comes due. A bandwidth cap (`docs/05` §3.1) is not simulated in M2.
- **Allocation:** in-flight packets are pooled copies (`PacketQueue`), and due times and draws stay in typed arrays (`Mulberry32.fillFloats`), so no fractional double crosses a call boundary per packet: 0 GCs under native ES modules. The host's `clock` and `wake` callbacks are the exception they cannot avoid (a fractional `performance.now()` is boxed when returned); the tests use a fake clock.

**Consequences (net simulator):**
- Code: `packages/shared/src/net/{netsim,profiles}.ts`, `Mulberry32.fillFloats`; `docs/05` §3.1 and §13, `docs/06` §3, `docs/10` §3.
- Tests (`packages/shared/test/net/netsim.test.ts`, fake clock): `lan` passes through in the same step; delay within ±jitter, with the jitter range used, on `wan-50`, `wan-100-loss1` and `wan-150-loss2` in both directions; FIFO order under ±40 ms jitter at 1000 packets/s without reorder; loss, duplication and reorder counts within 5σ of the binomial over 20,000 packets on `bad-250-loss5`, with each id delivered once or twice and overtaken packets bounded by the reorder count; the exact reorder hold; reliable packets all delivered in order both ways; identical schedules for a seed and different ones for another; `setProfile` mid-run; out-of-range profiles refused (and a refused first profile leaves it on `lan`, reported as such, when asserts are off); counters for sent and delivered packets and bytes; duplicates drawing their own jitter; the reorder hold with jitter past the delay; pumping only on wakes delivers on time, one wake per new front, and an early pump re-arms; a graceful close on `lan`, `wan-50` and `bad-250-loss5` (reliable messages sent before it arrive, then the close) and a drain driven by wakes alone, the peer's close delayed behind its reliable messages, and a close in either direction delivered behind the unreliable packets sent just before it (jitter without reorder, 49 seeds); arrivals past the receive cap (D-026) drop the oldest. The native-ESM `transport` workload includes a wake callback and pumps between polls. `packages/tools/test/docs/net-profiles-docs.test.ts` pins `NET_PROFILES` to the `docs/10` §3 and `docs/05` §13 tables.

**Decision (client clock, increment 10):**
- **Prediction runs in server-tick space:** the client's tick T is the server's tick T, run ahead of the server by the round trip plus an input buffer, so the cmd for T reaches the server just before it simulates T. There is no separate client clock to convert.
- **Handshake:** from WELCOME the client pings every 50 ms (a lost ping is replaced, not waited for) until 5 pongs are back; their median is the RTT and only then is READY sent. At the first snapshot A (the spawn, adopted whole) the client jumps to tick A + ceil(RTT / tick) + `cl_inputBuffer` (2), capped at 64 (half the rings). The ticks between are filled with **neutral cmds** (no move, the spawn's angles), predicted and sent at once; the server repeats that same neutral cmd until the client's own arrive (D-027), so the start costs no correction, and starvation before the end of that fill is expected and not counted.
- **Re-anchoring in steps:** a ping a second feeds EWMAs of the RTT and its jitter (weight 1/8) for the netgraph. Each snapshot's `inputBufferHealth` feeds an EWMA (weight 1/30, about 30 snapshots) and the window of the adaptive input buffer (next bullet), which decides the steps: fast-forwards of at most 5 ticks, predicted and sent that frame, and holds of at most 30 tick periods. (Until the close-out the EWMA alone decided them: below target − 1.5 for 0.5 s, k = round(target − EWMA); above target + 3 for 1 s, k = round(EWMA − target).) After a step, snapshots up to the tick the step's effect reaches are ignored and the estimates move by k at once, so one shortfall makes one step. Each step counts as a clock adjustment. The render offset hides a fast-forward's skip; a hold pauses the prediction for k ticks, so the drawn player briefly slows. **Smooth time dilation (±3%, `docs/05` §8.2) is NET-07 in M3.**
- **Adaptive input buffer (M2 close-out; `docs/05` §8.2 "target 1–2 ticks, adaptive to jitter"):** a client frame runs every tick it owes at once, so with long or irregular frames cmds reach the server in bursts and the health saw-tooths. The mean-only clock kept the EWMA in its band while each burst's low point starved the server, and each starved tick of a strafe-jumping player was a correction of up to about 20 u (measured with StrafeCircuit, 60 s, 1.5 s idle, seeds 1–2: 12 Hz frames 5.5–10.4 corrections/s; 50–83 ms frames 0.6–6.8/s, max 23.5 u, the mean only 1.05–1.25; 60 fps with 15% of frames 50–80 ms 2.6–8.1/s on wan-100-loss1 and wan-150-loss2; 33–83 ms frames 0.8–2.5/s; the SwiftShader e2e at 50–83 ms showed 2.8/s, max 17.6 u, at wan-150-loss2). So the clock now steers the **low edge**: the lowest health of the last 90 snapshots (1.5 s, a preallocated ring with a running sum).
  - **Grow fast:** when the low edge is below `cl_inputBuffer` − 1 (a dip to 0 at the default, one tick from starving) and the dips are a pattern (3 separate dips below it in the window, or one lasting 6 snapshots, 100 ms: a round trip that grew), the clock fast-forwards as soon as the dip stops deepening, by k = max(target − low edge, round(target − EWMA)), so the low edge lands on the target with a tick of margin and the clock learns the full depth of the dip at once. A lone dip is left alone: on wan-100-loss1 at 144 Hz two lost INPUTs within 1.5 s are common and never starve, while a step's skip at strafe-jump speed puts a tick of motion (about 11 u) in the render offset; reacting to every dip, or keeping the low edge at target − 1 instead of the target, made the existing 144 Hz NET-04 runs take such steps (offsets of 8.5–12 u).
  - **Shrink slowly:** a hold of k = round(min(low edge, EWMA) − target) once both have stayed at target + 2 or more for 4 s, or for 1 s if they are 4 or more above by then (a round trip that fell, a stall's lead; both timed from when they reached + 2). A small excess is often only a window that missed the longest frames; with a 1 s wait the clock gave back 2 ticks and needed them again 40 s later (a fast-forward at speed). Since the low edge itself waits out the window, nothing shrinks for at least 2.5 s after the spread went away. The EWMA counts rounded here: it approaches a health from below and stalls a few ulps short of it, so compared exactly a health that settled at target + 2 from below (frames steady again after a fast-forward) never held, keeping 2 extra ticks for good (wan-50 at 144 Hz after 2 s of 20 fps: lead 6, was 4). The low edge, an integer, is what makes a hold safe.
  - **`cl_inputBuffer` (ESTIMATE, 2)** keeps its name and default and is now the buffer the clock keeps at the health's low point, and the handshake lead's buffer. With steady frames on a clean link the health is constant, so the mean equals it as before (lan and wan-50 at 144 Hz: mean 2.00–3.00, 0 steps, 0 corrections, 0 starved, unchanged); bursts and jitter add their spread to the mean. The clock keeps the low edge at `cl_inputBuffer` − 1 or more, lifting it to `cl_inputBuffer`. The e2e's long-frame rule (frames longer than `cl_inputBuffer` ticks) stays: it is the lead's slack with steady frames, which the e2e host has at 57–60 fps.
  - **Cap:** fast-forwards never take the window's average past target + 8 ticks (133 ms: the burst of a 100 ms frame, 6 ticks, plus wan-150-loss2's ±1 tick of jitter), and once the average is 2 or more past it the clock holds back to it; the average, not the EWMA, because the EWMA lags a big saw-tooth by several ticks (with 30-tick bursts the lagging check let the clock grow 11 ticks). The snapshots skipped after each step still bias the average by about a tick, so the mean settles within two ticks of the cap and the clock then starves instead of growing. A health at the i8 floor (−128) never asks for a fast-forward: it counts as still deepening, since its depth is unknown and no step helps while the cmds are not arriving. Without that, an uplink outage past about 2.1 s fast-forwarded 5 ticks every 0.5 s through the cap (wan-50, 4 s outage: lead 4 → 29 ticks, the mean 24 ticks above the target for 2.5 s after it).
  - **Stalls:** a frame more than 100 ms after the last (`HITCH_FRAME_MS`; frames past the 83 ms per-frame tick cap cannot be sustained anyway) keeps the snapshots of the ticks it delayed (through the tick its catch-up reaches) from the watch: no allowed buffer would cover a long stall, and growing for a one-off adds latency (the 250 ms and 120 ms hitch cases keep their bounds).
  - **Across anchors:** the spread a full window measured (average − low edge, but no more than average − target, at most 8) is the **adaptive lead** an anchor adds to ceil(RTT / tick) + `cl_inputBuffer`, so a re-anchor does not forget the frame rhythm; reset clears it. The second bound keeps a lone dip (the mean still on the target) and a round trip rounded up (no spread) out of it. On `lan`, where the lead is all buffer, a gap past it resyncs before any snapshot shows the dip, and with the window restarted by every resync the clock otherwise never learns (60 fps with 15% of frames 50–80 ms: a first version of this clock resynced 24 times a minute, and the mean-only clock so often that the 60 s circuit did not get its 60 s of ticks past the last anchor in 120 s). So a hard resync counts as a dip when it came in a frame longer than `cl_inputBuffer` ticks (not a stall frame) and found the server up to 8 ticks past the newest prediction before the poll: a second one within 1.5 s grows the adaptive lead by its depth + target, like a fast-forward (now 1–2 resyncs). A lone one is left alone, like a lone dip: growing for it cost a 7–9 tick lead and a hold glide of 7–10 u about a second later on top of the resync (one 60–90 ms frame on lan). A resync after a short frame is a link outage, not a frame rhythm: growing for it added 5–8 ticks (snapshots lost for 1.1 s: lan lead 2 → 7, wan-150-loss2 7 → 16) until a hold.
  - **After** (same runs, seeds 1–2): 0 corrections on every frame model and WAN profile (bad-250-loss5: 0–2 a minute), 0 hard resyncs on the WAN profiles and 1–2 learning resyncs on lan. In the NET-04 block below (the profile runs' 1.5 s idle first; 18 frame-model runs) every run has 0 corrections and no starved tick once moving (0–26 while the clock learned, standing still), with 1–3 clock steps; in 2 runs the learning fast-forward came at speed, a 19.7–22.4 u forward glide over `cl_correctionSmoothMs`. Over seeds 1–10 (90 runs): at most 1 correction per run (under 0.25 u), no correction offset over 0.05 u, at most 2 starved ticks once moving, and a step while moving in 18 runs (a burst deeper than any before), each a glide of up to 32.8 u. **Frames that turn bad mid-play** (144 Hz, then 60 fps hitches or 33–83 ms frames 15 s into the circuit; seeds 1–4, lan to wan-150-loss2): until the third dip the bursts starve, 0–9 corrections of up to 23 u (the mean-only clock's cost, but once); the learning step comes within 1.4 s of the onset, one fast-forward of 2–5 ticks, a glide of 22–57 u at 765 u/s (on lan also a resync or two); after it, no correction offset and at most one more step. **Latency cost:** the mean buffer health over a run is 3.3–5.7 ticks at 33–83 ms and 50–83 ms frames and 4.0–6.4 with 60 fps hitches (target 2; seeds 1–10), so 1.3–4.4 ticks (22–73 ms) more input delay, only while the frames are irregular; at 144 Hz on wan-100-loss1 and wan-150-loss2 the mean stays 1.7–3.3. At 12 Hz the burst depth wanders by a tick with the frame phase, so learning fast-forwards also come later. The netgraph shows the low edge next to the mean.
- **The client's accumulator** runs at most 5 prediction ticks per frame and carries what a longer frame owes into the next frames. Unlike the server loop, which is the time reference and may drop time, the client's tick follows the server's clock: dropped time would be lead lost, with the server starving until a fast-forward (a 120 ms hitch on `wan-100-loss1` cost 20 corrections that way, 5 with the carry). Only a debt past 64 ticks is dropped; the snapshots then hard-resync. Its fraction is the interpolation weight, held in 0–1 during a hold.
- **Lead cap while snapshots are missing:** the prediction stops 64 ticks past the newest snapshot (the server's input horizon, half the rings), so a server or link stall neither runs it out of the rings nor past the cmds the server can queue; when the server resumes it simulates the cmds the client predicted, and holds bring the lead back.
- **Handshake pings** wait in 64 slots, so the handshake completes at round trips up to 3.2 s (at 16 slots it never finished past 800 ms). A handshake timeout comes with the session timeouts in M3 (`docs/05` §2).
- **Hard resync:** a snapshot for a tick the rings no longer hold (more than 127 behind the newest prediction) or not yet predicted is adopted as the newest tick and the clock re-anchors from it, filling with the last cmd, attack cleared. A backlog of snapshots after a stall is one hard resync: the client re-anchors once, after the poll, from the newest, sending one INPUT per fill tick, and a clock step asked for by an earlier snapshot of that poll is dropped (it measured the old anchor). A fill sends up to 64 INPUT packets in one frame (the spawn's too), so the M3 input rate limit (`docs/05` §12) needs a burst allowance of at least 64 packets, or the fill sends one packet per `INPUT_MAX_CMDS` ticks.
- **e2e link gaps (2026-10-08, after M3 increment 4):** the page also counts `linkGaps`, frames that ended a gap in the snapshot stream longer than `cl_inputBuffer` ticks plus their own frame gap (50 ms at 60 fps; frames on time take snapshots at most two frames apart) by taking a burst of two or more with none lost, and the starved flags and starved corrections taken by such a frame or within the gap's length plus the round trip and twice the input buffer after it (`starvedAfterGap`, `starvedCorrectionsAfterGap`). In the WebSocket cases (`connect.e2e.ts`) the e2e rule excuses those, and only those, in a window with no long frame; the Worker cases (`smoke.e2e.ts`) stay strict. **Why:** with the D-027 loop yield in place the connect e2e still failed once in 8 runs with "starved cmds, no long frame" (3 starved, 3 corrected). Probes showed the Node server ticking and polling its socket throughout, while 8 INPUTs the page sent at 60 fps over 110 ms reached it together 60–120 ms late and the snapshots reached the page 35–50 ms late: the browser's network process stalled both ways on a busy 4-core host (three Chromium instances with SwiftShader and the test runners). The input buffer is the slack for link delays as for frame gaps, so a link stall past it starves by design, as on a real link; frame timing cannot show it, the snapshot stream does. In the instrumented runs every starved tick on `lan` with frames on time had a snapshot gap of 53–97 ms before it (3 cases with the page's probe log; in one of them and in a fourth the server, ticking throughout, had received no input for 75 and 60 ms). **Causal and local:** a first version counted any snapshot gap and excused every starve of the window after one; on `wan-100-loss1` a single lost snapshot (a 33–36 ms gap) triggered it in 5 of 9 windows with frames on time, and on an idle host 7 of 26 windows had one. A link that holds the stream lets it through as a burst; a lost snapshot or a NetSim drop leaves a tick jump, which does not count, and a starve away from a gap (an uplink stall alone, a clock edge) still fails. Neither the burst nor the window tells a server stall from a link stall, so the D-027 yield is guarded by `server-stall.long.ts`, not by the e2e. The Worker path has no network process, so nothing there excuses a starve: its open case (D-027 amendment) stays visible. The failure messages carry the window's link gaps, both readings' snapshot gaps and the peak since the start (`peakSnapGapMs`), the last link gap and `lastStarve`. The rule stays as strict elsewhere: no correction on an on-time snapshot, ever, and hard resyncs only in long frames. **Tests:** `game.test.ts` (a 30 ms snapshot stall is not a link gap and an 80 ms one ended by a burst is, frames on time; an 80 ms run of lost snapshots is not one; both ways held 100 ms starves and every starve is counted after the gap, the uplink alone held 100 ms starves with none counted).
- **Known limits until NET-07 (M3):** below about 12 fps (frames at the 83 ms per-frame tick cap) the client cannot keep up and starves and resyncs whatever the buffer; at 12 Hz the burst depth wanders by a tick with the frame phase, so a learning fast-forward can still come at speed. (Until the adaptive buffer, the step clock watched only the mean, so below about 20 fps each burst's low point starved while the mean stayed in its band: wan-50 at 15 fps, about 10 corrections a second.) On `lan`, where the lead is 3 ticks, a frame gap longer than the lead (about 50 ms) is a hard resync rather than a catch-up, the first time or two: a second such resync within 1.5 s grows the adaptive lead. The ticks it refills were already simulated by the server with its starved repeat, so the outcome is the same, only counted differently. In the browser the Worker answers pings on its tick, so the measured round trip is about a tick and the lead 3–4 ticks, of which only the 2-tick input buffer is slack: gaps from about 40 ms resync there. A gap shorter than the lead but longer than the buffer starves the server without a resync, and the client is corrected on that starved snapshot (counted apart, `STAT_STARVED_CORRECTIONS`). The e2e smoke test therefore judges hard resyncs and starved corrections against frames longer than the input buffer (`docs/10` §2, `pnpm test:browser`). The adaptive buffer (above) addresses both for gaps up to about 100 ms after the first; smooth dilation will hide the steps.
- The thresholds, windows, weights and caps (the 90-snapshot window, the margin of 1, 3 dips or 6 snapshots, the 4 s and 1 s holds at 2 and 4 above, the adaptive cap of 8, the 100 ms stall, a second resync within 1.5 s) are design constants; the target `cl_inputBuffer`, the smoothing time `cl_correctionSmoothMs` and the snap distance `cl_teleportDist` are client `ARCHIVE` cvars (`docs/06` §7), never replicated.
- **Allocation:** the frame, prediction, reconciliation (re-simulation and the correction log, which keeps states and builds its diff only when read) and the render offset allocate nothing; time is read once per frame from the injected clock into a typed array the clock, stats and offset share, so no fractional double crosses a call per frame. The injected clock may box its one double per frame, as NetSim's does.

### D-029 — Node dedicated server (2026-10-07, accepted)
**Context:** M2 left the Node entry a placeholder that logged `server ok` and waited for a signal; the match ran only in the Worker. M3 needs a real dedicated server that browsers and bots reach over the network, with settings, logs and metrics a person and the load tests can read (`docs/06` §8 listed them without a shape). The match code must stay environment-agnostic (D-027). M3 plan, "Spec decisions"; M3 design §1, §2.14 and §3. This entry covers increment 1; metrics lines, GC and metrics files (increment 6), `sv_maxClients` (4), rcon (14) and several matches (17) extend it.
**Decision:**
- **Shape:** the Node code lives in `packages/server/src/node` (process entry, config, host, logs, maps, build hash, console) and `src/transport` (the WebSocket listener and transport, D-030), outside the pure `src/match`. A second package entry, `@game/server/node`, exports `startServer` and the listener so tools tests can start a real server in-process; the match-purity guard allows exactly that second entry. `src/main.ts` and `startup.ts` are gone; `pnpm dev:server` runs `src/node/main.ts` and `pnpm build` bundles it to `dist/main.js`.
- **One match per process** until D-047: `main` on `sv_map` (default `arena_greybox`). `startServer` returns `{matches, listener, stop, …}` with `matches.main`, the shape several matches keep.
- **Config:** `server.cfg` (`set <cvar> <value>` lines tokenized with the console's `tokenizeCommand`; lines starting with `//` or `#` are comments, and a comment after a value is refused rather than read into it), then the command line (`--port`, `--map`, then `--set name=value` in order; `--cfg`, `--maps`). A `set` reaches the SERVER `sv_*` registry or the match's replicated `pm_*` template. An unknown cvar, a bad value, an out-of-range one (which the registry would clamp) or `sv_sendBufferClose` not above `sv_sendBufferDrop` is a ConfigError: the process exits 1 with an `error` line rather than run with a setting nobody wrote.
- **Port 28700** (`sv_port`, design value; 0 picks a free port for tests and bots), bind address `sv_host`.
- **JSON-lines logs** on stdout, `{"t":ISO,"lvl":…,"ev":…}`: `server_ok` with `startupMs` (monotonic, replacing `server ok t=…ms`), then `listening` with the port, build hash and matches, both once the port is bound (M3 design §2.14), so a script waits for one parseable line. Match text lines are wrapped as `ev:"log"` with the match name: the match keeps its environment-agnostic `MatchLog`. A loop drop is reported once as `tick_drop`, naming every match: the loop's own "fell behind" line becomes that line. **Deviation from M3 design §2.14:** its `welcome`, `ready`, `leave` and `kick` (reason, strikes) events stay `log` lines for now; they become their own events with D-041 (increment 13), which adds strikes and timeouts, since that needs a structured `MatchLog` the Worker host also implements.
- **Metrics:** `TickHistogram` (`src/match/tickStats.ts`, pure: 2048 × 10 µs buckets, an overflow bucket and the exact maximum; a 1 s window closed by the host and a run window; nearest-rank p50/p95/p99 as the bucket's upper edge capped at the maximum, so never below the true value and at most 10 µs above). The Node `TimedPass` times each `match.tick()` and the whole pass into whole microseconds with one clock read per match boundary (N + 1 per pass); its own code allocates nothing (the native-ESM `timedPass` workload, on an integer clock), while Node's `performance.now` boxes each double it returns, the host-clock boundary cost the loop already has. It closes the 1 s windows every 60 passes and samples the process CPU time once a second. `GET /metrics` serves `{process, matches:{<name>}}` with tick times, dropped ticks, CPU per wall second, memory (heapUsed, external, RSS) and the match counters; `GET /status` serves `{buildHash, protocol, matches:[{name, map, players, maxClients}]}` from the start (one entry until D-047; `maxClients` is `MATCH_MAX_CLIENTS` until `sv_maxClients`, D-034).
- **Build hash:** one script, `scripts/build-hash.mjs` (`BUILD_HASH`, else the short git hash with `-dirty`, else `dev`). `build.mjs` bakes it into the bundle as `__BUILD_HASH__`; from source the server runs the script. Strict build checking and the client's use of the script are D-031.
- **Admin console** on stdin: lines run as admin on the match (`set`/`reset`/`toggle` on replicated cvars), replies logged as `console`.
- **Graceful shutdown** on SIGINT/SIGTERM, between ticks: stop accepting, KICK "server shutting down" and close 1001 in every match, stop the loop, wait up to 1 s (design value) for the closing handshakes, then terminate the rest, exit 0. The entry module installs the signal handlers before it starts anything, so a signal during startup (config, map, bind) stops the server as soon as it is up; one that arrives while Node is still loading the modules ends the process with the default action, before anything was accepted.
- **Metrics run, GC, traffic and the metrics line (increment 6, with D-036):** `ServerMetrics` (`src/node/metrics.ts`) keeps a **run window**, which starts at listen, again `--metrics-discard <s>` seconds later (a `metrics_reset` line, `reason` `discard`) and on the console's `metrics reset` (a process command, stdin only: it resets the process and every match; rcon's match-scoped reset is D-042's), and an **interval window** since the last metrics line. `/metrics` reports the run window: the pass's and each match's tick histograms (`TickHistogram` gained an interval window beside the 1 s and run ones), GC pauses from a `PerformanceObserver` on GC entries (count, longest, total), memory (the sample when read, and the window's peaks of heapUsed + external and of RSS from samples the server takes once a second on a one-shot unref'd timer between ticks, so a `--metrics-out` written at shutdown still judges what play cost), CPU ms per wall second over the window (the process's CPU time since the window began, not the pass's last second), connections, and the counters as deltas over the window, so passes, dropped ticks, loop yields, starved, strikes, snapshots, full snapshots (`MatchMetrics.fullSnapshots`, new) and kicks now count the window, not the process's life (a change of increment 1's `/metrics`; nothing read the old totals across a reset). `--metrics-discard` takes 0–86400 s (design value), below `setTimeout`'s 2^31 − 1 ms, past which Node would fire the reset after 1 ms. Traffic is counted where it crosses the sockets: each match owns a `WireTraffic` and the listener points the match's `WsTransport`s at it, which add payload plus RFC 6455 framing (`wsWireBytes` in `shared/src/net/protocol.ts`; masked client frames) for every binary message that arrived and every message sent (not those backpressure dropped), so a match's bandwidth needs no per-tick work in the match. Every `sv_metricsInterval` seconds (new SERVER cvar, 10, design; 0 = none) one `metrics` line per match and one for the process report the interval window; the timers are one-shot and unref'd. `--metrics-out <file>` writes the run window as JSON (`/metrics`'s object plus `buildHash`; the folder is created) at shutdown, after the loop stops, with a `metrics_written` line; a failure is logged and shutdown goes on. `metrics.ts` runs a few times a minute or on a request and allocates freely; the per-tick and per-packet parts (the histograms' third window, the traffic counters) stay allocation-free (the `timedPass` and `wsTransport` workloads).

### D-030 — WebSocket transport (2026-10-07, accepted)
**Context:** `docs/05` §3.1 named a `WebSocketTransport` for M3 ("both channels over one socket") but not how the channels share a socket, the limits a server needs against a hostile client, backpressure, or close codes. Node has no WebSocket server. M3 plan, "Spec decisions"; M3 design §2.6 and §3. Increment 1 built the server side; increment 2 added the client's `WebSocketTransport` (the last bullet of the decision).
**Decision:**
- **Dependency:** `ws` 8.x (MIT) on the server only, bundled into `dist/main.js` (a `createRequire` banner gives the CommonJS library its `require`; the optional `bufferutil` and `utf-8-validate` stay external, and ws falls back to JavaScript). `@types/ws` (MIT) for development. Browsers and bots use the native WebSocket. The build writes ws's notice to `third-party-licenses.md` beside the bundle.
- **One socket, both channels, no extra bytes:** a message's channel is its type's (`MSG_CHANNEL` in `shared/src/net/protocol.ts`, the `docs/05` §3.3 table: −1 for a type that is no message). An unknown type arrives as unreliable and the match strikes it. Binary frames only; a text frame closes the socket 1003.
- **Listener:** `http.Server` + `WebSocketServer({noServer: true, maxPayload: 2048, perMessageDeflate: false, clientTracking: false, skipUTF8Validation: true, autoPong: false})` behind one `upgrade` handler: it resolves the path to a match (`/` only until D-047; a query string or any other path is HTTP 404) before `handleUpgrade`, and looks the match up again once the upgrade completes (gone: close 1001). Every upgraded socket gets an `error` listener first, so a frame error never escapes as an uncaught exception. ws refuses `server` together with `noServer`, so no second, unchecked handler can exist. ws sets TCP noDelay. Origin and connection limits join the same handler with D-041.
- **Limits:** the server accepts frames up to `MAX_CLIENT_MESSAGE_BYTES` = 2048 B (the largest client message is a 1026 B CMD); ws closes a larger one 1009. An unreliable message over 1200 B is queued as a zero-length message, which no decoder accepts. Inboxes hold 256 unreliable messages (drop-oldest, counted lost, as D-026) and 64 reliable ones between polls (past that, close 1008).
- **Backpressure:** while more than `sv_sendBufferDrop` (32 KiB, ESTIMATE) waits in the socket, unreliable sends are dropped and counted lost; past `sv_sendBufferClose` (1 MiB, ESTIMATE) the socket closes 1008 "too slow", checked on every send and every poll (each tick), so the limit also holds for a session the match sends nothing yet. Reliable sends never drop. No automatic pongs (`autoPong: false`): the protocol has its own PING/PONG, and answering WebSocket pings would let a client that never reads grow the buffer before it says HELLO.
- **Close:** the match's KICK goes first, then close 1000 (1001 at shutdown) with the reason cut to 123 B (never inside a surrogate pair). A client's close, or one the transport forces, reaches the match from `poll()` behind the messages that came before it (D-026's contract).
- **Allocation (extends D-026):** ws's received Buffers and the one copy per send (a Buffer ws keeps until flushed) are the documented boundary allocation; arrivals are copied into a pooled `PacketQueue` (now exported from `@game/shared`). The match tick and the codecs stay allocation-free; NET-09 measures the GC cost.
- **Scheme:** `ws://` in M3; `wss://` with deployment (M9).
- **Client end (increment 2):** `WebSocketTransport` (`packages/client/src/net/webSocketTransport.ts`) over a structural `SocketLike` (binary type, ready state, send, close and the four handlers; the close event structural too, since Node's types have no CloseEvent), so the client's net code stays DOM-free and the browser's WebSocket, Node's built-in one (bots, tests) and a fake all fit. The channel comes from the type byte as on the server; arrivals go into a pooled `PacketQueue` with the server's caps (256 unreliable drop-oldest, 64 reliable between polls, then close; an unreliable message over 1200 B as the zero-length marker); a message over 16384 B (`MAX_RELIABLE_BYTES`) or a text frame closes the socket. Sends pass a view of the caller's bytes, which the WebSocket API copies before `send` returns (the contract test checks it on Node's); one view is cached per recent buffer and length (four, replaced round-robin), so INPUT, PING and CMD from the connection's one writer each reuse theirs and steady sends allocate nothing in the transport. `receiveBytes` is the arrival past the boundary (the ArrayBuffer's view), so the allocation workload can drive it. Reliable sends made before the socket opens (HELLO, sent as soon as the client starts) are copied and sent on open, in order; unreliable ones are dropped as lost. A page may close only with 1000 or 3000–4999, so every close the client starts is 1000 with its reason cut to 123 B. A peer close maps to the server's reason, or "could not connect to the server" when the socket never opened (a refused connection or upgrade, which reports an error and maybe a close), or "connection lost" for 1006. The design's `bufferedAmount` in `SocketLike` is left out: nothing on the client reads it yet, and client-side send backpressure would need a new ESTIMATE threshold (add it with its first reader). The server's test helper `NodeWsClient` stays in `packages/server/test`: the server package cannot import the client's code (the dependency graph is shared ← server ← client ← tools), so the client transport's real-socket tests live in `packages/tools`.

### D-031 — Connecting to a Node server: one build hash, the server's map, the connect path (2026-10-08, accepted)
**Context:** M2's page had one map (`movement_lab`, imported by name) and one server (the Worker). `vite.config.ts` computed the page's build hash with its own copy of the script's logic, and the match KICKed any other build. With the Node server (D-029, D-030) a browser must reach a server by address, play the map that server runs, and agree with it on the build; a dev page and a dev server started at different times may not. M3 plan, "Spec decisions"; M3 design §1, §2.14, §3 and §6 (increment 2).
**Decision:**
- **One build hash:** the page's `__BUILD_HASH__` comes from `scripts/build-hash.mjs` like the server bundle's and the server's from source; a guard (`packages/tools/test/guards/build-hash.test.ts`) checks the three agree and that neither build file runs git itself.
- **`sv_strictBuild`** (SERVER, int 0–1, default 1, design): at 1 a HELLO with another build hash is KICKed with both hashes (`build <client> does not match the server's <server>`); at 0 the client gets its WELCOME and a `PRINT` warning naming both. The Node server run from source sets it to 0 at startup, before `server.cfg` and the flags (which may set it back): `pnpm dev` and `pnpm dev:server` compute their hashes when each starts, so a commit in between would otherwise lock the dev page out. The bundle keeps 1, and so does the Worker (`MatchOptions.strictBuild`, default true). The protocol version is always strict.
- **The server's map:** the client build ships every `content/maps/*.cmap` as a file (`import.meta.glob` with `?url`, `packages/client/src/app/maps.ts`). `ClientSimOptions.cmap` is optional: without it, WELCOME's map name and content hash go to `onMapRequest`, the page fetches the bundled file and hands it over with `provideMap(cmap)` (synchronous), which refuses another name or hash (ending the session with both versions) and builds the collision world. Node clients provide it from disk, possibly from inside `onMapRequest`: a refusal or `disconnect` there leaves the session closed (WELCOME's handling stops once the session is closed), and a loader that throws ends the session with `could not load map <name>: <error>` instead of escaping the transport's poll. On the page, `loadServerMap` (app/maps.ts) fetches, checks and hands over the file, ending the session with the fetch's reason when it fails. **READY waits for the map and the clock-sync pings** (the pmove primer joins with D-040); a WELCOME for another map than a given `cmap` is still refused at once.
- **Connect path:** `?connect=ws://host[:port][/path]` (or `host[:port]`; without a port, the server's default 28700, not the scheme's 80) opens a `WebSocketTransport` to that server, wrapped in the net simulator at `?net_profile=<name>` (`lan` when absent; an unknown name warns and uses `lan`), which also applies to the Worker. `wss://` is refused until deployment (M9), and so are a query string, a fragment (even an empty `?` or `#`, which `URL` reports as empty but keeps) and credentials, which the server would refuse anyway. The console's `connect` alone says where the session plays (or, once it closed, `not connected (last: …)`); `connect <address>` reloads the page with `?connect=` (a fresh page rebuilds the map, the scene, the prediction and the mirror registry for the new server; nothing tears a session down in place before menus exist), and `disconnect` closes the session with "left the server". When a session on the local server closes, for any reason, the page terminates its Worker: nothing rejoins it short of a reload. The Worker stays the default. The autotest status gains `map` and `netProfile` (the simulated link, kept current after console commands).
- **Deviation from M3 design §3 (D-031 doc updates):** its "docs/07 §6" is the mapping-metrics table; the loading rule went into `docs/07` §2 next to `contentHash`, whose purpose (did client and server load the same map?) it implements.

M3 plan, "Spec decisions"; M3 design §2.1–§2.3 and §3. This entry covers increment 4, the full forms; deltas (increment 8) and the deferred list (increment 10) extend it within the same version, since nothing is released between them.
**Decision:**
- **`PROTOCOL_VERSION` 2.** Only SNAPSHOT changes; every other layout is v1's, HELLO's first 3 B stay frozen, so a v1 client hears why it is KICKed.
- **Header (86 bits with the type byte):** serverTick 32 (1…`TICK_MAX`), `baseBack` 6 (serverTick − the baseline's tick; 0 = full, the only form until D-038), flags 8 (bit 0 starved; bit 2 spectator; bit 3 the deferred list, refused until D-046; bit 1, v1's teleport flag, and bits 4–7 must be 0; spectator with starved refused), cvarHash 16, then inputBufferHealth i8 and teleportSeq 8 (D-035), both absent when spectator (70 bits). `lastProcessedCmdTick` is dropped: a cmd's tick is the server tick it is simulated on (D-027), so it always equalled serverTick, and no client read it; it returns if cmd ticks ever decouple from server ticks. `baseBack` replaces the u32 `baselineTick`: a baseline is at most 63 ticks back (`SNAPSHOT_HISTORY` 64).
- **Body:** the local block (v1's 199-bit `PlayerState`, unchanged; absent when spectator), entityCount 7 (0–63, or 0–64 when spectator), then one record per other present player, ids strictly ascending. A full ("new") record is 213 bits: id 16 (< 64; u16 per `docs/05` §4.2, kept for later entity kinds; never the receiver's own unless spectator), removed 1 (0: a removal needs a baseline), new 1 (1), origin 3 × i21 (1/32 u), velocity 3 × i16 (1 u/s: the 1/16 u/s velocity rounded half up and clamped to ±32767, INFERRED adequate for ≤ 2 ticks of extrapolation), yaw 16, pitch 16 (±16201), flags 10 (the `PMF_*` bits but jump-held and crouch-pressed-in-air, which only the owner's prediction reads: `ENTITY_FLAG_MASK`), team 2 (3 refused), teleportSeq 8, eventSeq 8 and two event slots (kind 4: 0 none, 1 step, 2 jump, 3 land, 4–15 refused; value 8: 0 when empty and for a jump; an empty first slot needs an empty second). "New" is only a body format: the client keeps no serial and snaps only on teleportSeq (D-035).
- **Sizes:** 292 bits alone (37 B), + 213 per other player: 436 B at 16 players, 862 B at 32 (the M3 design's golden), 995 B at 37. A live snapshot is at most `MAX_SNAPSHOT_BYTES` 1100: the encoder refuses more and so does the decoder (at most 39 other players fit a full one). A spectator snapshot (demo files only, D-044) is at most 2048 B; all 64 players take 1714 B.
- **Canonical:** an accepted packet re-encodes to the same bytes, and decodes to the frame it was encoded from as its receiver holds it (`WorldFrame`, D-034): the own slot from the local block with the header's teleportSeq, every record's slot with the snapshot's tick as its stamp, every other slot absent. The encoder refuses a frame it cannot carry exactly: a receiver absent, a slot whose stamp is not the tick (pending or deferred: D-046), a value out of range. Encoders and decoders allocate nothing, refusals included.
- **Code shape:** `shared/src/net/snapshot.ts` (`SnapshotHeader`, `encodeSnapshot(w, hdr, cur, base, selfId)`, `decodeSnapshotHeader`, `decodeSnapshotBody(r, hdr, base, selfId, out)`, with `base` null until D-038); v1's `SnapshotMsg` and its codec are gone from `messages.ts`, which now exports `readTick`/`writeTick`. The client's connection reads the header first, so a spectator snapshot on a live connection is struck and dropped before its body is parsed; outside the spawning and active states only the header is checked (an honest server sends snapshots only after READY, and before WELCOME the body can't be read without the receiver's id).
- **Deviation from M3 design §2.1 ("the encoder checks the size too: `w.fail()` and `DEV_ASSERT`"):** the encoder only fails (the NET-01 table drives it past 1100 B on purpose); the `DEV_ASSERT` sits in the match, where a failed encode is a bug.

**Consequences:**

### D-034 — Players: "Cap 64, default 32", entity slots and world frames (2026-10-08, accepted)

**Decision:**

A session's `serial` is its slot's connect counter (u16, wrapping): the encoder's "new incarnation" signal once deltas exist.

### D-035 — Teleport counter (2026-10-08, accepted)
**Context:** v1 flagged only the spawn tick's snapshot with TELEPORT, so a lost snapshot hid a spawn (the D-027 known limit), and remote players need the same signal for interpolation (D-037). M3 design §2.1, §2.3, §2.4 and §3. This entry covers increment 4 (the counter on the wire and its use for the render offset) and increment 5 (the predictor's `SNAPSHOT_TELEPORT` result, respawns, the remote view's `teleported` mark).
**Decision:**
- **An 8-bit `teleportSeq` per slot** replaces `SNAP_FLAG_TELEPORT` (flag bit 1 is now refused): every spawn steps it (wrapping), and it is kept per slot across the players who take that slot, so a new player in a slot also reads as a jump. The snapshot header carries the receiver's; every entity record carries its player's. It is the only snap signal; the server's `serial` only tells the encoder a slot holds a new player.
- **Client:** the first snapshot seeds the watched counter; afterwards only snapshots newer than the newest one (past the predictor's staleness check) move it, and a change drops the render offset as v1's flag did, even if the spawn's own snapshot was lost.
- **`SNAPSHOT_TELEPORT` (increment 5):** the counter lives in the predictor (`Predictor.teleportSeq`, seeded from the spawn snapshot; `teleports` counts the changes). A changed counter adopts the server's state and re-simulates the ticks after it like a correction, but returns `SNAPSHOT_TELEPORT`, is counted as `STAT_TELEPORTS` and never as a correction, and drops the render offset. A hard or parameter resync on the same snapshot keeps its own code (it adopts the state too) and the teleport still counts. `ClientSim.teleports` is gone: the stat replaces it.
- **Respawns (increment 5):** `Match.respawn(session)` spawns an active player again at the next point on the next tick, stepping the counter; team and serial stay (the same player). Unlike a READY spawn it keeps the player's queued cmds, a deviation from M3 design §2.4's "on spawn: … `queue.reset`": the client re-simulates the spawn state with exactly those cmds once it sees the new counter, so keeping them makes a respawn cost no starved tick and no correction, where clearing them would starve the ticks the client's lead had already covered and input redundancy (4 cmds per INPUT) doesn't re-send, which shows when INPUTs are lost right after the respawn. A respawned player faces the point's yaw on the spawn tick only: its next cmds carry the client's own absolute yaw, which never saw the spawn yaw (if the spawn snapshot is lost, no later snapshot holds it either), so it keeps its view direction. Turning the client's view to the spawn yaw on a respawn would need the server to hold the cmd yaw until the client has seen the counter; that is decided with deaths (M6) and rounds (M7), the first production callers. The spawn tick itself is closed in the input queue without a take (`InputQueue.skip`), so a copy of its cmd arriving later counts as a duplicate, not late.
- **Remotes (increment 5):** the client's `RemoteView` marks a slot `teleported` on the frame it appears or its counter changes, so nothing smooths it from its last place (interpolation keys on the same signal, D-037).

**Consequences:**
- Code: `packages/server/src/match/match.ts` (per-slot counters, stepped on spawn), `packages/client/src/net/clientSim.ts`. `docs/05` §2, §3.6, §5.
- Tests: `packages/server/test/match/match.test.ts` (the spawn snapshot carries counter 1 and no flag; a new player in a freed slot carries 2, and so does its entity in others' snapshots); `packages/tools/test/net/client-paths.test.ts` (a changed counter drops the render offset however short the move and counts one teleport, later snapshots with the same counter don't, the snapshot after the spawn's counts none, a lost snapshot of the jump still snaps, and a reordered older snapshot with the previous counter leaves the watched counter alone).
- Increment 5: code `packages/client/src/net/{predictor,clientSim,stats}.ts`, `packages/server/src/match/match.ts` (`respawn`), `inputQueue.ts` (`skip`); `docs/05` §2, §5, §8.1; `docs/10` §4.4 (the prediction workload's respawns). Tests: `packages/client/test/net/predictor.test.ts` (a changed counter returns `SNAPSHOT_TELEPORT` with no correction logged and the re-simulated state the server's, seeding, a wrapped counter, stale snapshots never move it, a teleport on a hard resync counted); `client-paths.test.ts` asserts the predictor's results directly: the bumped snapshot is the one `SNAPSHOT_TELEPORT` with 0 corrections, with it lost the next snapshot is, the reordered older one returns `SNAPSHOT_STALE`; a `Match.respawn` on `arena_greybox` with the spawn snapshot dropped is a teleport on the next snapshot with no correction, starve or hard resync, and snaps; `match.test.ts` (the respawn takes the next point and counter 2, faces the point's yaw on the spawn tick and the cmd's from the next, keeps team and serial, and simulates the cmd queued before it, which a cleared queue would starve; a copy of the spawn tick's cmd arriving afterwards is a duplicate, not late); `inputQueue.test.ts` (`skip`); `client-paths.test.ts` also: with `cl_inputBuffer` 6 and the two INPUTs after a respawn lost nothing starves (a cleared queue starves 2 ticks), a respawn on the first snapshot after the spawn is a teleport and not a correction (the counter seeded from the spawn snapshot), and a teleport drops a render offset still easing from a correction; the native-ESM prediction workload respawns every 4096 ticks, so the teleport path runs allocation-free.

### D-036 — Bots, server metrics and the bandwidth accounting (2026-10-09, accepted)
**Context:** `docs/05` §13 and `docs/10` §1 placed the headless bots in `packages/tools/bots` with no shape; NET-08 named "the lab map" and counted no framing; `docs/05` §9.2 priced INPUT at "4 cmds × 12 B", a layout M2 replaced (55 B with 4 cmds); NET-12 did not say what a reconnect is. The server's metrics (D-029) had no GC, traffic or run window to judge a load run by. M3 plan, "Spec decisions"; M3 design §2.14, §2.15, §3 and §6 increment 6. This entry covers increment 6; NET-08's test (increment 9), the human stand-in, the host gate and nice 10 (increment 18) extend it.
**Decision:**
- **Where and what:** `packages/tools/src/bots` (`pnpm bots`): one process, N bots, each a `ClientSim` behind its own `NetSimTransport` (the run's profile, seeded `seed + i`) over the client's `WebSocketTransport` on Node's built-in WebSocket, so a bot runs the browser's net code on a real socket; one `setTimeout` chain frames all of them at 60 Hz, bot i offset by i/N of a frame; each loads the map WELCOME names from `content/maps` inside `onMapRequest` (`provideMap`, synchronous). Defaults: 16 bots, `wan-100-loss1`, 2 min, `arena_greybox`, seed 1.
- **Behaviours** (`routes.ts`, `client/src/net/scriptedInput.ts`): 3 in 5 bots run `RouteInput`, a strafe-jump route; the rest `RandomWalk` (Mulberry32-seeded: forward on a heading drawn every 1–3 s, hopping on half of them). `RouteInput` starts at the waypoint nearest to the spawn, so one route serves all 16 spawn points; it shares the circuit's air steering (`StrafeSteer`, extracted from `StrafeCircuit`, whose cmds stay bit-identical). The arena route is the design's yard ring (x ±900, y ±560) **with its corners cut at 45°** (8 waypoints), and a route bot that lands more than 0.6 rad (design value) off its waypoint's direction runs on the ground until it points the way before it hops again: with the plain rectangle and air-only turning, bots overshot every corner into the walls and spent 7–22% of the time stuck (deviation from the design's bare "ring"; the tuning numbers are design values, `ROUTE_GROUND_TURN`). **Stuck** is under 32 u of progress toward the current waypoint in 2 s (design: "< 32 u of progress"): it random-walks for 1 s, then heads for the next waypoint. A route bot's stuck time counts the 2 s without progress and the 1 s out of it (the route test's "< 5% stuck" and the summary's stuck share). A map with no route gets random walks only.
- **The count check:** before connecting, the runner reads the target match from `GET /status` (`/` the default match, `/m/<name>` by name for D-047) and refuses a count that does not fit its `maxClients`, counting the players already in too: `count 40 > maxClients 37 on match main` (exit 2, nothing connected).
- **The server child** (no `--server`): `packages/server/dist/main.js` **when it is newer than the server's and the shared package's sources and its build script**, else the source under tsx (an addition to the design's "dist, else tsx": a stale bundle would run an older server, without this increment's metrics flags), with `--port 0 --map X --metrics-out <tmp> --metrics-discard 10` (a quarter of the run when that is shorter) and `--set sv_maxClients=<min(64, count + 2)>` only when count + 2 > 32, so 16 bots + 1 human need no flag. The child runs in a process group of its own (`detached`), so a terminal's Ctrl+C reaches only the bots, which end the window and stop the child with SIGTERM (a runner that exits any other way SIGTERMs it on the way out). The port and build hash come from its `listening` line (and must equal `/status`'s); with `--server` the hash comes from `/status`. The bots send that hash. The map a bot loads (`--map`, and the name a WELCOME sends) must be a map id (`[a-z0-9_]{1,63}`, the server's own rule), so a hostile `--server` can't point the load outside `content/maps`.
- **The run:** joins 100 ms apart; the measured window (`--minutes`) starts once every bot is in (or after 20 s); at its end the server's run window is read (the child's `--metrics-out` file after a SIGTERM, or `GET /metrics` of a `--server`, read at the window's start too, so its counters and traffic are end minus start), the bots disconnect, and `reports/bots/<UTC stamp>.json` and `.md` are written: configuration, host (CPUs, 1-minute load at start and end), server, each bot and the aggregate, and PASS/FAIL against `docs/10` §4.1 (tick p50 ≤ 1.5 ms, p99 ≤ 4 ms, GC pause ≤ 8 ms, the run window's peak heapUsed + external ≤ 150 MB) and §4.2 (the worst bot's down ≤ 32 KB/s and peak 1 s ≤ 48, up ≤ 8, every snapshot ≤ 1100 B), plus every bot joined and stayed. A server run window that began before the bots' first connect (a `--server` running since earlier; the runner can't reset it, `metrics reset` being stdin's) has its §4.1 numbers reported as "not judged", outside PASS. **Prediction health** (an addition to the design's "PASS/FAIL against `docs/10` §4", so the rule's bots run catches a netcode regression and not only a budget miss): no strike on the server (in the bots' window) or on any bot, and no misprediction, a correction on a snapshot the server did not flag starved (the e2e rule, `docs/10` §1; teleports are not corrections). Corrections per second and hard resyncs stay reported, not gated: a slow host's late frames cost them by design (D-028). ### D-037 — Remote entity interpolation (2026-10-09, accepted)
**Context:** `docs/05` §6 named the render time, the delay's formula and bounds, lerp, short-arc angles and ≤ 2 ticks of extrapolation, but not the render clock, the delay's window, what to do with lost or reordered snapshots, slots whose state is older than their frame (D-046), teleports, or how to judge NET-05 on stairs (a 16 u step-up in one tick with no vertical velocity breaks "speed × frame time × 1.5"). Until now the client drew the newest stored snapshot as it stood (D-034). M3 design §2.8, §3, §5 and §6 increment 7.
**Decision:**
- **Where:** `client/src/net/remotes.ts` (DOM-free). `ClientSim` owns a `RemoteInterpolator` over its snapshot store; every stored snapshot's tick reaches it as it is stored (`onStored`), and whoever draws calls `ClientSim.updateRemotes()` once per frame after `frame()` (the page's `Game.frame`, each bot, the NET tests): the view hides and the interpolation starts over while the session is not active. The renderer reads only its `RemoteView` (the same rows as D-034's).
- **Render clock** (`RenderClock`, independent of the prediction's clock): each newly stored newest snapshot gives o = serverTick − pollTime / TICK_MS (the frame's time: frame quantization counts as lateness). target = now / TICK_MS + max o over the last 120 arrivals (2 s) − D. Per frame the render tick advances by the frame's ticks × a rate of 1 + 0.5 × (target − (render + the frame's ticks)), clamped to [0.9, 1.1], with the floor at 0.5 while the render tick is past the newest stored tick; more than 6 ticks behind its target it snaps forward (counted after the first, which places the clock), and it never runs backwards, so ahead of its target by any amount it only slews down at the floor (the design's "|target − renderTick| > 6 → snap" read one-sided, since a backward snap would run render time backwards). **Window restart** (an addition): when 30 arrivals in a row (0.5 s) come more than 6 ticks later than the window's largest offset, that offset is stale and the window restarts from those 30 (`REBASE_ARRIVALS`, `REBASE_LATENESS_TICKS`, `RenderClock.rebases`). A server stall long enough for the match loop to drop ticks (`MAX_CATCHUP_TICKS` 5, so some 150 ms and more) shifts every later offset down for good; with the max kept for its full 2 s the render tick stayed past the newest snapshot and every remote was extrapolated or held for 2–3.6 s after each such stall (2.3 s after a 250 ms stall in NET-05's harness, 0.79 s with the restart). Jitter within the delay's reach never restarts it, nor does a burst after a link gap (its arrivals come in one poll, the last on time). The cost: a one-way latency rise of more than 100 ms that lasts over 0.5 s and then falls back can leave the render tick more than 6 ticks behind its target, a counted snap where the 2 s window would have held instead. **Deviation from M3 design §2.8's formula** (`1 + (target − renderTick) × 0.5`): the error is taken where the plain rate would put the render tick, since the target is of now and the render tick of the last frame; with the design's literal reading a frame of k ticks reads as k ticks behind, so the clock settles k ticks past its target, and at a slow host's 33–83 ms frames that put remotes 2–5 ticks ahead of their delay, extrapolating 30–55% of the time with NET-05 jumps.
- **Delay** (`InterpDelay`): lateness = max o − o over the same 120 arrivals, a histogram of 1/8-tick buckets to 8 ticks, p95 by nearest rank as the bucket's lower edge; snapshotInterval = the lower median tick step of the last 30 newest snapshots; D = clamp(ceil(2 × snapshotInterval + p95), 2, 6), rising at once, falling after 2 s below to the highest value of those 2 s. `cl_interpDelay` (default 0 = auto, design) fixes it at 2–6; **the cvar takes 0–6 and 1 counts as 2** (a deviation from M3 design §2.8's "2–6 when non-zero": the registry's range has no hole, so 1 is accepted and clamped rather than refused). The D-046 defer lag joins the sum in increment 10.
- **Samples by stamp:** per slot, a stored frame where it has state is a sample (stamp, fields, teleport counter); frames sharing a stamp give one; pending slots give none. a = the largest stamp ≤ the render tick, b = the smallest above, searched in the stored frames from the newest back over at least 8 (6 + the scheduler's 2-tick staleness bound, `SAMPLE_SEARCH_FRAMES`) **and on past lost frames to one 2 ticks before the render tick** (an addition: counting 8 frames or 8 ticks alone missed a after a 150 ms outage, holding the remote at its old place and then jumping).
- **Drawing:** same counter → lerp origin, short-arc yaw (u16), lerp pitch; crouch and team from a. A changed counter (D-035) or a removal between a and b → a until the render tick reaches b, then b, marked `teleported`; a first sample, or the first after a hide, appears at its stamp, marked too. Hidden from the first stored frame after a sample that marks the slot absent; pending slots never hide. No b → along the 1 u/s entity velocity at most 2 ticks past a, clamped by one `traceBox` of the stance's hull (`MASK_PLAYERSOLID`), then held. Back to samples (or a newer a while extrapolating) → drawn − raw becomes an offset decaying linearly over `cl_remoteSmoothMs` (100, ESTIMATE). **It snaps only when the raw path's own jump that frame is past both `cl_teleportDist` and what the slot's speed explains over the hold** (1.5 × the frame's NET-05 speed × (render − the old sample's stamp + 2) ticks, `REJOIN_SPEED_MARGIN`), and an offset still decaying is carried into the next one, not judged with it (a deviation from M3 design §2.8's "snap past `cl_teleportDist`", which conflicts with its own NET-05 outage case: a 150 ms outage at 700–760 u/s leaves 65–70 u, past the 64 u cvar, so the remote snapped and counted a violation; and on a busy page a sample landing while the last rejoin still decayed snapped 65–74 u on the carried total). A real teleport is keyed on the counter (D-035), so the snap is left for a jump nothing explains, and it counts as a NET-05 violation, in the bots' PASS/FAIL too. An eventSeq step of the drawn sample surfaces its new events, at most 2 (no consumer yet: sounds, M8).
- **Crouch blend:** the capsules blend their height over `cl_remoteCrouchBlendMs` (100, ESTIMATE), at once on an appearance or teleport (`render/players.ts`; `PlayerCapsules.update(view, blend)`).
- **NET-05's criterion** (`RemoteJumpMeter`): per frame, a drawn remote's step ≤ speed × dt × 1.5 + 0.5 u, speed = max(|v_a|, |v_b|, |b − a| / ((b.stamp − a.stamp) × TICK_DT)) over every bracket the render tick crossed since the last frame and the last frame's (an addition to M3 design §2.8's one bracket: the first real 16-bot run counted 6 violations, each a slow bot's 16 u step-up inside a bracket that a 60 Hz frame passed whole, neither end in it; the 16-client long leg now runs frames like the bots' timer), plus the rejoin offset's decay (its length, this frame's or the last's, × dt / `cl_remoteSmoothMs`); teleports, appearances and the clock's placement are exempt. The page counts it on its frames that are not long (`remoteJumps` and `remoteJudged`, the remote-frames it judged, with `remoteFrames`, `extrapolations`, `renderSnaps`, `interpDelay`, `interpP95` and `capsules`, the capsule instances the renderer drew, in the autotest status); each bot counts it the same way, and the bots summary judges it (an addition to M3 design §2.15's list, like D-036's prediction health): interp delay (mean, max), extrapolated or held share, NET-05 violations and the remote-frames judged per bot and aggregate, and the check "remote jumps (NET-05 violations)" = 0.
- **Stats** (`NetStats`): remote-frames drawn, extrapolated, held; render snaps after the first; remote events surfaced and lost. The netgraph gains a `remote` line ahead of D-043's full one: the delay in ticks and ms and the extrapolated and held shares of the last second.
- **Bench** (M3 design §5 "interp frame", §4's estimate; `packages/tools/bench/interp.bench.ts`, a fourth part of `pnpm bench`, reported, `--strict` failing only on a GC): one `RemoteInterpolator.update` with 16 remotes on `arena_greybox` at 144 Hz frames over a 60 Hz stream, clean and with 12 of every 512 ticks lost. ### D-038 — Delta snapshots: the codec, the client's store and the server's baselines (2026-10-09, accepted)
**Context:** `docs/05` §4.3 asks for deltas against the newest snapshot the client acked, a full snapshot when the baseline is too old or missing, and 64 snapshots kept on both ends; it does not say what the client acks, what it does with a delta whose baseline it lost, or how a re-sent body is told from a new player. Full v2 snapshots of 16 players are 436 B, about 26 KB/s down per client: inside the 32 KB/s budget of §9.2, but with little room. M3 plan, "Spec decisions"; M3 design §2.1, §2.3, §3 and §6 increment 8. This entry covers increment 8, the codec and the client's store, and increment 9, the server's history, ack validation and baseline choice (its own part below); the D-046 scheduler's deferred list builds on it.
**Decision:**
- **Delta forms** (layout in D-033's increment-8 part and `docs/05` §3.6): `baseBack` 1–63 codes the snapshot against the receiver's frame of tick serverTick − baseBack; a delta local block (mask 8, class-coded origin and velocity, the rest at the full block's widths; 8–219 bits); per other player a removal (17 bits), a full body ("new", 213) or a delta body (mask 8, never 0; 28–233); an unlisted player the baseline holds is unchanged and copied with the snapshot's tick as its stamp. Per axis a 2-bit class: 0 same, 1 a difference in i7 (entity velocity i6), 2 in i13 (i11), 3 the absolute value at the full width (design values); always the smallest.
- **"New" is a body format:** the encoder writes it when the baseline has no state for the slot or holds another incarnation (a different server `serial`, D-034), never by size; the client keeps no incarnation of its own and snaps on the teleport counter only (D-035). A decoded slot's `serial` is the baseline's, + 1 for a "new" record over a slot the baseline holds (0 over one it lacks), so a re-encode against the same baseline picks the same forms; the client reads it nowhere else (the M3 design §2.2 "the client leaves it 0" holds for full snapshots only).
- **Canonical and refused:** an accepted delta re-encodes to the same bytes against the same baseline (NET-01). Refused: a non-minimal class, a set group of all-0 classes, a set field or group equal to the baseline, mask 0, a delta record or removal for a slot the baseline lacks, a delta record for (and an unlisted copy of) a slot the baseline holds as pending (D-046), a baseline before tick 1, a delta against a baseline without the receiver's state, a full snapshot decoded with a baseline. The decoder never writes into its baseline (`out === base` is refused).
- **Sizes:** the worst delta is 312 bits + 233 per other player: 942 B at 32 players, 1088 B at 37 (`SNAP_FIT_MAX_PLAYERS`), so every snapshot fits by construction while baseline and current frame together hold ≤ 37 players by id; a static check in `snapshot.ts` fails the build if the layout breaks that (and if 37 stops being the largest such count). Exact size functions `localBlockBits` and `entityRecordBits` give what the encoder writes without writing (the scheduler sizes records with them).
- **Client store** (`client/src/net/snapshotStore.ts`): a snapshot is decoded only when newer than what its tick's ring slot holds (stale ones are dropped before the baseline lookup); a delta is decoded against the stored frame of its baseline tick, so by induction each stored frame equals the frame the server encoded it from (`frameDigest`). A delta whose baseline frame is not held is dropped as `STORE_NO_BASELINE`, counted (`baselineDrops`, `STAT_BASELINE_DROPS`), not struck; after 8 such drops in a row (`BASELINE_MISSES_BEFORE_FULL`, design) the store acks 0 until a full snapshot is stored. Counters `full`/`delta` (`STAT_FULL_SNAPSHOTS`). A snapshot whose body fails to decode is struck and leaves the ring as it was: it is decoded into a spare frame, so its tick's slot keeps the older frame it held, a genuine one the server encoded (this knowingly supersedes M3 design §2.3's "a failed body invalidates the slot", which would only lose a valid baseline).
- **Ack** = the newest stored tick (`SnapshotStore.ackTick`, 0 before the first and while asking for a full one), no longer the predictor's newest snapshot tick: `Connection.sendInput` reads it itself.
- **Until increment 9** the match still sent full snapshots and ignored the ack, so nothing on the wire changed with increment 8.

**Increment 9, the server (2026-10-09):** M3 design §2.3 and §2.5, §6 increment 9.
- **One shared history** (`server/src/match/history.ts`, `WorldHistory`): the match captures each tick's world frame (every active player, its serial, team, teleport counter and event history) at the end of the tick into a ring of the last 64, shared by every client; `Match.worldFrame` is the newest. Up to 37 players (D-034) a client's snapshot of T holds exactly world frame T as that client sees it, so nothing per client is stored but its **sent ring** (`Session.sentTicks`, the ticks of the last 64 snapshots sent, by `tick & 63`) and `newestSent`. A tick is marked sent only after its snapshot encoded; a failed encode clears its slot (`markUnsent`), so neither it nor the tick the slot held before can be acked or coded against (impossible up to 37 players; `DEV_ASSERT`). The D-046 mirror and the `snapshot_overflow` counter come with the scheduler.
- **Ack validation** (`acceptAck`, per INPUT, during the tick T it is read in; only from an active session, like its cmds): 0 drops the baseline (`ackTick` 0: the next snapshot is full); an ack past the newest snapshot sent is ignored and struck twice (`ACK_AHEAD_STRIKES`, design value; counted as two strikes until D-041's weighted strike score); otherwise the ack is taken only when it is valid, 0 < ack < T, T − ack ≤ 63, the sent ring holds it and the history still holds its frame, and newer than the baseline held, so a reordered or duplicated INPUT never lowers it and a stale or never-sent ack is ignored without a strike.
- **Baseline choice** (`baselineTick`, per snapshot): the acked tick while it is still valid at T, then baseBack = T − ackTick; else a full snapshot. Every session starts with no ack, so the first snapshot after READY is full, a late joiner's and a reconnected client's too (a reconnect is a fresh session, D-036); a client whose acks stop gets full snapshots from 64 ticks after its last one. ### D-046 — Snapshot byte-budget scheduler for 64 players (2026-10-09, accepted)
**Context:** `docs/05` §4.3 asks the server to defer low-priority entities to the next tick when a snapshot is over its 1100 B target (priority accumulator: distance, visibility, time since last update). Mustafa's "Cap 64, default 32" (D-034) admits up to 64 players, and above 37 the worst delta no longer fits: 1874 B with 63 others moving hard (1714 B full), 1101 B already with 36 others and 6 removals. Until this increment `sv_maxClients` was clamped to 37. M3 plan, "How the 64-player budget works" and "Spec decisions"; M3 design §2.1–§2.3, §2.5, §2.8, §3, §5 and §6 increment 10.
**Decision:**
- **Wire** (D-033's increment-10 part, same `PROTOCOL_VERSION` 2): flags bit 3 (DEFERRED) is accepted; with it a deferred list follows the records, count 6 bits (1–63) then ids u16 strictly ascending, never the receiver's own, never an id with a record, never a slot that left (a removal is always sent). In a delta a deferred slot whose baseline holds state keeps that state and its (older) stamp; one whose baseline slot is pending or absent, and every deferred slot of a full snapshot, becomes **pending** (present, stamp 0). The encoder writes a slot as deferred exactly when its stamp is not the tick, and only as the receiver would rebuild it (a copy of the baseline's state, stamp and incarnation, or pending where the receiver holds no state); it sets the flag itself, exactly when it lists an id, so encoding stays canonical. Spectator snapshots never defer (refused with SPECTATOR).
- **Cap:** `sv_maxClients` takes its full 1–64 range (the clamp to 37 and the `max_clients_clamped` log line are gone); ids stay the lowest free below the cap, so at the default 32 the scheduler never runs.
- **Worst-case check (bypass):** per client and tick, W = 312 + 233 p + 17 r bits for a delta (p other players present now, r slots the baseline holds, pending included, gone now: popcounts of the frames' masks), 292 + 213 p for a full snapshot. W ≤ 8800: everything goes, no size pass, the frame is plain (the world frame). Otherwise a size pass with the encoder's exact size functions; if the exact total fits, everything goes, still plain.
- **Selection** (`server/src/match/scheduler.ts`, `SnapshotScheduler`): removals (17 bits) always go; every other record is reserved up front at its out cost, 16 bits for a deferred id, 17 for a **reused slot** (a new incarnation where the baseline still holds the departed player), which is sent as a removal when left out (absent in the client's frame), so the departed player disappears on time and the new one is never drawn at the old one's place; then the records go in priority order while used + (bits − out cost) ≤ 8800, skipping one that does not fit and going on (first fit). Priority (M3's accumulator is the time term only; distance and visibility join with relevance in M9): staleness (ticks since the last sent snapshot that carried the player fresh) descending, then the tick it was last left out descending (the one left out longest ago goes next: rates rotate), then id ascending, by insertion into a preallocated order; a reused slot whose new player the client was already sent (its acked baseline still holds the old one, for about an RTT) ranks just above the other staleness-1 records, so it does not blink out for a tick as a removal unless the due ones fill the snapshot (the bound is unchanged). Unchanged players cost nothing and are never left out. A player new to the client (a join, or a new incarnation in the slot, told by the server serial the client was last sent) counts as carried at T − 1.
- **Bound** (static check in `shared/src/net/snapshot.ts`, failing at load): `SNAP_MIN_CAPACITY` = ⌊(8800 − 318 − 63 × 17) / (233 − 17)⌋ = 34 records fit any delta (`SNAP_MIN_CAPACITY_FULL` 37 a full one), and 2 × 34 ≥ 63, so at most 29 players are left out of a snapshot and only those are due (staleness ≥ 2) next tick, which always fit first: nobody is left out two sent snapshots in a row (`SNAP_MAX_STALENESS` 2), and every snapshot is ≤ 1100 B (the worst, 34 records + 29 deferred ids: 8704 bits, 1088 B). A due player left out anyway (impossible by the bound; `DEV_ASSERT` in the match) is counted as `sched_overrun` and logged.
- **Per-client rows and commit on success:** `lastSent`, `lastDeferred` and `sentSerial` (`Session`, `ScheduleState`) are written for every sent snapshot, bypass included, so crossing from 37 to 38 players starts with correct staleness. `buildSnapshot` prepares the next rows in the scheduler's scratch and commits them only after the encode succeeds; a failed encode (impossible by the bound; `DEV_ASSERT` in the match) sends nothing, marks the tick unsent and keeps the rows, and the match counts and logs `snapshot_overflow`.
- **Mirrors** (`server/src/match/mirror.ts`): in a match whose `sv_maxClients` is above 37 each session takes a `ClientMirror` from the match's `MirrorPool` at connect (and every session present gets one when `Match.setMaxClients` raises the cap above 37, outside the tick: the hook for a runtime admin change, which M3 does not have yet, since `sv_maxClients` is a SERVER cvar read at startup); it goes back on leave and the next session reuses it. A mirror is a 64-frame ring of what the client holds for each sent tick that left players out: fresh rows from the world frame, copied rows (a left-out player keeps its baseline's row, incarnation and stamp, copied when the snapshot is built, so a chain of deferrals never reaches past the 64-frame history) and pending slots. `sentFrame(history, mirror, tick)` resolves any sent tick: the mirror's frame when it holds the tick, else the world frame (plain). A 32-player match allocates none; at 64 they take about 225 KB each (14 MB in all).
- **Client:** the store decodes deferred copies and pending slots (stored frames equal the sent frames, stamps and pending slots included); counters `deferred`, `deferredSnapshots` (`STAT_DEFERRED`, `STAT_DEFERRED_SNAPSHOTS`). The interpolation searches samples by stamp over 6 + `SNAP_MAX_STALENESS` frames, and on past them while an older frame could still hold a fresher sample at or before render time (the bound holds for the sent stream, not for each frame: a deferred copy keeps its baseline's stamp, so with the fresh frames near the render tick lost the window could end on old copies and draw a remote back where it was, before a respawn even); it never hides a deferred or pending slot; `InterpDelay` adds the **defer lag** (`ID_DEFER_LAG`): the largest, over the last 120 newly newest snapshots, of each one's largest gap between its tick and the newest stamp held in any stored frame of a player it left out (pending slots with no sample yet ignored; 0 when it left nobody out), so D = clamp(ceil(2 × interval + p95 + defer lag), 2, 6); it is 0 up to 37 players and 1 with the scheduler working without loss.
- **Metrics:** the match counts size passes, players left out and the snapshots that left any out, the largest staleness at send, `snapshotOverflow` and `schedOverrun` (`MatchMetrics`, per session in `SessionStats`); the Node server's metrics line and `/metrics` carry them (`docs/06` §8), and the bots summary reports them.
