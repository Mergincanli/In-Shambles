### D-001 — Clean-room policy and licensing default (2026-10-04, accepted)
**Context:** We reproduce Urban Terror's movement and balance. Its assets and game code are proprietary; Quake III's code is GPL v2.
**Decision:**
- Use no UrT files, code, names or assets, and do not decompile or reverse-engineer its binaries.
- Use no GPL code. Implement from our specs; observing the original's behavior is allowed.
- Shipped dependencies are permissive only (MIT/BSD/Apache/ISC/MPL).

**Consequences:** some constants are ESTIMATE until measured from gameplay captures. We keep licensing options open (decision O-5).

### D-002 — Tech stack (2026-10-04, accepted)
**Decision:** TypeScript strict monorepo (pnpm), Vite client, Node LTS server, Vitest, Biome, Three.js (`WebGLRenderer` first), `ws` for WebSocket.
**Why:** one language across server, worker and client; mature tooling; Mustafa's existing Three.js/React experience (FORGE).
**Consequences:** performance discipline needed in JS hot paths (`docs/06` §9).

### D-003 — Server-authoritative Q3-style netcode (2026-10-04, accepted)
**Decision:**
- Inputs-only clients. Shared deterministic sim; client prediction + reconciliation.
- Snapshot interpolation for remote entities. Hitscan lag compensation with capped rewind (200 ms).

**Consequences:** every gameplay feature must define networked state, prediction and tests.

### D-004 — 60 Hz fixed tick (2026-10-04, accepted)
**Context:** UrT ended at a 20 Hz server rate. Modern competitive shooters run 60–128 Hz.
**Decision:** 60 Hz simulation, snapshots (30 Hz fallback per client) and inputs (with 4-cmd redundancy). Render decoupled with interpolation.
**Consequences:** movement feel is tuned at 60 Hz; changing the tick requires re-tuning (`docs/03` §1).

### D-005 — Everything runs through a server, even offline (2026-10-04, accepted)
**Decision:** local play uses the same server code in a Web Worker over a loopback transport, plus a network simulator.
**Why:** netcode is never an afterthought; one gameplay path.

### D-006 — Units and axes (2026-10-04, accepted)
**Decision:** 1 u = 1 inch, Z-up in sim, maps and netcode. Conversion to Three.js Y-up meters happens only in `client/render/space.ts`.
**Why:** matches UrT's unit convention and TrenchBroom/Quake map space; avoids conversion bugs in physics.

### D-007 — Brush-based collision; no physics engine for players (2026-10-04, accepted)
**Decision:** world collision = convex brushes (planes) with swept-AABB traces; Q3-style kinematic collide-and-slide.
**Why:** crisp, predictable edges are essential for wall jumps, ledge grabs and slides. Triangle meshes cause internal-edge snags.

### D-008 — Compiled map format + TrenchBroom via Valve 220 (2026-10-04, accepted)
**Decision:**
- A greybox TypeScript builder first.
- In M5, a TrenchBroom `.map` (Valve 220) compiler producing the same `cmap`.
- Custom TrenchBroom game config + FGD.

### D-009 — Transport abstraction; WebSocket first, WebTransport later (2026-10-04, accepted)
**Decision:** all messages are designed for unreliable delivery (acks, baselines, redundancy). Ship WebSocket in M3; add WebTransport datagrams with fallback in M9.
**Why:** WebTransport reached all major browsers in 2026, but server-side tooling is younger. WebSocket's head-of-line blocking is acceptable early on.

### D-010 — Balance source of truth = UrT 4.3 damage table (2026-10-04, accepted)
**Decision:** `content/weapons/damage.json` mirrors `docs/04` §4 exactly (golden test). Fire rates, reloads and spread start as labeled estimates and get replaced by captured measurements.
**Consequences:** FACT values change only on Mustafa's explicit instruction.

### D-013 — Art direction: "Comic Noir" (2026-10-04, accepted)
**Context:** O-4 was open. The game needs its own visual identity (pillar 5) that stays readable at competitive speed and fits the browser performance budgets.
**Decision:**
- Adopt **"Comic Noir"**: a modern Franco-Belgian comic look inspired by XIII (2003), rebuilt for a competitive browser FPS. The rules live in `docs/08`; `docs/08a` is reference research, not rules.
- Core techniques: banded lighting with tinted shadows over baked lightmaps, pixel-width hull outlines on actors, compiler-emitted crease lines plus a screen-space edge pass, world-space hatching on environments only, onomatopoeia lettering and comic panels.
- When rules collide: readability and fairness → performance budgets → style fidelity.
- Borrow the style family only: no XIII characters, story elements, logos, UI layouts or traced art (`docs/08` §3).
- Onomatopoeia is generated only from sound events the client legitimately receives (`docs/08` §11.2).

**Why:** flat color, baked light and ink lines are cheap to render in a browser and suit brush-built maps (`docs/08` §6, §7.2). Onomatopoeia doubles as a fair sound visualizer and an accessibility feature (`docs/08` §11).
**Consequences:**
- Exact parameters (bands, line widths, palettes, team colors, lettering font) are locked in look-dev (`docs/08` §17) and recorded in a later D-entry.
- Art work starts before M8 (`docs/08` §18): an optional style spike after M2, crease-line data from the compiler in M5, comic FX and UI hooks in M6–M7.
- Baked world lighting narrows the `docs/07` §5 lighting choice to a lightmap bake (options 1–2).

### D-015 — The dedicated-server dev command is `pnpm dev:server` (2026-10-04, accepted)
**Context:** the docs named it `pnpm server`, but pnpm 10 has a built-in `pnpm server` command (it manages a store server). Built-in commands take priority over package scripts, so `pnpm server` silently did nothing and exited 0.
**Decision:** the root script is `dev:server`. It runs the server from source with tsx. Production runs the esbuild bundle that `pnpm build` produces (`node packages/server/dist/main.js`).

### D-016 — Deterministic math (2026-10-05, accepted)
**Context:** prediction needs client and server to compute bit-identical results. ECMA-262 lets engines approximate `Math.sin`, `cos`, `atan2`, `pow`, `exp`, `log`, `hypot` and the other transcendental functions, so Chrome, Firefox and Safari can return different bits for the same input. A one-ulp difference is enough to diverge a predicted state from the server's.
**Decision:**
- **Banned** in `packages/shared` and in compiler code that produces output (the greybox compiler from M1, `mapc` later): `Math.acos`, `acosh`, `asin`, `asinh`, `atan`, `atanh`, `atan2`, `cbrt`, `cos`, `cosh`, `exp`, `expm1`, `hypot`, `log`, `log1p`, `log10`, `log2`, `pow`, `sin`, `sinh`, `tan`, `tanh`, and the `**`/`**=` operators (they are `pow`).
- **Allowed**, because the spec rounds them exactly: `+ − * / %`, `Math.sqrt`, `fround`, `round` (halves toward +∞), `floor`, `ceil`, `trunc`, `abs`, `sign`, `min`, `max`, `imul`, `clz32`, bitwise operators, number literal parsing, and constants such as `Math.PI`.
- **Trig:** `math/dtrig.ts` builds `dsin`/`dcos` from exact operations only (Cody–Waite reduction, Taylor polynomials, |x| < 1e5), plus a quarter-wave table for u16 angles: `sinU16`/`cosU16` are exact at the cardinal angles and exactly odd and even.
- **Vectors** are `Float64Array`s with out-params. Modules keep named scratch vectors instead of sharing a general pool, which would add bookkeeping and aliasing bugs for no allocation benefit (`docs/06` §3 and §5).
- Never route sim values through a `Float32Array` (render code copies, never writes back), never store NaN, normalize −0 to +0 when quantizing, and never enable "unsafe math" minifier options.
- `dpow` (from deterministic exp and log) follows in M4 for the fall-damage curve.

**Consequences:**
- The shared purity guard rejects the banned names and `**`, and flags any use of `Math` other than `Math.<allowed member>` (computed access, optional chaining, aliasing, destructuring). The rules live in `packages/tools/src/code/deterministicMath.ts`, so compiler code can reuse them.
- The same guard flags any bare `Date` (an alias would reach `Date.now`), locale-dependent APIs (`localeCompare`, `toLocale*`, `Intl`), whose results vary by engine and locale, and `\u` escapes outside strings, which would hide a banned identifier from every name rule.
- Committed determinism vectors (`packages/shared/test/vectors/determinism.ts`, input bits → output bits for dtrig, quantizers, `quantizePlayerState`, `sanitizeUserCmd`, Mulberry32 and hash32) are recomputed by the tests; M2 replays them in Chrome, Firefox and Safari (`docs/09` M2, `docs/10` §1).
- Constants that were written with `**` in shared (the cvar registry's i32 range) are now literals.

### D-017 — Trace epsilon, touching, and snapping to the nearest clear grid point (2026-10-05, accepted)
**Context:** M1 builds the brush traces (M1 design A, `docs/design/M1-design.md`) and needs a rule for contact. `docs/05` §4.1 and `docs/03` §6 rounded the origin to the nearest 1/32 u every tick. That is safe after a single stop, but not across repeated slides on a slope or a rotated wall: sliding keeps the distance to the plane unchanged, each tick's rounding moves the box by up to √3/64 u along the normal, and nothing pulls it back. Within tens of ticks the box sits inside the brush, the next trace starts solid and the player is stuck. Axis-aligned planes at grid distances can't drift, so only slopes and angled walls (the kick lanes) show it.
**Decision:**
- **ε = 1/32 u** (`TRACE_EPSILON` in `packages/shared/src/world/trace.ts`): a trace stops one skin short of the surface it hits. It is a design constant, not a cvar: client and server must trace identically, and ε is not a feel knob. It is exact in binary and one origin grid step.
- **Touching counts as outside.** Inside a brush means strictly behind every plane, so a box that exactly touches a brush is clear: a spawn with its feet on the floor, or a box flush against two brushes.
- **Trace rules:** entering times stop ε early and leaving times are exact, so in exact math a box can touch a brush but never enter it. A move that does not approach a plane, as computed, is free, which covers sliding on a face or inside the skin; one that approaches it from inside the skin stops at once without `startSolid`. Ties between brushes go to the lower brush index, so the result never depends on visiting order. `endpos` copies the end exactly at fraction 1 and the start at fraction 0, and the reported plane is the brush plane, not the box-expanded one.
- **End-of-tick snap** (`snapOrigin`): the nearest **clear** 1/32 u grid point, in this order:
  1. the rounded point, if a position test says it is clear;
  2. otherwise the 8 corners of the grid cell holding the exact position, nearest first, ties in corner bit order (bit 0 = x rounded up, bit 1 = y, bit 2 = z);
  3. otherwise last tick's origin, which was on the grid and clear.
- The snap tests world brushes only (the mask excludes players), so a client's prediction never depends on where it thinks other players are. The common case costs one position test per player-tick.

**Consequences:**
- pmove calls `snapOrigin` at the end of every tick from M2, instead of plain rounding. `quantizeOrigin` stays the codec primitive: the snap only chooses which grid point, and the result is already on the grid. Positions stay out of solid by induction: traces never end inside a brush, the snap never accepts a solid point, and the course tests check that spawns are clear.
- **Map metrics:** on a flat floor a player rests at floor + 1/32. Crouched, the hull top is then at 40 + 1/32 u, so a 40 u gap blocks: slide gaps are 41–44 u (the courses use 41, 42 and 44) and the crouch tunnel is 48 u. An 18 u step still clears and a 19 u step blocks. `docs/07` §3 and §6 say so.
- `docs/05` §4.1 and `docs/03` §6 say "nearest clear 1/32 u grid point"; `docs/03` §4 states the trace contract.
- **Tangency is not exact on angled planes.** On slopes and rotated walls a move along the stored plane can round to approaching it by a few ulps (about 1e-14 u), and from inside the skin that stops the trace at fraction 0. We keep the rule table rather than add a tolerance, because a tolerance would let slow inward drift through; M2's slide move leaves a plane through the overclip (`docs/03` §4.7) and the same-plane nudge (§4.8), not exact tangency. The M2 feel tests on the slope set watch for stalls.
- An `allSolid` trace reports no hit (brush and plane −1, zero normal, no surface flags; contents are the brushes it started in), even when a later brush lies on its path: the box never moves, so that brush is not a contact (M1 review; one committed trace vector changed).
- Traces and position queries reject coordinates beyond ±2^20 u (`TRACE_COORD_LIMIT`) like NaN: farther out, f64 rounding eats the skin and then whole brushes.
- The cost is corner snags of up to ε when a box passes within ε of an edge. Shrinking the leaving time by ε instead would allow real penetrations of up to ε, which would show up as `startSolid` on the next tick.
- Tests: `packages/shared/test/world/{trace,traceQueries,snapOrigin}.test.ts`, including slide-and-snap chains on 0.69/0.71/0.8 slopes and 15/30/45/60° walls: the snap never goes solid, and plain rounding does on every surface except the 45° wall, where rounding x and y moves the plane distance monotonically and by less than ε, so it cannot drift. Committed trace vectors in `packages/shared/test/vectors/trace.ts` (input bits → output bits on a fixed world) are recomputed by the tests, and M2 replays them in browsers. The increment 9 fuzz test adds 200-step snap chains (P7).

### D-018 — PlayerState and UserCmd layout for M1 (2026-10-05, accepted)
**Context:** M1 implements `PlayerState` (`docs/03` §6) and `UserCmd` (`docs/05` §3.4). Both docs leave the bit order, the fixed-point stamina format and the field ranges open, and `docs/05` lists "kick-eligible" among the buttons although it reads as derived state.
**Decision:**
- **Kick-eligible is not a button.** It reads as state derived from the player and the weapon, not an input, so it is left out until the kick is built in M4 (M1 plan, open question 1). `buttons` bits 0–11 are attack … drop in the `docs/05` order; bits 12–15 are spare.
- **Stamina** is an integer count of hundredths (u16). `flags` bits 0–9 are the `docs/03` §6 flags in the listed order.
- **Ranges:** `origin` ±16384 u and `velocity` ±(2^19 − 1)/16 u/s (±32767.9375, the i20 range) per axis, clamped by the end-of-tick quantizers so a stored value is exactly what the codec carries; `groundEntity` −1 (none) to 32767 (the world); `waterLevel` 0–3; move axes ±127 (the i8 never carries −128); pitch ±89°; `weaponSlot` 0–7 (the knife plus the seven `docs/04` §9 loadout slots); `tick` 0…2^30 − 1 (not the full u32), so ticks stay V8 small integers (about 207 days at 60 Hz).
- `quantizePlayerState` maps a non-finite `groundEntity` to −1, not 0, because 0 is a real entity. `sanitizeUserCmd` clamps and masks untrusted input and never throws. It is idempotent, and the client applies it before predicting, storing and sending a cmd (`docs/05` §5), so client and server simulate the same cmd.

**Consequences:**
- `docs/03` §6 and `docs/05` §3.4 carry "Pinned down in M1" notes; the code is in `packages/shared/src/sim/`.
- M1 implements the `docs/03` §6 fields `origin`, `velocity`, the view angles, `flags`, `groundEntity`, `waterLevel` and `stamina`. `wallJumps`, `health`, `armor`, `breathMs`/`drownMs`, `climbTarget`, the timers and `movementEvents` are appended to `PlayerState` (with their quantize, codec and parity coverage) by the milestone that first simulates them.
- Open for later milestones: whether kick-eligible needs any wire bit (M4), and which `weaponSlot` index is which and whether out-of-range slots clamp or mean "no change" (weapon switching). The `docs/03` §2 hull table is labelled FACT for Q3 (Mustafa, 2026-10-06).

### D-019 — Brush contents, surface flags and build rules for M1 (2026-10-05, accepted)
**Context:** M1 implements the collision brushes of `docs/07` §2. The doc names the contents flags and optional per-side surface flags but leaves their bits open, and §4.3 says to reject degenerate brushes without saying what degenerate means. Traces also need bevel planes, which the doc does not mention (M1 design B).
**Decision:**
- Contents bits 0–7 in the `docs/07` §2 order; masks `MASK_PLAYERSOLID` (solid + playerclip), `MASK_SOLID`, `MASK_WATER`.
- Surface flags per side: ladder, slick and nodamage bits (`docs/03` §4.10, §4.14, §5.6), plus a 4-bit footstep material field (`docs/07` §6 prefixes). M2 decides whether ladders use the face flag or the LADDER volume; M1 provides both.
- Brushes are built from f32-rounded planes, so polygons, bevels, bounds and render vertices agree with what traces use. Axial bevels follow the faces with outward-rounded distances; they make boxes, boxes rotated about Z and axis-aligned wedges exact. `buildBrush` adds only axial bevels, so other shapes build but trace inexactly: the greybox MapBuilder (increment 7) rejects shapes that would need edge bevels, and `mapc` adds edge bevels in M5.
- Cleanup rules the design left open: a vertex near its neighbours' line (1e-4 u) is removed only when it lies on fewer than 3 kept faces, so a real corner where two faces meet almost flat stays; vertices within 1e-5 u of an exactly axial face snap onto it, so axial coordinates are exact and the face distance is a tight bound.
- Each brush's bounds must be exactly the distances of six axial planes among its faces and bevels; `createCollisionWorld` rejects other bounds (increment 5). The BVH culls by these bounds, so a brush reaching past them would make `traceBox` drop hits that `traceBoxBrute` reports.
- Validation thresholds: weld 1/64 u (§4.3), minimum edge 1/8 u, no two vertices of a face within the weld distance, minimum volume above 1 u³, vertex-on-plane tolerance 1e-4 u, world limit ±16384 u (a plane further than 16384·√3 + 1 u from the origin is rejected up front, since no face of an in-bounds brush can be there).

**Consequences:**
- `docs/07` §2 carries a "Pinned down in M1" note and `docs/06` §3 lists the world modules.
- The shared polygonizer is the single implementation: the greybox compiler (M1), `mapc` (M5) and the trace fuzz oracle all use it, and its own tests cross-check it against brute-force triple-plane intersection.
- Outward-rounded bevels make the traced brush reach up to one f32 step of the coordinate past its vertices (about 1e-4 u at 1000 u, 1e-3 u near the ±16384 u limit), and position tests call a box in that sliver solid. Traces stop ε short of bevels like any other plane and the snap only accepts clear points, so a player never ends up there. The trace fuzz test (`packages/tools/test/fuzz/`) compares traces with exact geometry, so wherever the runtime may report contact beyond the true brush (P2, P3, P4) it allows that brush's sliver on top of τ = 1e-5, capped at one f32 step of the brush's largest vertex coordinate so a misplaced bevel cannot widen its own tolerance. P1 inherits the allowance: it excuses the brushes the runtime puts the start inside, and by M1 design A.4 (a box may move out of a brush it starts in) a box starting in the sliver may move through that brush; P2 bounds that set to τ + sliver, and such starts are unreachable in play. P4 checks the stop two-sided: at most M1 design G's 2√3·ε + τ (+ sliver), and at least ε − 1e-6 when the trace moved, because the entering plane is then exactly ε away.

### D-020 — cmap v1 layout: contentHash in a binary preamble (2026-10-05, accepted)
**Context:** `docs/07` §2 put `contentHash` in the JSON header, which would make the hash cover a header that contains it, and allowed a `.cmap.json` + `.cmap.bin` pair in dev. D-008 fixes the format's role, not its layout (M1 plan, spec change 3).
**Decision:**
- One little-endian file: a 32-byte preamble (magic, `formatVersion`, JSON length, section count, the 64-bit `contentHash`, total length), a section table, canonical ASCII JSON metadata, then 8-aligned binary sections (`PLNS`, `PLSF`, `BRSH`, `SURF`, `VTXS`, `IDXS`). No dev file pair: the greybox compiler writes the single file directly.
- `contentHash` is two Murmur3 x86_32 lanes over the whole file with the hash field read as zero: every other byte is covered, the hash never covers itself. This includes the preamble (the M1 plan said bytes [32, EOF)), so a corrupted `formatVersion`, length or reserved word also changes it. Identity and caching only, not security.
- The decoder accepts only the exact layout the encoder writes (sections contiguous in table order, zero padding, nothing after the last section, JSON followed by fewer than 8 spaces), so no two accepted files differ only in filler bytes.
- M1 review tightened this to the content the encoder writes as well: the JSON must be exactly `canonicalJson` of its parsed value (moved from tools to `packages/shared/src/world/canonicalJson.ts` so the decoder can check it), entity origins lie within ±16384 u, the header bounds equal the union of the brush bounds, and render surfaces tile `VTXS`/`IDXS` in order, one non-empty surface per material in increasing order. Overlapping surfaces made the index check cost surfaces × indices, so a small hostile file could stall a loader; tiled, it is linear. Every committed map already met these rules, so no map changed. A size cap for maps sent over the network is left to the milestone that first sends one.
- The BVH is built at load time, deterministically, not stored. Unknown section tags are ignored; `formatVersion` changes when the layout breaks, `compiler.version` when output changes on purpose.

**Consequences:**
- `docs/07` §2 carries the layout tables; `decodeCmap` validates everything and throws `CmapError`; `*.cmap` is `binary` in `.gitattributes`. Tests: `packages/tools/test/greybox/cmap.test.ts`, `packages/shared/test/world/cmap{,Hash}.test.ts`.

### D-021 — Greybox builder API and render-surface conventions (2026-10-05, accepted)
**Context:** M1 increment 7 builds the greybox compiler and `MapBuilder` (`docs/07` §3). The doc's API sketch has no slopes with a target normal, rotated boxes, ladders with a face flag or named anchors, which the courses need (M1 design I), and it leaves open where entity yaw goes, which faces render and how uv0 is mapped.
**Decision:**
- `MapBuilder` adds `slope` (rise = run·√(1 − nz²)/nz, returns the compiled wedge's f32 top so a platform at that z shares the crest's plane distance), `rotatedBox` (closed-form cos/sin, D-016), `ladder` (wall with the ladder surface flag plus a 16 u LADDER volume, both until M2 picks one, D-019) and `anchor` (`info_target` with `targetname`). `stairs`, `ramp` and `slope` return their top z.
- `ramp` must be axis-aligned; the builder throws otherwise. Every brush also passes an exactness check (each edge × axis, oriented outward between the edge's two face normals, is parallel within 1e-6 to an axis or points the same way as a face normal), so nothing that needs edge bevels compiles before `mapc` adds them in M5. A call that throws adds none of its brushes.
- Entity `angles` are [pitch, yaw, roll] in degrees, yaw 0 facing +x (now stated in `docs/07` §2); the builder stores yaw there as [0, yaw, 0], not in `props`.
- Render surfaces: one per material in material order (the table is in order of first use); solid brushes and water volumes render, clip, trigger, nodraw and other non-solid volumes don't; fans from each polygon's canonical start vertex, counter-clockwise from outside, f32 positions, flat face normals.
- uv0 is a world-space planar projection on the normal's dominant axis (ties to z, then x) at 1 uv per 64 u, which M2's grid texture relies on.
- `compile()` returns the decoded file (validated, with its hash); `compiler.version` starts at 1.

**Consequences:**
- `docs/07` §3 lists the API and conventions. Courses (increment 8) use anchors instead of coordinates in tests.
- The D-016 math ban now also guards `packages/tools/src/greybox` (`greybox-determinism.test.ts`), as D-016 already required.
- Tests: `packages/tools/test/greybox/{brushCompiler,mapBuilder}.test.ts`.
- Courses (increment 8): each course in `packages/tools/src/greybox/courses/` is a function that builds and returns its Cmap, listed in a fixed order in `courses/index.ts`. `pnpm greybox` writes them to `content/maps/<name>.cmap`, which is committed (M1 plan); a test fails with "run pnpm greybox and commit" when a file is stale. Anchors and spawns are standing spots (origin = ground + 24 u). `docs/07` §3 lists the sizes the courses pin down (lab area, water depths 12/36/128 u, slide gaps 41/42/44 u plus a blocking 40 u gap, 48 u tunnel, runway timers 2048 u apart, catch rails 64 u tall in separate columns so one catches a 768 u fall); they are design values, not ESTIMATEs of the original game.

### D-022 — Browser determinism replay (2026-10-06, accepted)
**Context:** D-016 and D-017 freeze the bits of the deterministic math and the traces as vectors, and the M1 plan promised a replay in real browsers in M2 (risk 2), because clients predict with the same code in Chrome, Firefox and Safari. M2 plan, increment 1 and risks 4–5.
**Decision:**
- Vitest browser mode with `@vitest/browser-playwright` (MIT) replays every `packages/shared/test/*-vectors.test.ts` unchanged, headless, from `vitest.browser.config.ts`; `pnpm test:browser` runs it and `pnpm test` (the Node run) never loads it. The vectors tests stay free of Node APIs and other packages: `packages/shared`'s `types: []` makes a `node:` import fail the type check, and `packages/tools/test/guards/browser-vectors.test.ts` checks that everything they load is a relative module or `vitest`, that the config stays in headless browser mode on that glob, and that the CI job's test step runs all three engines.
- `BROWSERS` (comma list of `chromium`, `firefox`, `webkit`; default `chromium`) picks the engines; an unknown, repeated or missing name stops the run. The dev container uses its preinstalled Chromium build and never runs `playwright install`; a CI job `browsers` installs all three with `playwright install --with-deps` and runs them, and other machines can run `pnpm exec playwright install` (README).
- WebKit runs JavaScriptCore, Safari's engine, so it stands in for Safari. It is not Safari itself; a phone test page for real Safari or Chrome on a phone comes in M2 increment 12.
- `playwright` (Apache-2.0) is pinned to exactly 1.56.1, the release whose Chromium revision (1194) matches the build installed in the dev container, so it finds it through `PLAYWRIGHT_BROWSERS_PATH` without a download. `CHROMIUM_PATH` overrides the Chromium executable if the versions drift.

**Consequences:**
- `docs/10` §1–2 and `docs/06` §11 list the command and the CI job; the `docs/09` M2 acceptance line cites this entry. The pmove vectors (M2 increment 6) and any later `*-vectors.test.ts` replay in the browsers with no config change.
- Firefox and WebKit are proven only in CI; the M2 acceptance box for them is ticked once the PR's `browsers` job is green.

### D-023 — pmove contract (2026-10-06, accepted)
**Context:** M2 increment 3 builds the base pmove pipeline (`docs/03` §3, §4.4–§4.11). The spec left four things open: what "starts in solid" means now that D-017 distinguishes `startSolid` from `allSolid`; where slick and nodamage come from, since bevel planes carry no face flags; what "crouch-blocked" means; and how the tick length and the movement events reach and leave pmove (M2 plan, "Spec decisions"; M2 design §2–§3).
**Decision:**
- **Signature:** `pmove(ps, cmd, world, params, dt, events | null, debugLog | null)` updates `ps` in place.
  - `cmd` is already sanitized.
  - `dt` is a parameter: `TICK_DT` in play, 1/120 s only in tests (MV-04).
  - `params` is `PmoveParams`, refreshed outside the tick when `CvarRegistry.version` changes.
  - `events` (step, jump, land) and the trace log are output only. No `PlayerState` fields are added, and the hull changes only in the pre-checks, at the tick's start origin.
  - Each tick ends with `snapOrigin` (fallback: the start origin), then `quantizePlayerState`.
- **Stuck rule (Q1):** the slide move stops only on an **allSolid** sweep: it zeroes vz, reports blocked and asserts in dev, since the snap keeps every start clear. A `startSolid` sweep that is not `allSolid` moves out of the brush and is accepted.
- **Ground surface (Q3):** ground is slick or nodamage when the hit plane's `SURF_*` bit **or** the hit brush's `CONTENTS_SLICK`/`CONTENTS_NODAMAGE` bit is set. Bevels keep flags 0, but `trace.contents` keeps the brush bits, so ramp crests work with no map format change.
- **Crouch-blocked:** crouched with the standing hull blocked at the origin, so no jump under a ceiling. Crouch-jumping in the open is allowed.
- **LAND value:** the downward speed at the start of the landing tick.
- **Landing clip:** when the ground trace turns an airborne player grounded, the velocity is clipped against the ground plane. Without it a fall that ended within `pm_groundTraceDist` of the floor, untouched by the slide sweep, kept its full vz, and the walk move's slope-following rescale turned it into horizontal speed (up to 690 u/s from a run-jump).
- **Ground settle:** after the move, a grounded player is moved down to the ground trace's end point before the snap. A walk along a slope rounds by the same vector every tick, and the accumulated drift otherwise lifted the player past the probe every 3–4 ticks (an air tick and a spurious LAND each time).
- **Step-down trace and ties:** the stepped path is traced back down by the raise plus `pm_groundTraceDist`, so it finds the floor at the start height. A stepped path within 1/16 u of the plain one (either way) is a tie: the plain origin, with whichever path's velocity kept more horizontal speed. Before this, a plain slide that touched a riser at a tick's end won with a velocity clipped to 0, and 7% (run) to 19% (walk) of stair approaches snagged to a stop.
- **Slope crests (M2 increment 4):** in the walk move the step-down trace also covers any rise of the stepped slide itself, so it reaches at least `pm_groundTraceDist` below the start height. A hull walking up a slope rides it inside the ε skin, so at the crest it meets the platform's riser a few hundredths of a unit below the platform top. The stepped path rose with the walk (3.8 u a tick on a 0.71 slope at the run cap), the old trace stopped above the platform, and the plain path's clip left the player stalled at 0.3 u/s of horizontal speed, popped 33 u into the air. MV-06 found it on `movement_lab`: before the fix 66–89% of start phases stalled at the crest (by slope and speed), after it none do. Air moves keep the old trace: there, reaching down further would pull a rising jump onto the ledge beside it.
- **Crest kick-off (accepted):** where the plain slide clears the riser lip instead (a few percent of start phases at the run cap on 0.71, none on 0.8; about a quarter at walk speed on 0.8), the walk reaches the platform still carrying the slope's vz, and the ground trace's kick-off rule (`docs/03` §4.10, vz > 0 and v·n > 10 against the flat platform) makes it airborne for one ballistic hop at the speed it had: up to 35 u and 35 ticks from 0.71 at the run cap, under 10 u at walk speed. It follows from the kick-off rule as specified (suppressing it would change that rule, so it stays open for a feel decision), and it depends on where a tick ends at the crest, so MV-06 allows it at the crest only (never on the incline, never gaining vz, at most one LAND).
- **Steep toes (accepted for now):** a hull whose feet are exactly on the floor (an anchor start, and a fresh spawn until D-027 raised it; a walk on flat ground never lifts it) meets the toe of a steep (non-walkable) wedge on the wedge's axial bevel, which the trace reports at the same fraction as the slope plane, and stops there as at a wall without touching the slope. A hull one ε above the floor (any player that has landed, D-017) is clipped onto the slope, slides back down and lands, and while forward is held repeats that jitter at the toe (about one LAND every 7–18 ticks). Walkable slopes are unaffected: the step-up carries both onto them. The match loop's spawn rests at floor + ε (D-027, M2 increment 9), so only anchor starts in tests have their feet exactly on the floor; MV-06 pins both behaviours so a change is noticed.
- **Steep crevices** (a V of non-walkable planes) can hold a player who can neither slide out nor jump. Accepted as base-movement behaviour; maps must avoid them, and a map-validation check is planned with the map pipeline.
- **Slide-move clip order:** as `docs/03` §4.8 step 4 says, the plane just hit is clipped against first, then every stored plane the result still moves into. Starting from the first stored plane instead would let the flat ground plane (which a level walk only grazes, so its clip changes nothing) use up the pass, and an acute corner would then not stop the move.
- **Design constants**, not cvars (the same code runs on client and server, and none is a feel knob):
  - same plane: normals' dot > 0.99;
  - a stored plane is cleared only when the velocity leaves it at more than 0.1 u/s;
  - a stepped path must get 1/16 u farther than the plain one;
  - a step event needs |Δz| ≥ 1/32 u.

  In the seeded random-input property run (`pmoveProperty.test.ts`), the step margins remove spurious "steps" (−2.5 u while falling past edges, 0.05 u on a slope) and leave the run's other tallies unchanged. Walking up a slope still tries the stepped path whenever a sweep grazes the slope; the 1/16 u margin is what keeps those from becoming step events.

**Consequences:**
- `docs/03` §3 states the contract and §4.8–§4.11 the rules above. The code is in `packages/shared/src/sim/pmove/` (`slideMove`, `stepSlideMove`, `ground`, `walk`, `debug`, `pmove`). It is tested in `packages/shared/test/sim/pmove/`, including a seeded 1e4-tick random-input property on slopes and rotated walls: never in solid, no consecutive previous-origin fallbacks.
- **Native ESM (M2 plan, risk 3):** pmove's move functions are too big for V8 to inline every call, and a double passed to a call that isn't inlined is boxed. So per-tick shared code passes no computed doubles across calls:
  - `accelerate(v, wishVel, kind, params, dt)` and `clipVelocity(out, v, n, params)` replace the increment-2 forms that took wishSpeed, coefficient and overclip;
  - `PmoveEvents.pushFrom` takes the event value from an array;
  - `angleVectors` gets sine and cosine from `sinCosU16` (same bits as `sinU16`/`cosU16`) through an out-array;
  - the slide move keeps its remaining time in a typed array.

  The native-ESM `pmove` workload allocates nothing. Rarely run code (a landing, a step) still boxes about 16 B per event until V8 optimizes it.
- **Bench:** `pnpm bench` times pmove on `movement_lab` against the `docs/10` §4.4 budget, at about 1.6–1.75 µs per player-tick with 0 GCs (`docs/10` §4.4).
- **Tests** for the landing, settle and step rules sweep their phases: drops onto flat ground from 8–120 u in 1/8 u steps never exceed the run cap; 300-tick walks up and down 0.71–0.99 slopes at run and walk speed have no air tick and no LAND; stair climbs from 192 start offsets in 1/32 u steps never drop below 90% of the cap.

### D-024 — Ladders and water (2026-10-06, accepted)
**Context:** M2 increment 5 adds crouch, water and ladder movement (`docs/03` §4.12–§4.14). The spec left open which of the two ladder markers M1 emits (the `SURF_LADDER` face flag or the 16 u LADDER volume, D-019, D-021) the movement reads, where the water samples sit, how a swimmer moves vertically and what happens with no input. M2 plan, "Spec decisions" (Q2, Q4) and "New tunables"; M2 design §3–§4.
**Decision:**
- **Ladders read only the face flag (Q2).** Contact is a horizontal sweep of the tick's hull, `pm_ladderReach` (2 u) along the yaw-only forward (pitch ignored), that hits a `SURF_LADDER` plane with dot(forward, −n) > `pm_ladderFacing` (0.5). Contact is refused while the velocity leaves the face faster than `LADDER_DETACH_SPEED` = 16 u/s (v·n, a design constant), so a jump-off does not re-attach, and on the ground unless forward is held.
- **Ladder move:** ground-term friction on the 3D speed (no water term, even in water) and `pm_accelerate` toward a wish of the forward axis on world z and the right axis along the face (the view right projected onto the face plane), at `pm_runSpeed` × `pm_ladderScale` (160 u/s), with no gravity and a slide move. A fresh jump press adds n × `pm_ladderJumpPush` (150 u/s), detaches at once and emits `jump`. At the top the probe misses once the hull clears the face, and an air move carries the player over the edge.
- **Greybox:** `ladder()` drops the 16 u LADDER volume and gives the flagged face the material `grey/ladder` (a rung texture for M2's renderer). `compiler.version` becomes 2 and all five maps are recompiled: every file carries the version, and the ladders of movement_lab and fall_tower lose their volumes. `CONTENTS_LADDER` stays reserved: `volume("LADDER")` still builds one, and movement ignores it.
- **Water samples (Q4):** `pointContents` at feet + 1, feet + 28 (the middle of the standing hull) and the eye, feet + 50 standing or feet + 36 crouched, the feet being the hull bottom; cumulative levels 1–3; `PMF_IN_WATER` at level ≥ 1. Design constants, not ESTIMATEs.
- **Swim move** at level ≥ 2: the water friction term on the 3D speed; forward and right along the 3D view vectors plus a vertical axis on world z, jump +127 and crouch −127 added to the cmd's up axis and clamped; command scale without the crouch factor, times `pm_swimScale`, and the summed wish capped at that speed (world z and a pitched forward are not orthogonal, so forward + jump looking up would otherwise reach √2 × 160); with no forward, right or vertical input the wish is straight down at `pm_waterSinkSpeed` (60 u/s); `pm_waterAccelerate`; no gravity; a step-slide, so a swimmer at the surface can step out over an edge up to `pm_stepSize` (movement_lab's pool is left that way, MV-17). No water-jump (M4).
- **Friction in water (clarifies `docs/03` §4.2):** the walk move adds the water term to its ground term with the same horizontal speed, so wading keeps the run, walk and crouch caps; the swim and ladder moves measure the 3D speed.
- **Crouch:** holding crouch sets `PMF_CROUCHED` and the crouched hull at once; on release a position test of the standing hull at the tick's start origin decides whether the player stands. No stamina cost until M4.
- **Pre-check order:** crouch, then water level, then ladder contact (`docs/03` §3 listed water first). The eye sample depends on the stance, and the ladder probe on the hull.

**Consequences:**
- `docs/03` §3, §4.2, §4.12–§4.14 state the rules; `docs/07` §3 the builder change and §4 that `mapc` must compile `tool/ladder` and `func_ladder` to flagged faces (M5).
- Code: `packages/shared/src/sim/pmove/{crouch,water,ladder}.ts`, dispatch in `pmove.ts` (ladder → swim → walk → air). Tests: shared unit tests (stand blocked, water levels, ladder facing threshold, detach, push-off), MV-03 (crouch cap and tunnel), MV-08, MV-17 and MV-18 on movement_lab, and a native-ESM `pmoveModes` allocation workload.
- `pnpm feel-report` (`packages/tools/src/reports/feelReport.ts`) prints the base metrics and writes `reports/feel.md`, git-ignored and byte-identical on every run.
- The pmove bench mix adds crouch and meets the pool and ladder anchors; its warm-up grows to 12500 ticks plus a scripted ladder climb per round, so the rarely run modes are optimized before the timed loop (0 GCs). The pre-checks cost about 0.7–0.9 µs per player-tick (`docs/10` §4.4), within the budget.
- The feel report also shows the D-017 snap bias: at the run cap the origin moves 320.625 u/s for a velocity of 320 (each 5.333 u step rounds to 171/32 u), so the runway takes 6.390 s against 6.400 s.
- Open for feel tuning, to decide with the user:
  - the ESTIMATEs above;
  - a jump at a ladder's foot with forward held pushes off the ladder rather than jumping (ladder dispatch comes first);
  - a ladder cannot be mounted from its top: walking back off the edge leaves the face faster than `LADDER_DETACH_SPEED`, so the player falls (options: refuse contact only for a while after a jump-off, skip the speed test while back is held, or skip it above the face's top edge);
  - crouching in the air cuts the air wish speed to `pm_runSpeed` × `pm_duckScale` (`docs/03` §4.1, §4.5 as written), which weakens air strafing on a crouch-jump and on every M4 power-slide approach; the Q3 lineage applies the crouch factor on the ground only.

### D-026 — Protocol v1 and transports (2026-10-06, accepted)
**Context:** M2 sends everything through a server, even offline (`docs/05` §2), so it needs a wire format before the match loop and the predictor (M2 increments 7–10). `docs/05` §3 named the messages and the INPUT and snapshot fields but not their bit widths, the message ids, how decoders fail (§3.2 said "throw → drop"), or what M2's snapshots hold. M2 plan, "Spec decisions"; M2 design §2 "Messages", §3. This entry covers the codec part (increment 7) and the transport part (increment 8).
**Decision (codecs):**
- **Bitstream:** `BitWriter`/`BitReader` over a preallocated `Uint8Array`, LSB-first, explicit widths 1–32, two's-complement signed values, f64 as raw bits. Neither throws: an overflow, a value its width can't carry or a short read sets a sticky error flag (this replaces "throw → drop" in `docs/05` §3.2; a throw would have to be caught on every packet, and a sticky flag needs one check per message).
- **Protocol v1** (`PROTOCOL_VERSION` = 1): one message per packet, a leading `u8` type (1 HELLO … 11 KICK; 0 is never a message), the layouts of `docs/05` §3.6. READY, PRINT and KICK are added to §3.3's list; LOADOUT, TEAM, CHAT, MAP and EVENTS stay for later milestones. Unreliable packets ≤ 1200 B, reliable messages ≤ 16384 B.
- **INPUT** carries 1–4 cmds newest first: the newest tick in full, older ones as a u8 offset back (strictly rising, never below tick 0). 55 B for four cmds.
- **SNAPSHOT in M2** is the `docs/05` §4.2 header plus a flags byte (starved, teleport) and the full local `PlayerState` (199 bits: origin 3 × i21 at 1/32 u, velocity 3 × i20 at 1/16 u/s, yaw and pitch u16, flags 10, groundEntity + 1 in 16, waterLevel 2, stamina 16), 42 B. `baselineTick` is always 0: delta snapshots are M3. The origin needs i21, not i20: ±16384 u is ±2^19 units, one more than i20 holds.
- **Validation:** decoders return false on a short read, a wrong type, a value the encoder never writes (origin past ±16384 u, velocity −2^19, pitch past ±16201, groundEntity past `ENTITY_WORLD`, ticks past `TICK_MAX`, an INPUT count outside 1–4 or cmds outside `sanitizeUserCmd`'s ranges, unknown snapshot flags, a non-zero baseline, PRINT level 3) or bits left after the message's last byte. The receiver drops the packet and counts a strike. The checks make the encoding canonical: a decoder that accepts a packet re-encodes it to the same bytes, and a decoded state is one `quantizePlayerState` leaves unchanged. Encoders refuse out-of-range fields with the same flag, so a sender bug never reaches the wire.
- **HELLO's first 3 B are frozen:** the type byte and protocolVersion u16 keep their place in every protocol version. The server reads a client's version with `peekHelloVersion` before it parses anything else, so it can answer a mismatch with a KICK that says why, whatever fields a newer HELLO adds. `decodeHello` parses the v1 layout and keeps any version.
- **Text:** short ASCII (u6 length, 7-bit printable) for the build hash, map name and cvar names; console text (u10 length, 8-bit Latin-1, printable plus tab and newline) for CMD, PRINT and KICK.
- INPUT, SNAPSHOT, PING and PONG encode and decode without allocating, refused packets included; text and cvar-block fields allocate (rare reliable messages). Decoders read every tick as two u16 halves and reject it past `TICK_MAX` before using it: a hostile u32 past 2^30 − 1 is not a small integer, and returning it from a reader call or storing it allocated a heap number on every such packet.

**Consequences:**
- Code: `packages/shared/src/net/{bitstream,protocol,messages,playerStateCodec}.ts`. `docs/05` §3.2–§3.4 and §4.1–§4.2 point at the new §3.6 layout table; `docs/06` §3 lists the files. A doc-golden test (`packages/tools/test/docs/protocol-docs.test.ts`) pins §3.6's type ids, state widths, sizes and the cvar hash seed to the code.
- Tests: bitstream widths, offsets, signed edges, overflow and short reads (`packages/shared/test/net/bitstream.test.ts`); NET-01 (`packages/shared/test/net/codecs.test.ts`): seeded round trips of every message, encoder and decoder rejections, every truncation, an extra byte and dirty padding refused, and fuzzing (1e4 random byte strings, every single-bit flip of messages up to 96 B and a seeded sample of about 768 bit flips of each longer one, random byte corruption) that never throws and only accepts packets its encoder takes back and re-encodes to themselves; per-message patched-field cases pin each decoder range check the fuzz can't reach. NET-01 is a shared unit test; its file is not named `net-01-*` because the naming guard then requires `pnpm test:net`, a stub until M2 increment 10, but its describe starts with `NET-01:` so `test:net` (`-t "^NET-"`) will select it.
- The native-ESM `codec` allocation workload (valid messages plus a hostile packet per message: random bytes behind an INPUT, SNAPSHOT or PONG type, and valid ones with a tick of 2^32 − 1) and `pnpm bench`'s codec part (`docs/10` §4.4): a snapshot round trip takes about 0.7 µs against the 30 µs budget, a four-cmd INPUT about 1.3 µs, 0 GCs.

**Decision (transports, increment 8):**
- **Interface** (`docs/05` §3.1): `sendUnreliable(d, len)` and `sendReliable(d, len)` take a `Uint8Array` plus its used length, so a sender encodes into one reused buffer; the transport copies what it keeps. `poll()` delivers queued messages to the `onMessage(d, len, reliable)` callback at fixed points of the caller's loop, never from inside a send, and `d` is valid only during the callback. This replaces the `ArrayBuffer` form, which would need a fresh buffer per packet. Unreliable packets are at most 1200 B and reliable ones 16384 B; an empty, oversized or out-of-buffer send is a sender bug, asserted in dev builds and dropped.
- **Reliable is ordered and lossless** on every transport (NetSim included); unreliable may lose, duplicate or reorder.
- **Close and `onClose`**, an addition to the M2 design's interface: after `close(reason)` that side drops its sends and delivers nothing more, while the other side still receives what was sent before and then gets `onClose(reason)` from its `poll()`, like a socket's graceful close. The server can send KICK and close at once, and a client learns that the Worker ended the session. `isOpen()` reports the state.
- **`TransportStats`** is one live object per transport: packets and bytes sent by its user and delivered to its callback, plus NetSim's lost, duplicated and reordered counts.
- **`createLoopbackPair()`**: two in-memory ends; a send copies into a pooled slot of the peer's inbox, and the peer's `poll()` drains the messages queued when it started, both channels interleaved in send order as on one socket. Slots start large enough for any unreliable packet and the pool doubles only when more packets are in flight than ever before, so steady traffic allocates nothing (a reliable message past 1200 B grows its slot once). `PortTransport` (increment 10, wired in increment 11) allocates one transferred `ArrayBuffer` per packet and the receiver's view of it, only at the `postMessage` boundary; its inbox is a ring of reused slots.

**Consequences (transports):**
- Code: `packages/shared/src/net/{transport,packetQueue}.ts`; `docs/05` §2 and §3.1, `docs/06` §3–§4 and the `docs/09` M2 scope name `createLoopbackPair` and `PortTransport` instead of a postMessage `LoopbackTransport`.
- Tests: `packages/shared/test/net/transport.test.ts` (send-order delivery on poll only, copy on send, counters, messages sent from a callback wait for the next poll, refused lengths (including fractional and NaN), a poll from inside a callback, pooling: no new slot or delivered buffer after warm-up, and close: drain then `onClose`, drops both ways, close from a callback); the native-ESM `transport` workload (a raw pair and a NetSim-wrapped pair on `bad-250-loss5`) runs with 0 GCs.

### D-027 — Replicated cvars (2026-10-06, accepted)
**Context:** prediction must use the server's tunables (`docs/05` §3.5), and a live `set pm_gravity 400` must not rubber-band. §3.5 said the cvars are sent "versioned by a hash" but not how they are encoded, which hash, or what a client does with a block. M2 plan, "Spec decisions"; M2 design §2 "Replicated cvar block", §3. This entry covers the block encoding and hash (increment 7), the server's match loop (increment 9) and the client's tick-switched parameters (increment 10).
**Decision (block and hash):**
- **Encoding:** every `REPLICATED` cvar in ascending lowercase-name order (the `CvarRegistry.replicated()` order), no duplicates: count u10, then per entry the name (u6 length + 7-bit ASCII), the kind (u2: int, float, bool, string) and the value: i32; the f64's raw bits, so a float arrives as the same double (finite, never −0, as the registry normalizes it); 1 bit; or a u8 length + 7-bit printable ASCII. The decoder requires that canonical form, so a block's bytes identify its values.
- **Hash:** `murmur3Bytes` over the block encoded alone from bit 0, zero-padded to a byte, seed `0x63766172` ("cvar"). It does not depend on registration order or on non-replicated cvars. CVARS carries all 32 bits (the decoder rejects a block whose hash differs), snapshots the low 16. The M2 movement defaults hash to `0x11df56b6` (a golden test; adding or changing a replicated cvar changes it).
- **Wire limits at the registry:** a `REPLICATED` cvar's name is at most 63 chars and a `REPLICATED` string's value printable 7-bit ASCII of at most 255 chars. Registration throws otherwise, and `set`/`setFromString` refuse such a value with a `type` error, so the block is always encodable: a console value can't stop WELCOME and CVARS or put the −1 "unencodable" result into snapshots (`cvarHash16` asserts on it).
- **Apply is all or nothing:** the block must list exactly the client registry's `REPLICATED` cvars, spelled as registered, with the same types and values within their min/max; unknown, non-replicated or missing cvars, wrong kinds and out-of-range values reject it unchanged. A client with another cvar set is another build, and a clamped value would mispredict.
- **The server's CHEAT and LATCH rules are the only ones:** it applied them before its values changed, so the mirror stores CHEAT and LATCH values as sent (`CvarRegistry.setReplicated`, which also drops a pending latched value), whatever the client's own cheat setting. A client-local gate would make it refuse every later block and predict with stale values. A latched server value changes when the server applies it (map restart) and reaches clients in the CVARS that follows, like any other change.

**Consequences:**
- Code: `packages/shared/src/net/cvarBlock.ts` (`captureCvarBlock`, `encodeCvarBlock`, `decodeCvarBlock`, `cvarBlockHash`, `registryCvarHash`, `cvarHash16`, `applyCvarBlock`); WELCOME and CVARS carry the block (`docs/05` §3.5–§3.6). `docs/06` §3 moves the block from `cvars/` to `net/`.
- Tests (`packages/shared/test/net/cvarBlock.test.ts`): a golden byte layout and hash for a four-kind registry (checked against an independent reference encoder when written), the golden hash of the M2 movement defaults, order independence over shuffled registrations, exact floats (0.1 + 0.2, the smallest denormal, −MAX_VALUE), seeded random round trips, canonical-form rejections, every apply rejection leaving the registry's version and hash unchanged, CHEAT and LATCH values taken from the server with the mirror's cheats off, and the registry's wire limits on names and replicated strings (`packages/shared/test/cvars.test.ts`).

**Decision (server match loop, increment 9):**
- **Environment-agnostic match code** (`packages/server/src/match/`, exported alone as `@game/server`): no clock, timer, console or I/O of its own. A `LoopHost { now(), schedule(cb, ms), log(level, msg) }` brings them (`performance.now` and `setTimeout` in the Worker, a Node host in M3), and the transports bring the clients. `tsconfig.match.json` (ES2023, `types: []`) and a purity guard (no `Date`, `performance`, `Math.random`, timers, `process`, imports beyond `@game/shared` and its own modules) keep it runnable in both. This replaces `docs/05` §8.1's `process.hrtime.bigint()`, which only Node has.
- **Loop:** re-armed through `schedule` after every wake, never an interval. A wake runs the ticks due since the loop started (tick k is due at start + k × 1000 / 60 ms; minus the ticks already run or dropped), not a sum of wake intervals, so rounding never drifts. The count of due ticks and the re-arm delay come from that one expression: a floor of elapsed × 60 / 1000 alone comes out one short at some ticks, so a host that wakes exactly when asked (a simulated clock) would find nothing due and re-arm with 0 ms forever. At most 5 per wake; more due are dropped with one warning, leaving less than a tick owed. An early wake runs nothing and re-arms. A restart while a wake is pending keeps one wake chain. A host whose timer truncates to whole milliseconds rounds the delay up.
- **Tick order** (`docs/05` §8.1): poll every transport in client-id order and handle HELLO, READY, INPUT, PING and CMD; if the registry's `version` moved, refresh the pmove parameters and, when the replicated block's hash changed, broadcast CVARS with `effectiveTick` = this tick; per active client in id order take its cmd for the tick or repeat its last with attack cleared and the tick set (starved), sanitize, pmove; then per active client a SNAPSHOT with `lastProcessedCmdTick` = the tick, `inputBufferHealth` = newest received − the tick (clamped to i8), the low 16 bits of the block hash and the starved or teleport flag. Each message must arrive on its own channel (INPUT and PING unreliable, the rest reliable); a packet that doesn't decode, comes on the other channel or doesn't fit the session's state (a second HELLO or READY, a server-to-client type) is dropped with a strike. M2 only counts strikes; when they lead to a kick is left to M3.
- **Input queue:** 64 slots indexed `tick & 63`, each remembering its tick; duplicates, cmds for ticks already simulated and cmds 64 or more ticks past the next one are dropped and counted. A slot keeps its tick after its cmd is simulated, so the redundant copies that arrive afterwards count as duplicates and `late` counts only cmds for ticks simulated without them (starved), the case that costs the client a correction.
- **Input buffer health** is the newest cmd tick received, accepted or not, minus the tick simulated: a client whose cmds all arrive two ticks late reads −2, not a value sinking to −128. A received tick counts at most the horizon past the next tick, so a hostile tick cannot pin it. At READY it starts at the spawn tick (the neutral spawn cmd stands for the client's last cmd), so the spawn snapshot reads 0 and each tick before the first cmd arrives one less, whatever the absolute tick; `docs/05` §8.2. The horizon and the catch-up cap are design constants, as is `MATCH_MAX_CLIENTS` = 64 (client ids 0–63, lowest free first; WELCOME's u8 holds them).
- **Handshake:** another protocol version (read from HELLO's frozen first 3 B) or another build hash gets a KICK saying why, then the transport closes. WELCOME and PONG carry the newest tick simulated. READY spawns at once (no spectator step in M2) at the map's first `info_player_start`: at rest, the entity's yaw through `degreesToU16`, pitch 0, stamina 100 points (`staminaMax` at health 100, no vest; docs/03 §5.2, FACT), grounded when the ground trace finds walkable ground.
- **The spawn rests at floor + ε:** the entity's origin raised by `TRACE_EPSILON` to the D-017 rest height (floor + 1/32 u). With its feet exactly on the floor a fresh spawn met a steep wedge's toe as a wall, while any player that has landed is clipped onto it (D-023, "Steep toes", found in increment 4); raising it makes a spawn behave like every later moment of play. Map entities keep their feet-on-floor origins (`docs/07` §3).
- **The spawn state is the player's state at the tick that handled READY**, sent in that tick's snapshot with the teleport flag; simulation starts the next tick. The repeat for a starved tick starts as a neutral cmd with the spawn yaw, the same cmd the client predicts with until its own cmds arrive (M2 design §2, "Client clock"), so startup needs no correction.
- **Known limit, for M3:** the teleport flag rides only the spawn tick's snapshot, on the unreliable channel. M2 is unaffected (its only teleport is the first spawn, and the client adopts its first snapshot whole), but respawns and teleporters must not depend on one datagram: M3 keeps the flag set until INPUT's `lastSnapshotTick` acknowledges the spawn tick, or makes it a counter. M3 also adds the 5 s no-packet timeout (`docs/05` §2) with the Node transports; M2's match closes a session only on a kick or a transport close.
- **Replicated cvars from a console:** a client's `set`, `reset` or `toggle` on a `REPLICATED` cvar becomes a CMD (the client side lands with the console, increment 12). The server applies it to its registry with its own CHEAT and LATCH rules, replies with PRINT, and the next step broadcasts CVARS. Changing cvars needs the session's admin flag; the Worker's single client has it, and M3 decides authorization on the Node server. Non-admins get a PRINT error and nothing changes. `CMD cvars`, open to all, resends the current block with the tick it took effect. WELCOME and resends carry the block captured at the last change, not the registry's live values, so a value changed earlier in the same poll reaches clients only with its effective tick.

**Consequences (server match loop):**
- Code: `packages/server/src/{index.ts, match/{host,loop,match,session,inputQueue,commands}.ts}`, `packages/server/tsconfig.match.json` (in the server's `typecheck`), the server package's `exports`; tools depends on `@game/server`. `docs/05` §2, §3.5 and §8.1, `docs/06` §3 and §6, `docs/03` §4.10's steep-toe note and `docs/07` §3 describe it.
- Tests: `packages/server/test/match/` — the loop (exactly 60 ticks per simulated second for 10 s of wakes 4 ms early to 12 ms late, 600 ticks in 10 s of wakes exactly on time from six start offsets, the wake delay, a 1 s stall running 5 ticks and logging once, a clock stepping back, stop, a restart with a wake pending, an idempotent start, busy time), the input queue rules and counters (lossless redundancy counts no late cmd; the newest tick received, late or capped), the commands (tokens, admin gate, replicated-only, reset, toggle, resend, cheat and latch replies), and the match over loopback pairs (WELCOME fields including the map hash and a block a mirror applies to the same hash; client ids, kept sorted, and handling in id order; version, build and malformed-HELLO kicks; PONG; strikes, including READY and CMD before HELLO, INPUT on the reliable channel and packets after a kick in the same poll; the READY spawn at floor + ε, grounded, with the teleport flag, and the spawn yaw on fall_tower; a join after 200 ticks; server states equal to a local pmove of the same cmds for 120 ticks; the starved repeat with attack cleared; snapshot fields, health 0 at spawn counting down and −2 for cmds two ticks late; an admin's `set pm_gravity 400` changing the value, the params and the hash and broadcasting CVARS at the tick, with an airborne player's effective tick simulated on the new gravity; CVARS skipping clients before HELLO; a non-admin's refused; 6000 seeded random packets across every session state without a throw). `packages/tools/test/guards/match-purity.test.ts` and the tsconfig guard; the native-ESM `match` workload runs a steady-state match tick with 0 GCs.

**Decision (client, increment 10):**
- **Parameters switch by tick.** The client keeps a mirror registry (`registerPmoveCvars` plus its own `ARCHIVE` cvars). WELCOME's block is applied to it (all or nothing) and becomes the parameters in force, with the block's hash. A CVARS block is applied to the mirror and loaded as a pending parameter set for ticks from `effectiveTick` on; the predictor re-simulates at once from the newest snapshot, each tick with the set in force at that tick, and promotes the pending set when a snapshot at or past `effectiveTick` carries its hash (at once when the newest snapshot is already past it). A lossless link sees 0 corrections from a live `set pm_gravity 400` (a NET-03 variant).
- **A snapshot's cvar hash is checked before its state:** when it differs from the hash the client expects for that tick (the block is still in flight on the reliable channel, which may lag the unreliable one under NetSim), the state is adopted and re-simulated and counted as a parameter resync, not a correction. If that lasts 1 s (a design constant) the client sends `CMD cvars`, which resends the block with its effective tick.
- **One pending set:** a second CVARS before the first takes effect replaces it; the ticks between the two effective ticks then resync (counted, not corrections). A refused block (another build) disconnects with the reason.
- The client's console path (a `set` on a replicated cvar becomes CMD) lands with the console in increment 12; `ClientSim.sendCommand` is the hook it uses.

**Consequences (client):**
- Code: `packages/client/src/net/{predictor,clientSim,connection}.ts`; `docs/05` §3.5 describes the client side.
- Tests: `packages/client/test/net/predictor.test.ts` (pending parameters switching at the effective tick with an airborne player, promotion, a block effective before the newest snapshot, a hash mismatch resyncing without a correction); NET-03's live `set pm_gravity 400` variant (`packages/tools/test/net/net-03-prediction-parity.test.ts`), sent mid-jump so the ticks already predicted on the old gravity must be re-simulated: their first predictions differ from the server, yet 0 corrections, 0 parameter resyncs, server and prediction equal on every tick, the mirror and the server both at 400; a lost CVARS (`client-paths.test.ts`): parameter resyncs and no corrections, `CMD cvars` after 1 s, back in sync.

### D-028 — M2 clock and the net simulator (2026-10-06, accepted)
**Context:** NET-03/04 and the manual `net_profile wan-150-loss2` check need impaired links that are reproducible. `docs/05` §13 and `docs/10` §3 both listed the profiles but disagreed (§13 had no reorder for `wan-150-loss2`, §10 had 0.5%), and neither said how delay, jitter, loss, duplication and reordering combine, so jitter could reorder packets on its own. M2 plan, "Spec decisions"; M2 design §2 "Transport", §3. This entry covers the simulator (increment 8) and the client clock (increment 10: prediction in server-tick time, handshake lead, step re-anchoring).
**Decision (net simulator):**
- **Profiles:** `docs/10` §3 is the canonical table and `docs/05` §13 repeats it with Dup and Reorder columns (`wan-150-loss2` reorders 0.5%). `NET_PROFILES` and `findNetProfile` (`shared/src/net/profiles.ts`) implement it, frozen. Profiles are test conditions, not tunables, so they are not cvars.
- **`NetSimTransport(inner, profile, clock, seed, wake?)`** wraps the client's end and delays both directions by the one-way delay, so the round trip is twice it. Time is milliseconds from the injected monotonic `clock`; the draws come from Mulberry32 seeded with `seed`, a fixed count per packet (five per unreliable, one per reliable), so one seed and one send/poll schedule give one delivery schedule.
- **Unreliable packets:** independent draws for loss, reorder and duplication. Jitter is uniform within ±jitter. A kept packet is due at max(previous due, now + max(0, delay ± jitter)) in its direction, so jitter alone never reorders. A reordered packet is held a further 2 × jitter + one tick (16.7 ms; a design constant) past that and does not move the FIFO due, so the packets behind it overtake it. A duplicate draws its own jitter and follows its original through the FIFO rule.
- **Reliable packets** use the same delay and jitter, in order, never lost or duplicated. A close in either direction is queued like a reliable packet, behind everything sent before it (a reordered unreliable packet still held then is lost).
- **Pumping:** a send and `poll()` forward every due outbound packet to the inner transport (`pump()` does it alone); `wake(at)` reports each new earliest outbound due time once, so a browser host can arm a timer to pump between frames; `pump()` re-reports a front still pending, so a timer that fires early (`setTimeout` truncates a fractional delay) re-arms instead of stranding the packet. `poll()` takes the inner transport's arrivals, stamps them with the current time and delivers the due ones. `lan` therefore behaves like the bare transport.
- **`setProfile`** (the `net_profile` command) applies to packets sent or arriving afterwards; packets in flight keep their due times and new ones still queue behind them. Out-of-range values (negative or non-finite times, probabilities outside 0..1) are refused, asserted in dev builds.
- **Close is graceful**, so NetSim keeps the `docs/05` §3.1 close contract under every profile: after `close()` the simulator drops later sends and the arrivals it holds, still forwards the outbound packets it holds when due (through `pump()`, `poll()` or a wake), and closes the inner transport when its close comes due. A bandwidth cap (`docs/05` §3.1) is not simulated in M2.
- **Allocation:** in-flight packets are pooled copies (`PacketQueue`), and due times and draws stay in typed arrays (`Mulberry32.fillFloats`), so no fractional double crosses a call boundary per packet: 0 GCs under native ES modules. The host's `clock` and `wake` callbacks are the exception they cannot avoid (a fractional `performance.now()` is boxed when returned); the tests use a fake clock.

**Consequences (net simulator):**
- Code: `packages/shared/src/net/{netsim,profiles}.ts`, `Mulberry32.fillFloats`; `docs/05` §3.1 and §13, `docs/06` §3, `docs/10` §3.
- Tests (`packages/shared/test/net/netsim.test.ts`, fake clock): `lan` passes through in the same step; delay within ±jitter, with the jitter range used, on `wan-50`, `wan-100-loss1` and `wan-150-loss2` in both directions; FIFO order under ±40 ms jitter at 1000 packets/s without reorder; loss, duplication and reorder counts within 5σ of the binomial over 20,000 packets on `bad-250-loss5`, with each id delivered once or twice and overtaken packets bounded by the reorder count; the exact reorder hold; reliable packets all delivered in order both ways; identical schedules for a seed and different ones for another; `setProfile` mid-run; out-of-range profiles refused (and a refused first profile leaves it on `lan`, reported as such, when asserts are off); counters for sent and delivered packets and bytes; duplicates drawing their own jitter; the reorder hold with jitter past the delay; pumping only on wakes delivers on time, one wake per new front, and an early pump re-arms; a graceful close on `lan`, `wan-50` and `bad-250-loss5` (reliable messages sent before it arrive, then the close) and a drain driven by wakes alone, and the peer's close delayed behind its reliable messages. The native-ESM `transport` workload includes a wake callback and pumps between polls. `packages/tools/test/docs/net-profiles-docs.test.ts` pins `NET_PROFILES` to the `docs/10` §3 and `docs/05` §13 tables.

**Decision (client clock, increment 10):**
- **Prediction runs in server-tick space:** the client's tick T is the server's tick T, run ahead of the server by the round trip plus an input buffer, so the cmd for T reaches the server just before it simulates T. There is no separate client clock to convert.
- **Handshake:** from WELCOME the client pings every 50 ms (a lost ping is replaced, not waited for) until 5 pongs are back; their median is the RTT and only then is READY sent. At the first snapshot A (the spawn, adopted whole) the client jumps to tick A + ceil(RTT / tick) + `cl_inputBuffer` (2), capped at 64 (half the rings). The ticks between are filled with **neutral cmds** (no move, the spawn's angles), predicted and sent at once; the server repeats that same neutral cmd until the client's own arrive (D-027), so the start costs no correction, and starvation before the end of that fill is expected and not counted.
- **Re-anchoring in steps:** a ping a second feeds EWMAs of the RTT and its jitter (weight 1/8) for the netgraph. Each snapshot's `inputBufferHealth` feeds an EWMA (weight 1/30, about 30 snapshots). Below target − 1.5 for 0.5 s the client fast-forwards k = round(target − EWMA) ticks, at most 5, predicting and sending them that frame; above target + 3 for 1 s it holds k = round(EWMA − target) tick periods, at most 30. After a step, snapshots up to the tick the step's effect reaches are ignored and the EWMA moves by k at once, so one shortfall makes one step. Each step counts as a clock adjustment. The render offset hides a fast-forward's skip; a hold pauses the prediction for k ticks, so the drawn player briefly slows. **Smooth time dilation (±3%, `docs/05` §8.2) is NET-07 in M3.**
- **The client's accumulator** runs at most 5 prediction ticks per frame and carries what a longer frame owes into the next frames. Unlike the server loop, which is the time reference and may drop time, the client's tick follows the server's clock: dropped time would be lead lost, with the server starving until a fast-forward (a 120 ms hitch on `wan-100-loss1` cost 20 corrections that way, 5 with the carry). Only a debt past 64 ticks is dropped; the snapshots then hard-resync. Its fraction is the interpolation weight, held in 0–1 during a hold.
- **Lead cap while snapshots are missing:** the prediction stops 64 ticks past the newest snapshot (the server's input horizon, half the rings), so a server or link stall neither runs it out of the rings nor past the cmds the server can queue; when the server resumes it simulates the cmds the client predicted, and holds bring the lead back.
- **Handshake pings** wait in 64 slots, so the handshake completes at round trips up to 3.2 s (at 16 slots it never finished past 800 ms). A handshake timeout comes with the session timeouts in M3 (`docs/05` §2).
- **Hard resync:** a snapshot for a tick the rings no longer hold (more than 127 behind the newest prediction) or not yet predicted is adopted as the newest tick and the clock re-anchors from it, filling with the last cmd, attack cleared. A backlog of snapshots after a stall is one hard resync: the client re-anchors once, after the poll, from the newest, sending one INPUT per fill tick, and a clock step asked for by an earlier snapshot of that poll is dropped (it measured the old anchor).
- **Known limits until NET-07 (M3):** the step clock watches the mean buffer health, so below about 20 fps, where cmds leave in bursts of several ticks, the low point of each burst can starve while the mean stays inside the band (wan-50 at 15 fps: about 10 corrections a second); and on `lan`, where the lead is 3 ticks, a frame gap longer than the lead (about 50 ms) is a hard resync rather than a catch-up. The ticks it refills were already simulated by the server with its starved repeat, so the outcome is the same, only counted differently. The adaptive buffer target of `docs/05` §8.2 and smooth dilation address both.
- The thresholds, windows, weights and caps are design constants; the target `cl_inputBuffer`, the smoothing time `cl_correctionSmoothMs` and the snap distance `cl_teleportDist` are client `ARCHIVE` cvars (`docs/06` §7), never replicated.
- **Allocation:** the frame, prediction, reconciliation (re-simulation and the correction log, which keeps states and builds its diff only when read) and the render offset allocate nothing; time is read once per frame from the injected clock into a typed array the clock, stats and offset share, so no fractional double crosses a call per frame. The injected clock may box its one double per frame, as NetSim's does.

**Consequences (client clock):**
- Code: `packages/client/src/net/{clock,clientSim,smoothing,stats,cvars}.ts` (exported as `@game/client/net`, checked by `tsconfig.net.json` and the client-net purity guard); `docs/05` §1.3, §5 and §8.2–§8.3, `docs/06` §3 and §7.
- Tests: `packages/client/test/net/clock.test.ts` (median, lead, ping spacing, the EWMA, a fast-forward after 0.5 s below and its cap, a hold after 1 s above, nothing inside the band); NET-03 (0 corrections and 0 starved cmds after startup on loopback and `wan-50`); NET-04 M2 basic on every profile, each run also checking that every snapshot the client reconciled with left its prediction equal to the server's recorded state; a round-trip step from `wan-50` to `wan-150-loss2` and back to `lan` that fast-forwards, then holds, with the lead measured against the server's tick; 250 ms and 120 ms frame hitches caught up without lost lead (`packages/tools/test/net/net-04-reconciliation.test.ts`); `packages/tools/test/net/client-paths.test.ts` (a 20 u correction carried in the render offset and gone after `cl_correctionSmoothMs`, snaps past `cl_teleportDist` and on the teleport flag, one hard resync after a 3 s stall with the fill's attack cleared and no burst, the per-frame tick cap, the 64-tick lead cap through a server stall and the holds after it, a step dropped by a hard resync in the same poll); long-RTT handshakes in `clock.test.ts`; the native-ESM `predict` workload (real `ClientSim` and `Match`; inputs dropped every 256 ticks, their delay switched between 0 and 10 ticks every 1200 and client frames skipped for 8 ticks every 2048, so corrections, clock steps and hard resyncs all run) with 0 GCs.
