# 10 — Testing & Performance

> Claude Code works best with a **verification loop**: a check it can run that proves the work is done. This doc defines those checks.

The viewport is small on purpose: SwiftShader's frame rate falls with the pixel count (about 57–60 fps at 320x180, 30 at 640x360, 18–20 at 960x540, 11 at 1280x720 on a 4-core host), and a slow host costs starved cmds and hard resyncs while the clock learns its frame rhythm (D-028's adaptive input buffer: at 18 fps one or two resyncs in the first 2 s, then about one in 10 s (after a 70–130 ms frame), 3–4 starved cmds and no correction in 13 s; at 11 fps, frames at the 83 ms per-frame tick cap, it keeps resyncing), so a zero-corrections check would pass or fail by timing. **Prediction health** between two readings: no misprediction, always (NET-03): every correction must be on a snapshot the server flagged starved (`starvedCorrections`, the client's `STAT_STARVED_CORRECTIONS`). Hard resyncs, starved cmds and those corrections are judged against frame timing, which the autotest status reports (`longFrames`: frames that came more than `cl_inputBuffer` ticks, 33 ms, after the previous one; `lateResyncs`: hard resyncs in such frames; `maxFrameMs`: the longest gap since the last report; `linkGaps`: frames that ended a gap in the snapshot stream longer than `cl_inputBuffer` ticks plus their own frame gap (50 ms at 60 fps) by taking a burst of two or more snapshots with none lost, the trace of a link that held them, while a gap a lost snapshot leaves ends in a tick jump and does not count; `starvedAfterGap` and `starvedCorrectionsAfterGap`: the starved flags and starved corrections taken by such a frame or within the gap's length plus the round trip and twice the input buffer after it; `maxSnapGapMs` and `peakSnapGapMs`: the longest snapshot gap since the last report and since the start; `lastLinkGap`: the last one's length and page time; `lastStarve`: at the last starved flag, the prediction's lead over the snapshot, the clock's low edge and mean input buffer health, the frame gap, the snapshot gap and the round trip; counted allocation-free in `Game.frame`): on `lan` the lead is 3–4 ticks, of which the input buffer is the slack and the rest covers the round trip (the Worker answers on its tick), so one longer gap sends cmds late and the server repeats one; the client is then corrected on that starved snapshot or, past the lead, hard-resyncs, by design (D-028); a second shallow resync within 1.5 s grows the lead by its depth plus `cl_inputBuffer`, and dips that recur grow it too, so gaps cost this once or twice, not on every repeat (before the adaptive buffer, in 6 runs with 2 of 4 cores busy, the 13 resyncs once moving came in frames 44–78 ms long; idle, one run in 10 had a starved correction after two long frames). So every hard resync must come in such a long frame, bar one on-time resync before the bot moves, and in a window with no long frame every starved cmd and starved correction must be one counted right after a link gap, and only in the WebSocket cases (`connect.e2e.ts`): the Worker cases (`smoke.e2e.ts`, a `MessageChannel` with no network process) stay strict, so a starve there with frames on time fails. A stall of the server's host does not starve: the match loop yields on a wake a tick or more late, so its catch-up ticks run after the input that arrived meanwhile (D-027; before that, a 37–117 ms stall of the Node server on a busy host starved 2 cmds with no client frame over 32 ms). The e2e cannot tell such a stall from a link stall (both end in a burst), so `pnpm test:long` holds the real Node server to it (`server-stall.long.ts`). A stall of the browser's network process does starve, as a real link's would: on a busy host it held 8 INPUTs sent at 60 fps for 60–120 ms (they reached the Node server together) and the snapshots 35–50 ms, with every frame on time and the server ticking; the snapshot gap it leaves is the page's only sign of it (D-028). The failure messages carry the window's link gaps, the snapshot gaps of both readings and the peak, the last link gap and `lastStarve`, so a starve with frames on time tells a link stall from a clock edge (D-028's low edge or adaptive lead). Each check first asserts at most half the frames long (the share where the mean frame reaches the input buffer, about 30 fps) and fails with "host too slow" otherwise; it is the only host gate, since each frame is judged by its own gap. The message gives the fps (frames over the page clock between the two reports, `statusAt`). Under 2 busy cores of 4 the fps fell to 31–39 and up to 25 % of the frames were long with the prediction healthy, which an earlier 40 fps and a quarter-long gate failed; a GitHub runner gave 27 fps with 41 % long frames and the prediction healthy, which a 30 fps floor failed. The e2e project runs after the vectors (`sequence.groupOrder`), so in CI the smoke test does not share the runner with the Firefox and WebKit runs. This is the canonical table (D-028): `NET_PROFILES` (`packages/shared/src/net/profiles.ts`) implements it and `docs/05` §13 repeats it with the simulator's rules; a doc-golden test (`packages/tools/test/docs/net-profiles-docs.test.ts`) keeps the three equal. ## 4. Performance budgets (requirements)

### 4.1 Server (Node, per match, 16 players, 60 Hz)

| Metric | Budget |
|---|---|
| Tick time p50 / p99 | ≤ 1.5 ms / ≤ 4 ms |
| GC pause (max) | ≤ 8 ms |
| Memory per match | ≤ 150 MB |
| Snapshot build per client | ≤ 50 µs |

### 4.2 Network (per client, 16 players)

| Metric | Budget |
|---|---|
| Down | ≤ 32 KB/s average, ≤ 48 KB/s peak |
| Up | ≤ 8 KB/s |
| Snapshot size | ≤ 1100 B (datagram-safe) |

### 4.3 Client

| Metric | Budget |
|---|---|
| Frame rate | ≥ 144 fps on a mid-range desktop GPU at 1080p "high"; ≥ 60 fps on integrated graphics at 1080p "low" |
| CPU per frame (game logic + interpolation + HUD) | ≤ 2 ms |
| Render submission | ≤ 4 ms |
| Draw calls | ≤ 300 typical scene |
| GC | no per-frame allocations in steady state (verify with the heap profiler; allocation-rate check in dev builds; `Game.frame` is guarded natively since M2, §4.4 allocation guards) |
| Input-to-photon | camera rotation applied the same frame as mouse input |
| Startup | first-match download ≤ 30 MB; main menu interactive ≤ 3 s on broadband (cached ≤ 1 s) |

### 4.4 Sim microbenchmarks

| Op | Target |
|---|---|
| `traceBox` on `movement_lab` | ≤ 1 µs average |
| `pmove` per player-tick (all mechanics) | ≤ 5 µs |
| Lag-comp rewind + hitscan vs. 16 players | ≤ 30 µs per shot |
| Codec encode/decode of a typical snapshot | ≤ 30 µs |

Budgets are checked by `perf-auditor` before closing a milestone. A regression > 20% needs a decision-log entry.

**How `pnpm bench` measures the trace** (`packages/tools/bench/trace.bench.ts`, since M1):
- **Workload:** `content/maps/movement_lab.cmap`, decoded and built as the game loads it. A seeded Mulberry32 draws 4096 cases per category before the clock runs, into typed arrays. Every case is built from a clear 1/32 u grid spot (`snapOrigin`) on the ground beside a random brush, for 60% of moves swept against a wall, step or slope first, with the standing or crouched hull. Categories, weighted by our ESTIMATE of one pmove player-tick (`docs/03` §3): hull moves ≤ 12 u (3), 0.25 u ground probes (2), 18 u step-up and step-down traces (2) and snap position tests (1; a position test is the zero-length box trace). Long rays (1024–8192 u) are timed but kept out of the average.
- **Timing:** 1e5 warm-up calls per category, in 100 short rounds so the loops are optimized as whole functions (a loop only ever optimized on-stack can box its doubles and allocate), then 1e6 timed calls per category with `process.hrtime.bigint()`. Results feed a printed sink. A `PerformanceObserver` counts GC events inside the timed loops: anything above 0 means a query allocates.
- **Report:** ns/op, BVH nodes and brushes tested per call, blocked share and GCs per category, then the weighted box-trace average against the 1 µs budget with PASS/FAIL. The exit code is 0 unless `--strict` is given and the budget or the GC count is missed. `--calls` and `--warmup` change the counts.
- **M1 result** (Node 22.22, Intel Xeon @ 2.10 GHz cloud VM, 3 runs): weighted average 238–338 ns, about a third of the budget (moves 310–359, ground probes 195–369, step traces 211–335, position tests 161–225, rays 507–605 ns; about 20 of 133 BVH nodes and 1.7 brushes tested per move), 0 GCs. Re-run on the reference machines in §5. On the M2 cloud VM (Intel Xeon @ 2.80 GHz, M2 increment 6, 4 runs): 351–410 ns, 0 GCs, with pmove at 2.17–2.46 µs per player-tick on the same runs (below).
**How `pnpm bench` measures pmove** (`packages/tools/bench/pmove.bench.ts`, since M2 increment 3):
- **Workload:** 16 players on `movement_lab` (a full match), each starting at `info_player_start` or one of the course anchors and moved to the next one every 600 ticks, so the mix keeps meeting steps, stairs, slopes and walls. A seeded Mulberry32 draws 4096 ticks of sticky input before the clock runs: a new choice every 6–60 ticks, about 70% running forward, strafes, back-pedalling, walk, crouch (since M2 increment 5), held and re-pressed jumps, turning up to ±400 u16 a tick and looking up and down. The anchors include the pool and the ladder, so the mix swims (about 10% of player-ticks) and, rarely, climbs. Each player reads the table at its own offset. Events are collected as on the server; the trace log is off.
- **Timing:** 12500 warm-up ticks in 100 short rounds, each followed by one scripted 90-tick ladder climb from `ladder_base` (random input reaches the ladder in only about 0.2% of player-ticks, too rarely for V8 to optimize the ladder move), then 12500 timed ticks (2e5 player-ticks) from a fresh state with `process.hrtime.bigint()`, and a GC count over the timed loop. `--pmove-ticks` and `--pmove-warmup` change the counts.
